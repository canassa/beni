\chapter{Conclusion}
\label{sec:conclusion}

We have proposed a checker that makes an in-place edit of a list, while anything else still holds the
old version, a compile error in beni, a pure language compiled to JavaScript, so that every list can be
an array written in place with no run-time ownership information, no annotations in user code and no
silent copy. Edits are the library's named writers and list construction, which consumes a base chosen
by position; so the question that decides whether the rule is usable is one of design: \emph{how should
the language and the checker be designed so that idiomatic code almost never hits the ownership error?}
In-place lists are a feature of one back end, the direct platform, which compiles the view away and
decides what to re-render from compile-time write sets; the rule itself is a rule of the language, checked
for every target, so that one source has one verdict and one meaning everywhere.

Our answer has three parts. The \emph{analysis}: uniqueness at the update site, decided by liveness over
an evaluation-order normal form; a directional, field-sensitive cell analysis whose paths reach into
closure environments, a closure holding only the paths it reads; summaries whose results say whether a
cell is new, an argument's, the closure's own, a top-level value's, escaped or unknown; callback classes
that hand an accumulator owned; an optimistic, validated fixpoint over a stated lattice; exclusive contents
for nested edits, kept by callbacks that keep shape; and an entry protocol for every function a UI runtime
calls, which follows a message's payload to the model paths it reaches. The \emph{language and library}:
construction consumes its base by a fixed rule of position, a chain of \code{++} being one construction;
patterns only read; \code{eq} and \code{compare} only read; \code{init} is a function and top-level lists are
shared; the folds, \code{map} and the container updates supply their callbacks owned; and \code{List.copy}
is the only copy. The \emph{platforms}: only the direct platform writes in place; its runtime hands the
model over, and it re-renders what a message's write set names, never what an identity test calls
unchanged; and commands carry values rather than closures over lists. With these, every idiom we
enumerated---accumulators, folds, recursive builders, lists built by \code{map} and \code{filter}, pipelines,
\code{update} arms that extend a model list, edits inside containers, tuple accumulators---is accepted by
the rules as written, by derivations traced by hand, and what remains rejected is a short list of forms,
each real sharing, a consequence of the position rule, or a named limit, each with a one-line fix.

\section{What we are confident of, and what we are not}

\begin{itemize}
\item \emph{The property is the right one.} It is liveness-based, so a dereference that completes before
the write is free and a dead alias is harmless. Every production system that accepted real array code
has some form of it: Sisal's ordering edges, Clean's observing references, Futhark's syntactic order,
Rust's two-phase borrows, Mazur's forward use. It is incomparable with Clean's occurrence-based
uniqueness, not stronger.
\item \emph{The first-order and closure core holds up.} Three adversarial readings found no accepted
program that observes a write through the checker's own rules; every hole they found was at the boundary
with a platform, in what a renderer or an entry protocol was said to guarantee.
\item \emph{That boundary is where the argument is weakest.} The renderer obligation \Obl{P7} is now
stated over every identity test the direct platform makes, and rests on a restated fact of the write-set
analysis (A12); two of its parts, the element guards (f) and (g), and \Obl{P3}'s rule for markup values,
are additions to that platform's design. Lemmas~\ref{lem:once} and~\ref{lem:entry} are the parts of the
argument we would scrutinise first; the forty-five programs of Table~\ref{tab:counterexamples} are decided as
they should be.
\item \emph{The idioms are accepted by the rules as stated}, by derivations we have traced by hand, not
by an implementation. The frequency of the error on real idiomatic code is unknown until the report mode
runs.
\item \emph{The trusted surface is large}: by our estimate several dozen to a hundred and fifty asserted
rows, where an implementation is most likely to be wrong. The differential run with a stale-read
sanitiser is the instrument for them.
\end{itemize}

What we cannot know from the design alone is whether the rule is worth its cost. It rejects correct
programs---every program that keeps a version of a list and extends it, every list a command captured and
a later message edits---on every target, while only the direct platform gains from it, and it moves part
of its burden onto that platform. Of the two applications we examined, both edit their lists in place under
construction-as-consumption; one is accepted as written, and the other once a value is computed before a
command.

\section{Recommendations}
\label{sec:conc-recommend}

\begin{enumerate}
\item \emph{Enumerate the trusted surface first}, one asserted row and one pinned test program at a time
(\S\ref{sec:soundness-trusted}).
\item \emph{Build the in-place backend and the stale-read sanitiser in a test mode}, and the report mode
(Chapter~\ref{sec:evaluation}) as a checking-only pass with its dump, its idiom classifier and its test
programs, on the design of Chapters~\ref{sec:model} and~\ref{sec:inference}, with the direct platform's
entry protocol as an asserted row (\S\ref{sec:eval-report}). Nothing emitted outside the
test mode changes.
\item \emph{Specify the decided changes} (Changes~1--4) and \emph{the required ones} (Changes~5--8) in the
language's specification before building them, stating where they touch recorded decisions: the
kept-version part of linear prepending, the identity of an append onto an empty list, the lowering of list
literals and \code{++} chains, and the direct platform's element guards and its plan to keep elements that a
row shows out of in-place updates.
\item \emph{Specify \Obl{P1}--\Obl{P7} in the direct platform's design}, with the write-set analysis's
contract restated over contents (A12), and \emph{measure \Obl{P7}} there, on a page whose list elements are
lists edited in place, before that platform writes any list in place.
\item \emph{Run the experiments} over the five corpora, classify every rejection by idiom and by hand, and
run the study of \S\ref{sec:eval-people}.
\item \emph{Decide on the criteria of \S\ref{sec:eval-decisions}}: soundness first, then adoption on the
idiomatic error rate, then the renderer, then which extensions and library choices to build.
\item \emph{If the rule is adopted}, specify the pass as a normative amendment to the checker's design,
the ownership words for \code{foreign} declarations and foreign types in the boundary contract, the
writers' rows, the construction rule and \code{List.copy} in the language definition, the representation
change in the backend's contract, and the message catalogue among the language's diagnostics---then build
it test-first, with the rule set versioned in the interface format.
\end{enumerate}

\section{Limitations and open questions}
\label{sec:disc-open}

\begin{enumerate}
\item \emph{The error rate on idiomatic code}, exact, approximate and positional, per idiom and per target. Nothing in
the literature we know of stands in for it.
\item \emph{The renderer obligation} (\Obl{P7}): what its unguarded element scripts cost on the direct
platform for lists of lists, and whether the restatement of the write-set analysis over contents (A12) holds
rule by rule, as we expect from its rules but have not argued.
\item \emph{The trusted surface}: its exact size, and whether every row can be pinned by a test that the
sanitiser would catch failing.
\item \emph{The proof}: monotonicity is checked case by case but not written out; nothing is mechanised;
the once-closure and entry lemmas are the newest parts and the least tested.
\item \emph{Escapes for the rest of the program} (\S\ref{sec:hard-fibers}): how often a command's capture
blocks an edit, and whether value-taking command constructors (O6) remove most of it.
\item \emph{Mutable cells} (\S\ref{sec:hard-ref}): a sound discipline for in-place edits of a cell's
contents needs a whole-program argument about readers; it is left as a limit with a copy as the fix.
\item \emph{Path-sensitive cell sets} (\S\ref{sec:hard-branches}): worth their cost only if the join tag is
frequent.
\item \emph{Path-insensitive use}: \code{f xs flag = if flag then List.length xs else List.length
[ …xs, 1 ]} is summarised as writing \code{xs}, so \code{n = f xs True; List.length xs} is a false error.
A summary conditional on a \emph{value}, rather than on a class or an argument's state, is outside the
summary grammar.
\item \emph{Interface churn} under inferred summaries; Change~5's optional annotation is the remedy if it
is high. Henriksen's objection that such facts clutter interfaces applies to published summaries too.
\item \emph{The warm rebuild budget}, since a body edit that changes a summary is a signature edit.
\item \emph{Room in front of a list} (O3): the policy, its memory cost, and how often views must be
flattened at the boundary.
\item \emph{Exclusive contents in practice}: how often the containers that real programs edit through
their elements are built exclusively, and which construction most often clears the flag. If decoded
data---every list a schema parses---is not declared exclusive, every nested edit of loaded data is a limit.
\item \emph{View-event payloads}: whether the coarse rule of \Obl{P6} fires often enough to justify
summaries split by message constructor (O7).
\item \emph{The identity promises} (O2): we recommend keeping them; the evaluation's count of rejections
caused by a source read after its filtered result was edited would show whether that is right.
\item \emph{A once closure called once in fact} but passed to a $\mathit{many}$ position stays an error.
\item \emph{A relational entry} (\S\ref{sec:hard-undo}): an undo history of a list needs a second copy because
the entry's fixpoint records which cells each path may hold, not which paths hold one cell at once; whether
the split of a dead container's head can be carried across the entry is open.
\item \emph{Splices and rotations} (\S\ref{sec:idioms-rejected}): written with \code{take} and \code{drop},
they are rejected because of identity promises that fire only at the edges; how often Elm code writes them
decides whether a value-conditional summary, or dropping those promises (O2), is worth its cost.
\item \emph{The rule on targets that do not use it}: how many rejections a program built only for the
template runtime or for Node meets for nothing, and whether that cost of one verdict per source is
accepted in practice.
\item \emph{The development crash screen} must print no program value (A9); this is to be confirmed, or
made so.
\item \emph{Record paths} (\S\ref{sec:compiler-records}): the same rules with a stronger A4.
\item \emph{Primary sources we could not check}: Kone\v{c}n\'y's best-typing proof
\citep{konecny2003typing}, which we know through Aspinall et al.'s report of it; the papers we cite from
secondary sources only, marked as such in Chapter~\ref{sec:related}; and a formal statement of the ``two
semantics coincide'' theorem for Cogent, against which Theorem~\ref{thm:main} could be compared.
\end{enumerate}

The next step is the differential run and the report mode of Chapter~\ref{sec:evaluation}: build them,
run them over real programs, classify every rejection by idiom and by hand, and decide on criteria written
down beforehand.
