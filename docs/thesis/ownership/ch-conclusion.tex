\chapter{Conclusion}
\label{sec:conclusion}

We have proposed a checker that makes editing a list while anything else still holds the old version a
compile error in beni, a pure language compiled to JavaScript, so that every list can be a plain array
written in place with no run-time ownership information and no annotations in user code. The property is
uniqueness at the update site, decided by liveness; the inference is a directional, field-sensitive cell
analysis with per-path liveness and four side conditions, whose function summaries are polymorphic over
the ownership classes of function-typed parameters and are solved for recursive groups by an optimistic,
validated fixpoint. The design depends on three properties of the language---strict evaluation in source
order, saturated calls with no automatic currying, and an existing inference of per-function facts
published in interfaces---and on ten assumptions about the runtime, the library and the platforms, the
most demanding of which is that a UI runtime hand the model over to \code{update} and keep nothing of the
old one.

\section{What we are confident of}

\begin{itemize}
\item \emph{The property is the right one.} It is liveness-based, so reads before writes are free and
dead aliases are harmless. Every production system that accepted real array code has some form of it:
Sisal's ordering edges, Clean's observing references, Futhark's syntactic order, Rust's two-phase
borrows. beni's strict evaluation order gives it with no construct.
\item \emph{The inference is directional, has a best solution, and is linear per round.} The optimistic
fixpoint with validation afterwards is the published recipe of Aspinall, Hofmann and Kone\v{c}n\'y, of
Lean, and of Brandon et al.
\item \emph{The soundness argument has the right shape and the right assumptions}, and its lemmas are
standard. We would direct a reviewer to attack A3 and A4---the platform's obligations---and the list of
\S\ref{sec:soundness-gaps}.
\item \emph{Higher-order code is handled without annotation}, because lambdas are in front of the
checker and function types already carry inferred classes. This is the place every prior system gave up
or required declarations; it is also where a reviewer should look hardest, at the $\mathit{supply}$ and
$\mathit{need}$ edges.
\end{itemize}

What we cannot know from the design alone is whether the rule is worth its cost. It rejects correct
programs---every program that keeps an old version, every list captured by a command that a later
message edits---in exchange for a guarantee about performance, and its benefit to the two applications
we examined depends on widening the set of operations that write in place, which would reject more.

\section{Recommendations}
\label{sec:conc-recommend}

\begin{enumerate}
\item \emph{Build the report mode} (Chapter~\ref{sec:evaluation}) as a checking-only pass with its dump
and test programs, on the design of Chapters~\ref{sec:model} and~\ref{sec:inference}, with the
hand-over obligations assumed for TEA programs. Nothing emitted changes. Its size is that of the effect
pass.
\item \emph{Run it with both demand sets} over the core library, the test corpus, TodoMVC, Conduit and
the table application; classify every rejection by hand; report the counts of
\S\ref{sec:eval-counts}, the churn and the timing.
\item \emph{Decide the demand set first} (change~1). As stated, the rule touches almost nothing the two
applications do; widened, it touches every list edit in them. The number that decides is the rejection
rate under the widened set.
\item \emph{Then decide error versus warning}, on the split between exact and approximate rejections.
The soundness argument holds for both; the choice is the principle's.
\item \emph{Write the six hand-over obligations into the direct platform's specification} whatever the
decision: in-place records would need them too.
\item \emph{If the error is adopted}, specify the pass as an amendment to the checker's design, the
ownership words for \code{foreign} declarations in the boundary contract, the demand summaries and
\code{List.copy} in the language definition, the representation change in the backend's contract, and
the message catalogue among the language's diagnostics---then build it test-first, with the rule set
versioned in the interface format.
\end{enumerate}

\section{Limitations and open questions}
\label{sec:disc-open}

\begin{enumerate}
\item \emph{The rejection rate on real code}, exact and approximate, for both demand sets. Nothing in the
literature we know of stands in for it; Chapter~\ref{sec:evaluation} proposes how to measure it.
\item \emph{The demand set} (change~1): whether the same-shape rebuilds join it, and in which form.
\item \emph{Mutable cells} (\S\ref{sec:hard-ref}): a sound discipline for in-place edits of a cell's
contents needs a whole-program argument about readers; it is left as a limit with a copy as the fix.
\item \emph{Path-sensitive cell sets} (\S\ref{sec:hard-branches}): worth their cost only if the join tag is
frequent.
\item \emph{Path-insensitive use}: \code{f xs flag = if flag then List.length xs else List.length
(List.push xs 1)} is summarised as consuming \code{xs}, so \code{n = f xs True; List.length xs} is a false
error. A summary conditional on a \emph{value}, rather than on a class, is outside the summary grammar;
the evaluation counts how often it bites.
\item \emph{Interface churn} under inferred summaries; change~5's optional annotation is the remedy if it
is high.
\item \emph{The warm rebuild budget}, since a body edit that changes a summary is a signature edit, and
signature edits do not yet meet their budget.
\item \emph{Prepend without the trie} (change~8): decided by the count of loose prepends.
\item \emph{Exclusive contents in practice}: how often the containers that real programs edit through
their elements are built exclusively, and which construction most often clears the flag. If decoded
data---every list a schema parses---is not declared element-fresh, every nested edit of loaded data is a
limit; the decoder's declaration decides it.
\item \emph{The two-slots-one-record hazard} is the one place the design relies on a flag that the
program's construction must establish rather than on liveness alone. We would direct a reviewer to try
to break Lemma~\ref{lem:excl} with containers built through constrained generic code and through
\code{foreign} siblings.
\item \emph{The entry fixpoint's cost}: one whole-program pass over \code{init} and the arms per build,
the only non-modular computation in the design.
\item \emph{A \textit{once} closure called once in fact} but passed to a $\mathit{many}$ position stays
an error; whether a \code{List.map} over a one-element literal deserves a special case is for the count of
the $\mathit{calls} = \mathit{many}$ tag to decide.
\item \emph{The development crash screen} must print no program value (A9); this is to be confirmed, or
made so.
\item \emph{Record paths} (\S\ref{sec:compiler-records}): the same rules with a stronger A4.
\item \emph{Primary sources we could not check}: the best-typing result that Aspinall et al.\ attribute
to Kone\v{c}n\'y \citep{konecny2003layered}, and a formal statement of the ``two semantics coincide''
theorem for Cogent, should be checked against the originals before the design is specified, so that the
shapes of \S\ref{sec:inf-recursion} and Theorem~\ref{thm:main} can be compared with them.
\end{enumerate}

The next step is the report-mode experiment of Chapter~\ref{sec:evaluation}: build the analysis, run it
over real programs, classify every rejection by hand, and decide on the numbers.
