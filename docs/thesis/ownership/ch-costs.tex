\chapter{What the Rule Costs}
\label{sec:discussion}

beni's design follows a principle: \emph{guarantees, not restrictions}. The language keeps Elm's
guarantees---no run-time exception, no silent wrong answer, exhaustive matches, managed effects---but a
rule that does not buy such a guarantee does not belong in the language as an error: it becomes a
warning, gets an escape hatch, or is dropped. A limit that bounds a real blow-up and can be lifted
by an annotation is the model of a restriction done right. Every rule in this design is to be tested
against that principle.

This rule buys a guarantee about \emph{cost}: \emph{an edit the program writes is performed in place},
with no hidden copy and no slower path chosen behind the program's back---\code{set}, \code{update},
\code{swap} and \code{pop} in $O(1)$; \code{push}, \code{cons} and every element a construction adds at
either end of its base in amortised $O(1)$; the elements a construction copies from a read operand in
time proportional to them, as JavaScript's spread copies them; \code{insertAt} and \code{removeAt} in the
$O(n)$ element move a hand-written program also pays. Every $O(n)$ copy a program pays for is a
\code{List.copy} in its source. On the direct platform, where lists are written in place, there is no trie
and no reference count, and the runtime is smaller. The
price is that programs that are \emph{correct} under value semantics are rejected. The design choice made
here is that the error is wanted. This chapter states its price without softening it.

\section{Programs that are rejected}
\label{sec:disc-rejected}

Every one of the following is a correct beni program today; Table~\ref{tab:rejected} gives each with its
fix.
\begin{enumerate}
\item Keeping an old version and then editing it in place: an undo history of lists, a snapshot for a
diff, a ``previous'' field in the model, a test that holds its input and compares it with the output, a
persistent stack whose old versions are read (\S\ref{sec:hard-undo}), and two lists built from one,
\code{a = base ++ [ 1 ]; b = base ++ [ 2 ]}.
\item Reading a construction's base again in the same expression:
\code{\{ model | items = [ …model.items, x ], count = List.length model.items \}}.
\item A command, fiber, subscription or stored closure that captured a list which a later message edits
in place (\S\ref{sec:hard-fibers}).
\item A construction whose base is a top-level list, \code{[ x, …defaults ]}, or a model list in
\code{view}, a derived value or \code{subscriptions}.
\item A closure that edits a captured list in place and is passed to \code{map}, \code{filter},
\code{sortBy} or any other $\mathit{many}$ position, called twice, or handed to the runtime
(\S\ref{sec:hard-closures}).
\item An in-place edit of a list read out of a container that is still live: a dictionary lookup
followed by an extension, or an edit of an element of a list of lists whose contents are not exclusive
(\S\ref{sec:hard-containers}).
\item An in-place edit of a list from JavaScript, a \code{Ref}, a value the runtime retains, or a
\code{foreign} without a summary (\S\ref{sec:hard-foreign}, \S\ref{sec:hard-ref}).
\item A splice or rotation written with \code{take} and \code{drop}, whose identity promises make the
operands possibly one list (\S\ref{sec:idioms-rejected}); and an undo history of a list, which needs a
second copy (\S\ref{sec:hard-undo}).
\item A writer or construction whose base is also another operand, such as \code{[ …xs, …xs ]}, which
fails \Disjoint.
\item Anything the checker's joins, path cut or caps cannot follow (\S\ref{sec:hard-branches}): limits.
\end{enumerate}
The fix is one call, \code{List.copy}, in every case, and the message writes it; where the edit need not
be in place, a reading form---\code{[ x ] ++ ys}, \code{List.concat}, \code{List.map}---is the other fix,
and for commands, computing the value before the command is made. As Henriksen puts it for Futhark, ``an
alias-related type error can always be fixed by copying'' \citep{henriksen2022uniqueness}. What the fix
costs is a copy where the program meant to share. For the first case that is the program's intended
semantics made explicit; for the last it is a copy the programmer pays for the checker's blindness.

\section{What construction-as-consumption costs}
\label{sec:disc-copy}

Making construction consume is what lets idiomatic code run in place (Chapter~\ref{sec:idioms}), and it
has three costs of its own.

\emph{The error lives in the commonest code.} Every spread and every \code{++} on lists is a demand, so the
checker's precision on idioms I1--I7 is not a refinement but the design's main obligation; a single
false error in a common idiom would be met by every user. That is why the evaluation's main metric is the
error's frequency on idiomatic code (\S\ref{sec:eval-decisions}).

\emph{The programmer must learn which operand is reused.} \code{[ x, …ys ]} reuses \code{ys};
\code{[ x ] ++ ys} reads it. Both mean the same list, at different costs and with different consequences
for \code{ys}. The rule is positional and fixed so that it can be learned and read off the text, and
every message about a construction states it (\S\ref{sec:errors-examples}), but it is one more thing to
know, and a reader of Elm code will not expect a spread to have an effect on its operand.

\emph{Versions cost a copy.} Today a prepend onto an older version copies at most 31 elements, so a
persistent stack that keeps versions is linear; under the rules each kept version that is later extended
needs an explicit $O(n)$ copy. This reverses the part of the language's linear-prepend decision that
covers kept versions (\S\ref{sec:idioms-rejected}). It also withdraws one identity promise, that an
append whose left operand is empty at run time is its right operand itself, and it replaces the
specification's right-to-left lowering of list literals and \code{++} chains with one from the base
(\S\ref{sec:model-demands}).

\section{What it costs the representation}

On the direct platform the trie's reason to exist is gone, and so is its persistence: a program that wants versions pays
$O(n)$ per version, explicitly. Prepending in amortised $O(1)$ needs free space in front of a list, so
lists built by prepending are views, as a pattern's \code{rest} already is, and a view handed to
JavaScript must be flattened; the space in front costs memory. The policy is open
(\S\ref{sec:compiler-backend}).

\section{What it costs the API}

A public function's summary is part of its contract. Editing a body can break a caller in another
module with an ownership error that the caller's author did not write---the usual objection to
inferring signatures, that changing the body of a function would change its signature. The interface
firewall makes this visible, not painless. It is also the objection Henriksen raises against
fresh-result annotations: they clutter interfaces, and the programmer ``will not be able to be
completely ignorant of this facet of the type system'' \citep{henriksen2026aliasing}. Inferred summaries
are not written, but they are published, and a caller depends on them; non-locality is, if anything,
greater than with written annotations, since the cause of an error may be a body the caller never
read. Construction-as-consumption sharpens this: a helper that once returned a new list and now returns
one of its arguments, because its body was rewritten with a spread, makes that argument consumed at
every call.

\section{What it costs learners}

The error will fire first in \code{update}, in the very idiom TEA teaches. Crichton and Krishnamurthi
found the chapter on ownership to be ``a significant drop-off point'' for readers of the Rust book
\citep[\S3.1]{crichton2024profiling}, and in Crichton, Gray and Krishnamurthi's study learners who could
usually say why a program was rejected fixed it in only 46\,\% of cases \citep[\S2.4]{crichton2023grounded}.
The message design of Chapter~\ref{sec:errors} and the library choices of Chapter~\ref{sec:idioms} are
the mitigation; they are not a guarantee, and the evaluation plan measures something about people for
this reason (\S\ref{sec:eval-people}).

\section{What it costs on the other targets}

In-place lists are a feature of the direct platform only (rule~7), but the rule is checked on every
target. A program built for the template runtime, or for Node, is rejected wherever a program built for
the direct platform would be, and gains nothing from it: its lists stay persistent, its edits copy as
they do today, and its runtime keeps the trie. What the rule buys there is only that the same source is
accepted for the direct platform with the same meaning. We think that is the right trade, because the two
browser back ends are compiled from one source and each is the other's test oracle; but it is a cost, paid
by every program on a target that does not use the verdict, and the evaluation reports the error rate per
target so that it can be weighed. The core library also carries two implementations of its writers, one
persistent and one in place, with one set of rows.

\section{What two real applications say}

Chapter~\ref{sec:idioms} re-assesses TodoMVC and Conduit (\S\ref{sec:disc-apps}). In short: both now edit
lists in place, in \code{update}; TodoMVC is not accepted as written, and needs \code{init} as a function
and, where it persists, one binding moved before a command; Conduit is accepted as written, by our hand
trace, once a closure holds only the fields of the model it reads. Neither needs anything of the direct
platform's renderer beyond what it already does. What they gain there is small---in-place appends on short
lists, and the smaller list runtime. They test whether the rule is livable, not whether it is fast.

\section{The run-time alternative}
\label{sec:disc-runtime}

Henriksen's 2026 advice to other designers is to avoid this fight: ``unless you have a good reason to
pick this fight, don't do it'', because abstraction hides aliasing, fresh-result annotations clutter
interfaces and convenience functions produce ``spurious and annoying aliasing errors''; he suggests that
``most languages that want in-place updates should probably just use APL/SaC/Koka/Lean-style reference
counting, which reuses memory when the count is one and copies otherwise'', keeping a static discipline
for languages that ``must guarantee that no allocation takes place'' \citep{henriksen2026aliasing}. His
reasons are not specific to type systems, and our design being an inferred pass does not answer them:
he is himself exploring inference outside Futhark's language of types.

Our own prototype study supports his alternative more than it supports us. A run-time scheme with a
sticky ``shared'' bit on each array and no decrements made the same in-place decisions as a full
reference count in every scenario; our static variant matched its in-place writes only with the help
of inlined folds and per-field summaries (Appendix~\ref{app:method}). The bit accepts every program and
never errs. Measured against it, the rule buys three things and only three: \emph{a cost the programmer
can read from the source}---an edit either is in place or is an error, never a silent $O(n)$ copy that
turns a loop quadratic, which in the same study cost a fold 8.2 times the baseline's time---\emph{a
smaller runtime}, with no bit to test on every write and no copy-on-shared path to ship; and \emph{the
absence of run-time ownership state}, which in a garbage-collected target has no other use. Whether those
are worth the rejections is not a question the design can answer. It is why the evaluation measures the
rejections (\S\ref{sec:eval-decisions}).

\section{Escape hatches}
\label{sec:disc-hatches}

\code{List.copy}, always. The reading forms---\code{[ x ] ++ ys}, \code{List.concat}, \code{List.map}---which
read the operands they do not reuse. A persistent-vector library written in beni for programs that want
versions, not a representation of \code{List}. There is deliberately no mode in which the compiler copies
where it would reject: a run-time fallback that copies silently would give up the one thing the rule is
for, an accepted program's cost being readable from its source. Lean offers a diagnostic,
\code{dbgTraceIfShared}, which prints a message ``if the argument's reference count is greater than one''
\citep{lean2025rc}, and Koka's \code{fip} check reports where a function is not fully in place
\citep{lorenzen2023fp2}; both sit beside a run-time fallback that this design does not have. If the
evaluation finds the error too frequent on idiomatic code, the response is to improve the checker or the
library and measure again, or not to adopt in-place lists at all and keep today's persistent
representation; it is not to ship a silent copy (\S\ref{sec:eval-decisions}).
