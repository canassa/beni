\chapter{The Hard Cases}
\label{sec:hard}

Each case below is stated, run through the rules, and marked \emph{solved}, \emph{solved with a
cost}, or \emph{open}.

\section{Closures}
\label{sec:hard-closures}

\paragraph{A closure that reads a captured list, called many times.}
\begin{Verbatim}
total = List.foldl xs 0 (λx acc → acc + List.length ys)    -- reads ys, called n times
zs = List.set ys 0 7                                       -- then edits ys
\end{Verbatim}
The lambda holds \code{ys} under $\env$ and only reads it, so it is not once. \code{foldl} calls it many
times and does not keep it, and the edge check passes. The closure holds \code{ys} while it is live,
which is during the \code{foldl} call only, so at \code{List.set ys 0 7} the holder is dead.
\emph{Solved.}

The reason it is solved is that beni's lambdas are in front of the checker. In type-based usage
analyses the capture counts as a use of the capture's \emph{type}: in Wansbrough and Peyton Jones's
usage analysis, ``all free variables of an abstraction have at least the usage of the abstraction
itself'' \citep[\S6.1]{wansbrough1999once}. Effect- and capture-based systems close the case with
declarations on the API side---Deng et al.'s use and kill effects \citep{deng2025capture}, and
Capybara's markers on mutating and consuming methods \citep[\S6.1]{xu2026capybara}, although Capybara
infers read-only permissions from capture sets---and Affe with an explicit shared borrow \code{\&x}
\citep[\S3.3]{radanne2020kindly}.

\paragraph{A closure that consumes a capture, called many times.}
\begin{Verbatim}
ys2 = List.map xs (λx → [ …acc, x ])                        -- consumes a capture, called n times
\end{Verbatim}
The lambda writes its captured \code{acc}, so it is once: a cell, whose every call is a demand. \code{map}
calls it many times; the edge ``a once lambda requires $\mathit{calls} \le 1$'' fails, and the program is
\emph{rejected}, correctly: the first call writes \code{acc} and returns it, the second writes the same
array, and the first element of the result would change under the second call. The message names the
lambda, the capture and \code{map}'s call count, and offers a fold (\S\ref{sec:errors-examples}). This
is OxCaml's lock rule for closures, under which a closure that consumes a captured value must be
\code{once} \citep[\S3.3]{lorenzen2024oxidizing}, and Futhark's refusal to let the function of a
\code{map} consume an array bound outside it, since ``that would imply the array is consumed once for
every iteration'' \citep[\S3.3]{henriksen2017futhark}. A once closure that \emph{is} called at most
once---\code{Task.scope (λscope → ⋯ [ …acc, x ] ⋯)}, \code{Result.andThen r (λx → [ …acc, x ])}---passes.
\emph{Solved}, with a cost: a once closure passed to a $\mathit{many}$ position is an error even when the
program would in fact call it once for reasons the checker cannot see, for example a \code{List.map} over
a one-element list.

\paragraph{A closure that leaves its binding.} Capture and once-ness belong to the closure value, held
at $\env$ and $\varepsilon$ of its abstract value, so both travel when a closure is returned, stored or
captured by another closure (\S\ref{sec:model-functions}). A closure \emph{stored} in a structure holds
its captures exactly as long as the structure is live, so a record of handlers built from a list of
columns keeps that list from being edited in place while the record is used, and no longer. Programs T7
and T8 of Table~\ref{tab:counterexamples} test this. \emph{Solved.}

\paragraph{A closure that returns what it holds.} A lambda that returns a captured list,
\code{get = λ⊤ → xs}, or a captured closure, \code{give = λ⊤ → push1}, has a result drawn from its own
environment, $\{\env\}$, and a call translates it through the called closure's environment. So
\code{List.push (get ⊤) 3} is a demand on \code{xs}'s cell, held by \code{get}; a \code{map} whose
callback returns a capture produces elements that are the captured cell, not exclusive ones; and two
results of \code{give} are one closure. A local function that consumes what its own recursive call
returns from its environment is once and calls itself, and is rejected. Programs T23--T26 test this.
\emph{Solved.}

\paragraph{Local functions.} A block's local functions form a group whose closures exist from the
block's entry (\S\ref{sec:model-functions}), so a call written above the definition sees the closure's
cell and captures, and two calls of a once local function fail \Dead\ wherever they are written (T31).
Mutually recursive local functions are solved by the group fixpoint. \emph{Solved.}

\paragraph{A once closure the runtime calls.} A closure handed to code the checker does not see---a
markup handler, a callback a sibling keeps, a field of the model that the runtime passes to markup at
every render---may be called any number of times. A value that may be once is therefore allowed to reach an escaping
position only where that position is called at most once, a handler in markup is called
$\mathit{many}$ times, and every asserted row with a function-typed parameter states its call count,
$\mathit{many}$ by default (T27). The body of a spawned fiber or of a command runs once, and may
consume what it captured. A handler that edits a list it captured is rejected with the
message ``this function changes a list it captured, and the page may call it more than once''; the fix is
to keep the list in the model and edit it in \code{update}. \emph{Solved.}

\section{Pipelines, identity and composition}
\label{sec:hard-pipelines}

The pipe is syntax: \code{xs ▷ List.filter p ▷ List.set 0 v} \emph{is}
\code{List.set (List.filter xs p) 0 v}, because pipes are rewritten before anything runs, and a
placeholder or a \code{←} bind is a written lambda, so there is no plumbing function in which to lose
precision. \code{identity x = x} is inferred with $\mathit{res} = \{\pi_1\}$; a user-written
\code{apply f x = f x} with $\mathit{res}$ equal to its callback's result translated through its supply,
here $\{\pi_2\}$ wherever the callback returns its argument; a composition \code{λx → g (f x)} likewise.
Futhark's alias analysis is lossy exactly here and its author is exploring parametricity as the fix
\citep{henriksen2026aliasing}; we analyse the body and let the class carry the result's provenance, so
identity, application and the pipe keep exact aliasing with no free theorem needed. \emph{Solved.}

The residual cost lies in the identity promises the language keeps (\S\ref{sec:bg-lists}): \code{filter}
that keeps every element returns its input itself, as does \code{map} when every result is \code{===} its
element---which it can be only when the callback's result type can hold the element at run time. Such a
function has $\mathit{res} = \{\fresh, \pi_1\}$, so
\code{List.set (List.filter xs p) 0 v} and \code{[ …List.filter xs p, y ]} demand \code{xs} unique too.
In an \code{update} arm, where \code{xs} is a model path the arm replaces, or in a pipeline over a local
list, \code{xs} is dead there and nothing is lost; a program that edits the filtered list and still reads
the source afterwards is rejected, and the message offers \code{List.copy}. Dropping the promises would
remove this cost and move it to the renderer; it is an open proposal (\S\ref{sec:disc-options}).
\emph{Solved with a cost.}

\section{Generic code}
\label{sec:hard-generic}

A type's \code{eq} and \code{compare} only read, by the rule of \S\ref{sec:inf-generic}, so
\code{where k.compare : k, k → Order} and \code{a.eq} need no class. A user method's summary is a class
on the constraint's method type, bound at each call site from the dispatch table's term. Inside the
generic body, a call \code{x.m a} is a call through a function-typed value whose class is the
constraint's, and the body's own summary is expressed over it. A generic body writes a value of type
\code{a} in place only through such a method---\code{x.push 1} with \code{List.push} as the evidence---so
its writes and the side conditions it leaves to its callers are guarded on the method's class and decided
where the evidence is bound; the message points from the caller's argument to the generic body's line
(\S\ref{sec:inf-generic}, T55). \emph{Solved}, at the cost of one rule on \code{eq} and \code{compare}.

\section{Lists in containers}
\label{sec:hard-containers}

\paragraph{A record.} In \code{\{ m | rows = [ …m.rows, x ] \}} the operand is $(m, .\mathit{rows})$,
and the holders of that cell are $(m, .\mathit{rows})$ itself and whatever else holds \code{m} or its
\code{rows}. A record update shares every \emph{other} field's value between the old and the new
record, but not \code{rows}, which the construction's result replaces. After the update \code{m} is dead
unless used later, and a later \code{m.name} reads a path that does not meet $.\mathit{rows}$, so it is
not a use of the cell. A helper that receives the model and replaces \code{rows} is $\unused$ at
$\pi_1.\mathit{rows}$, so passing the old model to it after the construction is not a use either.
\emph{Solved}: a model threaded through helpers that each touch one field is accepted, because
$\mathit{use}$ and $\live$ are per path.

\paragraph{A tuple, a constructor.} The same, through $.i$ and $C\#i$.

\paragraph{A list of lists.} In \code{List.update rows i (λr → \{ r | tags = [ …r.tags, t ] \})} the
lambda's parameter \code{r} is an element of \code{rows}. Two slots of \code{rows} may hold the same
record (\code{[ r, r ]}), or one record may hold one list at two fields; in either case an edit through
one path would be seen at the other, and the cell-set domain cannot tell slots apart
(\S\ref{sec:model-excl}). The derivation therefore needs two things: \code{List.update} must be a
consuming writer that overwrites slot $i$ with the callback's result---a destructive read, so the slot's
old holder is dead during the callback---and \code{rows} must be unique and exclusive, in the deep sense
of \S\ref{sec:model-excl}. Then \code{r} is unique inside the callback, its paths are distinct cells,
\code{r.tags}'s only holder is \code{r}, and the construction is in place: accepted. If \code{rows} is
unique but not exclusive---its elements came from a \code{foreign} that declares nothing, from
\code{List.repeat}, or from a literal that placed one list at two fields---the program is rejected: as a
limit, ``the elements of \code{rows} may share'', when the checker cannot see the construction, and as
sharing when it can; the fix is \code{List.copy r.tags}. With \code{map} in place of \code{update}---Elm's
idiom for editing an element by its id, since Elm's list has no \code{update}---the single-pass row of
\S\ref{sec:model-demands} applies: \code{map} reads each element once and never again, so when \code{rows}
is unique, exclusive and dead after the call it supplies each element owned, and
\code{List.map rows λc → if c.id == id then \{ c | tags = [ …c.tags, t ] \} else c} is accepted, the
one edited card's list written in place and \code{rows} consumed: nothing reads element $i$ after the
callback has run. This one example contains Lean's
motivating \code{groupBy}, Clean's propagation rule and the two-slots-one-record hazard. \emph{Solved
with a cost}: a nested edit needs exclusivity, which the program's own construction of the container
must establish, and which the evaluation counts.

\paragraph{A tree.} An outline or a comment thread is a recursive type,
\code{type Node = Node \{ id : Int, items : List String, kids : List Node \}}, and its paths fold
(\S\ref{sec:model-cells}): \code{.items} stands for the items list of every node. The idiomatic edit is a
recursive function by id:
\begin{Verbatim}
addItem id s (Node n) =
    if n.id == id then Node { n | items = [ …n.items, s ] }
    else Node { n | kids = List.map n.kids (addItem id s _) }
\end{Verbatim}
The construction is a demand at the representative \code{.items}, so \code{addItem} records
$\mathit{xreq}$ on its parameter: no list at two nodes. Inside, \code{n.kids} is kept by the first arm and
reaches \code{.items} again, at other nodes; liveness reads prefix order, so that is not a use of the
cell written, which the $\mathit{xreq}$ makes true. The second arm hands each kid to the recursive call
through \code{map}'s owned supply, which is exclusive because \code{n}'s contents are
(\S\ref{sec:model-summary}); inside the call the kid's own \code{.items} and its descendants' are
different parameter paths, so the recursion checks as the root does. A tree built by stores of fresh
lists is exclusive, and the edit is accepted at every dispatch; one that placed a list at two nodes is
rejected at the call (T49). An edit two levels down written with patterns in one body, rather than by
recursion, needs the split of \S\ref{sec:model-excl} to separate the sub-tree's lists from the enclosing
node's. \emph{Solved with the cost of a list of lists}: exclusivity, established by construction.

\paragraph{A dictionary.} beni's \code{Dict k v} is a balanced tree of constructors written in beni with
no \code{Js}, and it is exported opaquely. Its paths fold (\S\ref{sec:model-cells}): every key of the tree
is reached by one folded path and every value by another, which importers see as the two slots
$\langle\mathit{Dict}\rangle.k$ and $\langle\mathit{Dict}\rangle.v$, both containers whose positions are
the nodes. Its summaries are therefore inferred, not asserted. \code{Dict.empty} is \code{Dict Leaf}, a
top-level value that holds no cell, so a dictionary started from it is not $\shared$. A lookup \code{Dict.get d k} is a non-destructive read: its result aliases a value
inside \code{d} ($\mathit{res} = \{\pi_1.\langle\mathit{Dict}\rangle.v\}$), and \code{d}'s values stop being
exclusive while that result is live. \code{Dict.insert d k v} stores \code{k} and \code{v} in its result,
rebuilds a path and shares the rest with \code{d}; it keeps $\excl$ only if both were stored exclusively,
disjoint from each other and from the rest. \code{Dict.update d k f} is written as a lookup followed by an
insert or a removal: it gets the value at \code{k}, calls \code{f} on it, and inserts the result at
\code{k} or removes the key. By the inferred rules the lookup clears $\excl$ while \code{d} is live---and
\code{d} is live, because the insert reads it---so the callback would be supplied a borrowed value, and
for the same reason the result would not be known exclusive. The module's one asserted row therefore
states both, together, and consumes the dictionary only when the callback consumes what it is given:
\begin{Verbatim}
update : Dict k v [aliased; consumed+aliased and requires excl if g consumes 1], k,
         (Maybe v → Maybe v) [calls ≤1; supply 1 owned π₁⟨Dict⟩.v if g consumes 1 and π₁ excl;
                              supply 1 borrowed π₁⟨Dict⟩.v otherwise; supply 1 excl if π₁ excl]
           → Dict k v [= π₁, fresh; ⟨Dict⟩.v = π₁⟨Dict⟩.v, g.res Just#0;
                       excl if π₁ excl and g keeps shape]
\end{Verbatim}
A callback that only reads, or that builds its answer from nothing it was given,
\code{λ\_ → Just [ t ]}, leaves the dictionary aliased by the result and nothing more:
\code{( Dict.update d k f, Dict.size d )} is accepted, and an \code{update} arm that adds a key with it
does not put the dictionary's values among the paths written in place (T51).
with its argument written beside it: the insert or removal that follows the callback rebuilds the path to \code{k}, comparing keys with
\code{compare}, and reads neither the old value nor any key that aliases it, provided \code{d}'s contents
are exclusive in the sense that includes keys---every key disjoint from every value. Keys of a crossing
type, as nearly all are, satisfy that condition trivially. A dictionary into which one list was inserted
as both key and value is not exclusive, and its \code{update} supplies a borrowed value (T32). The flag
the row keeps is what lets a fold call it again: \code{foldl} carries its accumulator's exclusivity from
one call to the next (\S\ref{sec:inf-classes}), so a grouping fold is accepted at every iteration and not
only at the first (T44, Appendix~\ref{app:groupby}).

Huisinga's motivating example for Lean \citep[\S2.1]{huisinga2023lean}, in which a group is looked up,
extended and re-inserted, is \emph{rejected} as real sharing with the holder named---the dictionary is
live across the construction, because it is passed to \code{insert} afterwards---and the message offers
\code{Dict.update}, which is accepted when the values are exclusive (Appendix~\ref{app:groupby}). Lean
accepts the lookup form and copies silently at run time, because the dictionary still holds the group;
the program is quadratic \citep[\S2.4]{huisinga2023lean}. \emph{Solved with the same cost.} A set is the
same, with keys only.

\paragraph{An opaque record.} elm-spa-example's article feed, which Conduit copies, is
\code{opaque type Model = Model Internals} over a record with two lists, \code{errors} and
\code{articles}, and its \code{update} appends to \code{errors} in place. Inside the module, that demand
leaves \Disjoint\ between \code{.errors} and \code{.articles} to the callers. If importers saw one path
$\langle\mathit{Model}\rangle$, there would be no second path to check it against, and a module whose
constructor placed one list at both fields would be accepted, the append showing through the other field
(T48). With slots (\S\ref{sec:model-cells}) the importer sees two, the demand is at one of them, and the
check is the one it makes for two fields of its own record. In Conduit the home page receives the feed as
a command's payload, built by the feed's \code{init} from \code{errors = []} and a decoded list of
articles, so the two slots hold different cells at every entry and the append is accepted. Requiring the
whole opaque value exclusive instead, the cheaper rule, would reject it: after the feed replaces an
article with a message's payload, two positions of \code{articles} may hold one record.
\emph{Solved}, at the cost of publishing each opaque type's slot count (Change~9).

\section{Recursion and folds}
\label{sec:hard-recursion}

\begin{Verbatim}
go xs acc = case xs of
    [] → acc
    [ x, …rest ] → go rest [ …acc, f x ]
\end{Verbatim}
\code{go}'s group is one declaration. The optimistic start assumes \code{acc} $\unused$ and the result
empty. In round 1 the tail call passes \code{[ …acc, f x ]}, a construction whose base is \code{acc}'s
cell, whose only holder in the frame is \code{acc} itself; after the jump \code{acc} is rebound, so it
is dead. Hence $\mathit{use}(\mathit{acc}) = \{\mathsf{R}, \mathsf{A}, \mathsf{W}\}$, and $\mathit{res} =
\{\pi_2\}$ (the \code{[]} arm returns \code{acc}) united with the recursive call's result. Round 2 gives
the same; validation passes. \code{List.foldl} in the core library has this shape, with its callback's
class carrying the accumulator's ownership (\S\ref{sec:inf-classes}), so
\code{List.foldl xs [] (λx acc → [ x, …acc ])} is accepted and runs as the in-place builds of our
prototype study did. A callback that returns, as the next accumulator, a list it does not own---a
top-level list, a capture, an element it was supplied borrowed---is rejected, because the fold supplies
the accumulator owned only when the callback returns owned (\S\ref{sec:inf-classes}, T46). Mutual recursion
is the same fixpoint over the group. \emph{Solved.}

\section{Branches that keep the old value}
\label{sec:hard-branches}

\begin{Verbatim}
case List.get xs i of
    Just v  → v
    Nothing → List.set xs i d ▷ List.get ⋯
\end{Verbatim}
\code{v} is an element, not the array, and the \code{set} writes a slot; per-arm liveness makes
\code{xs} dead after the \code{set} on the \code{Nothing} arm, where it is the operand. Accepted. The
shape that Rust's borrow checker has long rejected and still rejects on its stable release---the third
``problem case'' of non-lexical lifetimes \citep{rfc2094}, deferred from that work to Polonius
\citep{matsakis2018alias}---does not arise, because beni has no references into a list: \code{get}
returns the element, not a pointer to the slot.

In \code{ys = if c then [ …xs, 1 ] else xs}, $A(\mathit{ys})$ is \code{xs}'s cell on both arms---in
the \code{then} arm as the construction's result, in the \code{else} arm as an alias. The demand in the
\code{then} arm asks whether \code{xs} is live after it \emph{on that arm}, and it is not: the
\code{else} arm's use of \code{xs} is not on the \code{then} path. Accepted, and \code{ys} owns the cell
on both arms. Futhark's rule that the aliases of a conditional are the union of both branches
\citep[Fig.~5]{henriksen2017futhark} is kept for cells, but liveness is per path, so a value ``used''
only in the arm not taken causes no false error. \emph{Solved.}

What remains coarse: in \code{xs = if c then a else b} followed by \code{[ …xs, 1 ]}, both \code{a}
and \code{b} must be unique, so a later read of \code{a} on the path where \code{xs} is \code{b} is a
false error. A known imprecision; the evaluation counts how often it occurs.

\section{The foreign boundary}
\label{sec:hard-foreign}

A \code{foreign} has no body; its declaration carries a summary as it already carries an effect rung
and its \code{sync} marks. \emph{The default is pessimistic}: a parameter that says nothing is read and
escaped, because beni's existing contract lets a sibling keep a list it was given in order to read it
later, as some platform code does; a result that says nothing is $\top$; and a function-typed parameter
that says nothing is called many times. A sibling that only reads its argument during the call says
borrowed; one that returns a fresh plain array that nothing else holds (already the rule for arrays a
sibling returns) says fresh; \code{Debug.log}, which is beni over \code{Js}, has an asserted row saying
that it reads its second argument and returns it. A platform author who writes nothing therefore loses
precision and never soundness. \code{Js.from x} marks \code{x} escaped forever; a \code{Js.call} that
passes a list is a call with no summary, which reads and escapes it.

\emph{Foreign types} are the other half of the boundary. A \code{foreign type}---the markup type
\code{Html msg}, the runtime's types for jobs, outlets and fibers---has no definition, so it does not
cross unless its declaration says so, and its values carry the cells their constructors put under the
opaque step. Every constructor of such values has an asserted row. A markup site stores its handler
closures and the messages it will send under the markup value's opaque step, and its row says that each
handler is called $\mathit{many}$ times. The captures are then held for as long as the markup value is
live in the program, as a closure stored in a record holds its captures; what the platform keeps of the
markup that \code{view} returns is said by the platform's entry row (\S\ref{sec:hard-tea}). So in
\begin{Verbatim}
field = <input onInput={λs → Typed (String.join "," xs)} />
ys = List.push xs "b"
\end{Verbatim}
\code{field} holds \code{xs}, it is used after the push, and the push is rejected by \Dead\ (T28). The
captures are not escaped at the markup site: the template runtime keeps a handler from one render to the
next, but it writes nothing in place, and the direct platform's listener bodies keep nothing from one
dispatch to the next (\Obl{P3}). The existing build-time checks
on siblings are unchanged; the new promises are tested as the effect rung is, by review and by a test
program that pins each row (A8). The residual risk is a sibling that lies---a bug in privileged code of
the same class as a wrong effect rung. \emph{Solved, by contract} (A2, A6), with the trusted surface of
\S\ref{sec:soundness-trusted}.

\section{Fibers and commands that capture values}
\label{sec:hard-fibers}

\code{Cmd.perform (λsend → ⋯ todos ⋯)} captures \code{todos} in a body that the runtime stores and runs
later. \code{Cmd.perform}'s row puts $\mathsf{E}$ on its argument's $\env$, so every captured path is
escaped at the capture---every path of a captured variable that the body uses, and only those
(\S\ref{sec:model-functions}). A command that reads \code{model.session} escapes the session, not the
model's lists: a parameter path gains $\mathsf{E}$ in the enclosing function's
summary, and a list the arm built is named $\esc_k$ in its result. Either way the entry protocol carries
the escape into every later dispatch that may receive the same cell in its model (\S\ref{sec:hard-tea}).
Spawning a fiber, the bodies of a parallel combinator and \code{Ref.set} are the same. A body the callee
calls synchronously and does not keep---the body of a structured-concurrency scope, the acquire step of a
bracket---is called at most once and kept by nothing; a bracket's \emph{release} is stored on the fiber's
list of finalisers and escapes. These facts are asserted rows of the core \code{Task} module and
inferred for its beni wrappers.

Nothing here depends on when a command's body runs. A body that cannot suspend still runs after
\code{update} returns, and the platform's dispatch order lets other messages reach \code{update} before it
does: a body earlier in the same batch may send a message, which is dispatched at once (T29). So a
command's captures are escaped whether or not its body can wait.

\paragraph{The cost, and the library choice that removes most of it.} An escape is per cell and for the
rest of the program: once an arm hands a list built from \code{model.todos} to a command, every in-place
edit of \code{model.todos} is rejected, at every dispatch, even after the command has finished. That is
coarse. Two refinements would recover some of it, and we adopt neither. A fact ``held until the command's
fiber ends'' would let a later edit through once the runtime knows the fiber has ended, which is a fact
about run time; and a subscription's tagger, though replaced at every render, may run with an old model
list between a dispatch and the next render, when several events arrive before a frame. What removes most
of the cost is not analysis but the shape of commands. A command that persists or reports a list needs a
\emph{value} computed from it---the encoded text, a count, a request body---and when that value is computed
before the command is made, the command captures a string and the list is never escaped:
\begin{Verbatim}
save todos =
    text = encode todos                       -- read now
    Cmd.do λ⊤ → saved (Storage.set Local key text)
\end{Verbatim}
Elm's own HTTP library has this shape, encoding a request body when the command is constructed; command
constructors in beni's platforms that take values rather than closures would make it the only shape
(\S\ref{sec:disc-options}). The message for a capture offers exactly this rewrite
(\S\ref{sec:errors-examples}). \emph{Solved by escape}, with the cost stated; the evaluation counts the
tag on its own (\S\ref{sec:eval-counts}).

\section{The TEA runtime: an entry protocol}
\label{sec:hard-tea}

A TEA platform calls the program's functions---\code{init}, \code{update}, \code{view}, subscriptions
(in \code{settle}), the bodies of commands, and, on the direct platform, derived values and listener
bodies---on a model the runtime holds between calls. None of these calls has a caller in the program to
discharge \Unescaped, \Dead\ and \Disjoint\ for the model, so the platform must say, for each one, what it
passes owned, what it passes only to read, and what it keeps of the result. It must cover every entry, or
a \code{view} that builds on a model list in place is accepted and writes it at every render.

\paragraph{Which platform.} By rule~7 of \S\ref{sec:bg-language}, only the direct platform writes lists
in place. The template runtime keeps persistent lists, so its holds---the handlers it keeps from one
render to the next, and every identity skip of \S\ref{sec:bg-browser}---can never meet an in-place write,
and it needs none of the obligations below. The checker nevertheless evaluates every program against
one entry row, the direct platform's, whatever the target, so that a source has one verdict on both
browser back ends; on the template runtime that verdict changes nothing a program does.

\paragraph{The protocol.} Table~\ref{tab:entry} gives the protocol. It is an asserted row on the
function the runtime actually calls---on the direct platform, the program constructors, which its
lowering recognises---whose record parameter's fields carry the classes in the table. The row models the
runtime's loop---the model is \code{init}'s result, then each dispatch's result---as a recursive caller of
\code{update}. The checker evaluates it \emph{at the call of the program constructor}, from the published
summaries of the functions in the record, as it evaluates any call: it computes the abstract model at
entry as the least fixpoint of \code{init}'s result and \code{update}'s result over it---cells, with
numbered fresh cells for aliasing, $\esc_k$ and $\mathsf{E}$ for escapes, $\shared$ and $\top$ carried, and
the exclusive-contents flag, from $\mathit{xres}$---and then checks every path that \code{update} writes as a
caller would check an argument. Because the program's functions are known at that call, every guard of
the row is decided there and none is left over. Nothing in this is whole-program: it reads interfaces.

A program value may be mounted several times on one page. The protocol is per mount, and it needs nothing
more than the constructor's call: \code{init} is a function the runtime calls once per mount, so each
mount's first model has the cells \code{init}'s summary describes and no mount sees another's, and the
other functions of the record are shared between mounts only as closures, whose captures the row treats
as it treats any closure the runtime calls many times (T30).

\paragraph{The obligations.} The table rests on seven obligations on the direct platform's lowering and
runtime.
\begin{description}[leftmargin=1.2em,font=\normalfont\itshape]
\item[\Obl{P1}, hand-over.] The runtime calls \code{update} with the model \emph{owned}: after the call,
it holds no content reference to any list reachable from the old model, and the model it keeps is
replaced by the result.
\item[\Obl{P2}, reads before the arm are the handler's.] Anything the runtime needs from the old
model---the indices it uses to locate rows, a derived value's old input---is read \emph{before} the arm,
into locals, as scalars. A handler that kept the old model and read one of its lists after the arm would
read the new contents, which the lowering must not generate. The direct platform as designed binds
\code{const old = model} before the arm when a script needs an index symbol or a derived value's old
input, and its scripts read \code{old} after the arm; reading a scalar field of \code{old} then is
harmless, but an index computed from an old list---the position an identifier had before a removal---is
not. So the binding must become a set of scalar locals, each computed before the arm (Table~\ref{tab:p7cost}).
Whether any derived value's old input is a list we have not found in its specification; if one is, it must
be read into a scalar or recomputed, never held.
\item[\Obl{P3}, nothing made by an earlier evaluation of the view is used after a conflicting dispatch.]
A listener body runs when its event fires, as program code, on the model, row item and derived slots
that are current \emph{at that moment}: it evaluates its handler expression then, and holds no value
computed before. After every dispatch the runtime re-obtains each instance's item from the new model for
every row whose path is in the write set, so that no listener uses a reference obtained before an
in-place write; rows outside the write set hold items whose cells were not written. Markup that is a
value rather than a compiled site---a \code{List (Html msg)} hole, a recursive helper---keeps its handler
closures between dispatches, so its read paths must include the paths its handlers' bodies read, and
every handler whose write set conflicts with them evaluates it again, installing new closures, before
the dispatch ends and so before any later listener runs. So a handler made by an earlier evaluation of
\code{view} is never called after a dispatch that may have written what it reads. The first two
sentences describe the direct platform as designed; the third is an addition, about its fallback for
markup values.
\item[\Obl{P4}, slots are recomputed.] A derived value's slot that holds a list is recomputed by every
message whose write set conflicts with its reads, before any DOM write reads it, and the old slot value
is never dereferenced after the arm. A derived value only reads the model, so a derived value that
writes a model list in place---by a writer or as a construction's base---is an error at its definition.
\item[\Obl{P5}, the entry is checked as a call.] The abstract model at entry is the fixpoint described
above, and it includes the escapes made by \emph{every} function the platform calls: \code{init}, every
arm of \code{update}, every command body, every subscription, and \code{view} through its row in
Table~\ref{tab:entry}. \emph{Aliasing between paths}: an \code{init} that places one cell at two paths,
\code{xs = ⋯; \{ a = xs, b = xs \}}, publishes $\mathit{res}(.a) = \mathit{res}(.b) = \{\fresh_1\}$, so an
edit of \code{model.a} fails \Disjoint\ against \code{model.b}. \emph{Escapes across dispatches}: a cell
that \code{update}'s summary marks $\mathsf{E}$ on a model path, or names $\esc_k$ in its result---captured
by a command, a subscription, a stored closure, a \code{Js} call---is escaped at every later entry,
because the runtime may hand the same cell back in the next model. \code{view}'s handlers make no escape,
by \Obl{P3}: a handler made by one evaluation of \code{view} is not called after a dispatch that conflicts
with what it read, and a handler's message reads the model at its event. \emph{Shared and unknown cells}:
an \code{init} or an arm that returns a top-level list puts $\shared$ in the model, and one that returns a
value the runtime retains puts $\top$; an edit of either is rejected. \emph{Exclusive contents}: the entry
carries $\mathit{xres}$ through the fixpoint, so a path is exclusive at entry when \code{init}'s result is
exclusive there and every arm keeps it so. \emph{Payloads}: the cells a message brings are named by
\code{update}'s first parameter, and the fixpoint follows them through \code{update}'s results into the
model, where \Obl{P6} decides whether they may be written.
\item[\Obl{P6}, payloads.] A message's payload list is unique at the arm only if nothing else holds it
when the arm runs. \emph{Program senders.} The runtime calls \code{update} with the messages that command
and subscription bodies send, so a send is a \emph{supply} to \code{update}'s first parameter, in the sense
of \S\ref{sec:model-summary}: a command body is a lambda whose parameter \code{send} is a function value,
and the body's summary already records, for that parameter, what each call supplies and whether it is
\emph{owned}---unique, unescaped and disjoint across its paths at the send, and dead after it. The rows of
the command constructors carry that fact into the command value: under the opaque step of a value of type
\code{Cmd msg} or \code{Sub msg}, one bit per tracked path $p$ of \code{msg}, set when every payload any of
its sends may put at $p$ is supplied owned. \code{Cmd.perform} reads the bit off its body's class;
\code{Cmd.task work tag} sets it when \code{work} and \code{tag} both return owned; \code{Cmd.map}
translates the bits through its tagger's $\mathit{res}$; \code{Cmd.batch} takes the conjunction over its
list; \code{Sub.map} and the subscription constructors do the same. The bits are facts of a result, not
guards, so they travel through summaries like $\mathit{xres}$, and their size is bounded by the message
type's tracked paths, not by the number of sends.

At the program constructor's call the entry fixpoint reads the bits off the commands that \code{init} and
\code{update} return, and applies the supply edge with \code{update} as the callee and the model loop
around it: \emph{a message path $p$ whose payloads are not all supplied owned must reach no cell written
in place}---neither a path of \code{update}'s message parameter with $\mathsf{W}$ in its summary, nor,
through \code{update}'s results round the loop, a model path that some arm writes in place. So a payload
stored at \code{model.rows} by one arm and extended in place by another, one dispatch later, must be owned
at its send, and a sender that reads the list after sending it is rejected (T38); a payload that an arm
extends in place without storing it, \code{Got rows → \{ model | total = List.length [ …rows, 0 ] \}}, is
the same (T50); a payload that reaches no cell written in place may be borrowed, and a sender that keeps
using it is accepted (T34). \code{Cmd.task}'s payload is owned when its work returns a list it built,
as a decoder's result is, and \code{Http.expectStringResponse}'s when its callback returns owned. The
check needs nothing but interfaces, and no guard survives to the constructor: the bit is decided where
the send is written, the reach where the program is started. The message points from the send to the arm
that edits what the payload reaches. \emph{View events}: a message built from a model path or a row item,
\code{onClick=\{Keep model.rows\}}, hands the arm a cell the model may still hold; such a payload path is
aliased with the model at every arm, because the check reads \code{update}'s summary, which is not split by
the message's constructor. That is coarse---one such handler makes every in-place edit of
\code{model.rows} fail \Disjoint, in arms that never see \code{Keep}---and we accept it with a limit tag; a
summary split by the constructor of \code{update}'s message is a possible extension, decided by how often
the tag fires. The message offers to send an identifier instead of the list.
\item[\Obl{P7}, write sets, not identity, decide what to re-render.] Stated below.
\end{description}

\paragraph{\Obl{P7} precisely.} The obligation is stated over \emph{entry cells}, the objects the model held
when the dispatch began, because those are the only objects a dispatch can change while keeping their
identity: an arm writes in place only cells the model held at entry and cells it made itself, and a cell
it made itself is an object the renderer has never seen. For a program, let $\mathit{IP}$ be the entry
cells that may be written in place:
\begin{itemize}
\item the lists at the model paths, list positions included, at which \code{update}'s published summary
has $\mathsf{W}$, named by their entry paths: $\pi_2.p \in \mathit{IP}$ when $\mathsf{W} \in
\mathit{use}(\pi_2.p)$;
\item if the direct platform's own in-place update of records is adopted with this design, the records at
the paths it assigns through, which its own rule proves owned (\S\ref{sec:compiler-records});
\item closed under the release representation (\S\ref{sec:model-cells}): a path through a constructor step
of a type with one constructor of one field is identified with its field's path, \emph{in every build}, so
that with \code{type Column = Column (List Card)} the column at \code{cols[*]} is in $\mathit{IP}$ whenever
its cards at \code{cols[*].Column\#0} are. Development and release builds then emit the same scripts.
\end{itemize}
For a message key $\kappa$ with write set $\mathit{writes}(\kappa)$, let $\mathit{IP}_\kappa$ be the cells
of $\mathit{IP}$ whose entry path conflicts with $\mathit{writes}(\kappa)$. A value \emph{may hold an
$\mathit{IP}_\kappa$ cell} when its abstract value, by the ownership analysis of the code that computes it,
names such a cell at any of its paths. That analysis reads the \emph{new} model, whose paths' cells are
named in entry terms by \code{update}'s $\mathit{res}$, so a cell an arm moved is still found: in
\code{\{ model | a = [ …model.b, x ], b = [] \}} the entry cell of \code{b} is written and is now at
\code{a}, and whatever reads \code{a} may hold it. (The renderer's last value at \code{a} is another cell,
because \Disjoint\ held between \code{a} and \code{b} at entry.) Examples are \code{model.todos};
\code{List.filter model.todos p}, whose result may be its input; a user helper that returns its argument on
some branch; \code{Dict.values model.groups} when \code{Dict.update} edits the groups in place; a row's
item when its list's elements may hold one. The obligation is:
\begin{quote}
\emph{In the handler of $\kappa$, no test \code{a === b}, and no comparison of two views by base and
offset, concludes ``unchanged, skip'' about a value that may hold an $\mathit{IP}_\kappa$ cell. Whatever
reads such a value runs because the key's write set conflicts with its read paths.}
\end{quote}
Concretely, over every piece of the direct platform's output:
\begin{enumerate}[label=(\alph*)]
\item \emph{Groups.} A group runs exactly when its read paths conflict with $\mathit{writes}(\kappa)$, and
then compares only the leaf values it computes, scalars that hold no cell. \emph{Already so} for scalar
holes. A hole that shows a structure---a list, a markup value, a \code{Maybe Html}---is, in the platform's
words, ``written when its key writes it (a \code{value} write at or above its path) and compared by identity
only where this document says identity holds''. A structure that may hold an $\mathit{IP}_\kappa$ cell must
instead be written whenever its group runs, whatever the tag of the write: a field of type
\code{List (Html Msg)} shown whole and extended by \code{[ …model.extras, <li/> ]} is written by an
\emph{append}, not a \code{value} write, and keeps its identity. The alternative is to compile such a hole
as a \code{<For>}. \emph{To be added} (T54).
\item \emph{Derived values and \code{let}s.} A derived value is recomputed when its read paths conflict;
when it may hold an $\mathit{IP}_\kappa$ cell, every reader of it that conflicts runs after the
recomputation, and no reader is skipped because the new value is \code{===} the slot. \emph{Already so}
in the design, which has no such skip; the obligation forbids adding one for these values.
\item \emph{Helpers and components.} Their markup is inlined or emitted as a shared site whose groups run
by conflict of their read paths, anchored through the arguments. No call is skipped because its
arguments are \code{===} to last time when an argument may hold an $\mathit{IP}_\kappa$ cell.
\emph{Already so}; to be kept.
\item \emph{Branches and \code{Show}.} The condition is evaluated again when its reads conflict, the arm
that stays runs its conflicting groups, and a \code{Show}'s value---a list, say---is never the ground for
skipping its body. A keyed \code{Show}'s key is of a key type, a scalar. \emph{Already so.}
\item \emph{Row inputs.} A row group that reads an enclosing path, such as \code{model.picked}, runs on
every row when that path conflicts; a selector's two-row visit compares keys, which are scalars.
\emph{Already so.}
\item \emph{Indexed edits and swaps.} For a list whose elements may hold an $\mathit{IP}_\kappa$ cell, the
script of an indexed edit or a swap is guarded by its range test (and, for a swap, \code{κ₁ !== κ₂})
only, and runs the row groups that the sub-writes conflict with \emph{unconditionally} on the rows it
names, re-reading their items; the guard \code{get(xs, κ) !== insts[κ].it} stays for every other list.
The swap's element guard also made the script idempotent, so that rows already in their new order are left
alone. Dropping it is safe because the platform's handler never visits again an arm it mounted earlier in
the same dispatch, whose rows were built from the new model, and because one key carries one tag per list,
two swaps of one list joining to a replacement. \emph{To be added.}
\item \emph{The \code{map} idiom, the merge and the reconciler.} For a list whose elements may hold an
$\mathit{IP}_\kappa$ cell---a model list, or a derived one reached through the reconciler---the identity walk
patches every row, running its conflicting groups and re-reading its item, instead of the rows whose item
is not \code{===} the new element; the merge and the reconciler still \emph{match} rows by key or by item
identity, which an in-place write does not disturb, but patch every kept row instead of the kept rows whose
item changed. \emph{To be added.}
\item \emph{Length guards.} Append, prepend, insert, remove and clear are guarded by comparing the new
list's length with the instance array's, which reads the current list. \emph{Already so.}
\end{enumerate}

\paragraph{Why write sets provide it.} Everything above is decided when the handler is compiled:
$\mathit{IP}$ from \code{update}'s summary at the program constructor's call, $\mathit{writes}(\kappa)$ from
the write-set analysis, and whether a value may hold an $\mathit{IP}_\kappa$ cell from the ownership
analysis of \code{view}'s code. The handler contains either the guarded script or the unguarded one, and
nothing is tested at run time that the identity-based design did not test. The argument has two halves.
\begin{itemize}
\item \emph{What runs by conflict reads current contents.} If the content of the value at an anchored read
path $r$ differs from what it was at the last render, then $r$ conflicts with $\mathit{writes}(\kappa)$.
This is Lemma~\ref{lem:writes}, which derives it from the write-set analysis's own soundness statement,
over identity and for the value semantics: the in-place run and the value run agree on the contents of
every current reference, and in the value run a list whose contents changed is a new object, which the
write set must name.
\item \emph{What is skipped by identity did not change.} A value's content can change while its identity
stays only if some object reachable from it was written in place during the dispatch. The only such
objects are the cells of $\mathit{IP}_\kappa$---lists written by accepted demands, records the platform
assigns through---named modulo the release representation, under which a constructor erased to its field
is rebuilt only when its field is. Every other object reachable from the value is either new or unchanged.
So an identity test on a value that may hold no $\mathit{IP}_\kappa$ cell is as sound as it is today, and the
obligation forbids every other.
\end{itemize}
The direct platform's verification mode, which re-evaluates every derived value after each message in a
development build, and its differential fuzzing against the template runtime, remain as tests of the
lemma and of the analysis that decides ``may hold''.

\paragraph{Four programs.} \emph{TodoMVC's count and \code{hidden}.} Its Enter arm appends with
\code{model.todos ++ [ new ]}, so $\mathit{IP} \ni \mathit{todos}$, and the key's write set holds
\code{todos} with the tag \emph{append}. The derived value
\code{left = List.length (List.filter model.todos λt → not t.completed)} reads \code{todos}, conflicts,
and is recomputed (a); the groups of \code{hidden=\{List.isEmpty model.todos\}}, of

read \code{todos} or \code{left}, conflict, run, compute a boolean or a string, and write it on
difference (a). The \code{<For>} over \code{List.filter model.todos (visible model.filter \_)} reads a
derived value that may be \code{model.todos} itself, an $\mathit{IP}_\kappa$ cell; it runs because it
conflicts (b), and reaches the rows through the reconciler, which the direct platform uses for a derived
list; a todo is a record that holds no list, so \code{todos[*]} is not in $\mathit{IP}$ and the
reconciler's patch test stays as it is. The new row appears, the section and the footer show, and the
count reads 1 (T35). Nothing in TodoMVC needs (f) or (g). \emph{A row input.}
\code{Pick id → \{ model | picked = [ id, …model.picked ] \}} with rows whose class reads

\paragraph{The obligation a future slice must meet.} The direct platform's design plans in-place updates
as its last step, for model paths it proves unshared, and never for an element that a row shows; that
restriction is what lets it keep its element guards. The in-place lists of this thesis write elements of
rendered lists in place whenever the checker accepts the edit, so the slice that adopts them must meet
\Obl{P1}--\Obl{P7} as stated here, (f), (g) and \Obl{P3}'s markup values included, and pin each with a test
program that runs in a page, in a development and a release build: the four programs above, a by-id
\code{map} edit of a board of columns, a swap of two rows of a grid, a structure hole extended in place,
and a removal by identifier whose index the handler computes. The same platform's design plans in-place
update of \emph{records} on paths it proves owned, under its own rule that no group decides
``unchanged'' by the identity of an object on an in-place-written path; if both are adopted, the records it
assigns through are in $\mathit{IP}$, and the two mechanisms must be adopted together or not at all
(\S\ref{sec:compiler-records}). Until then, the direct platform keeps persistent lists too, and the
checker's verdicts change no program's meaning anywhere. For a table application's row swap and row update, whose
rows are records, the derivation is short: the model is owned at entry; \code{model.rows} is escaped by no
arm and aliased by no other path; the operand's only holder is $(\mathit{model}, .\mathit{rows})$; the
model is dead after the arm; and the swap is two assignments on the plain array, its script still guarded
by element identity, since \code{rows[*]} is not in $\mathit{IP}$. \emph{Solved, conditional on the direct
platform meeting the protocol}: \Obl{P2}'s scalar locals, \Obl{P3}'s re-obtaining of items and its rule for
markup values, (a)'s rule for structure holes, \Obl{P7}(f) and (g), and the closure of $\mathit{IP}$ under the
release representation are not yet in its specification.

\paragraph{\code{init} is a function.} In beni's TEA platforms today \code{init} is a value, usually
declared at top level or written inline in the program record. Under the rules \code{init} is a function
of \code{⊤} or of the program's flags, as Elm's own \code{init} is a function of its flags, called by the
platform once per mount; a \code{Reset} arm calls it again and gets new cells (T14). The alternative of
keeping a value \code{init} and ignoring its hold is unsound: a program whose \code{Reset} returns the
value would get back the array earlier messages wrote, and a program mounted twice would share one model's
arrays between the mounts. A top-level list that \code{init} returns is still shared (T21), and so is a
top-level \code{initialModel} record that it returns (T53); the message offers to build it in a function or
to copy it there (\S\ref{sec:model-check}).

\paragraph{\code{view}, derived values, subscriptions and spreads.} These receive the model to read. A
construction whose base is a model list, \code{[ …model.pinned, …model.recent ]}, would write
\code{model.pinned} at every render, so it is an error at the definition, and the message offers
\code{List.concat [ model.pinned, model.recent ]}, which builds, or a construction whose base is a new
list (T13). A construction on a list \code{view} builds from the model, such as
\code{List.map model.items viewItem ++ [ addButton ]}, consumes only the new list, since \code{map}'s result
cannot be its input when the element and the result types cannot share a value (\S\ref{sec:model-demands}).
A text search found no construction with a model list as its base outside \code{update} arms in the
compiler's test programs and the example applications; in markup, lists are usually rendered rather than
concatenated.

\section{The explicit copy}
\label{sec:hard-copy}

\code{List.copy : List a [borrowed] → List a [= fresh]} is a shallow copy, \code{a.slice()}, or for a view
\code{b.slice(o, o + n)}. The elements are the same values; records are immutable and need no copying; a
list nested inside an element is still shared, and editing it in place is still an error whose message
names the inner holder, with the fix \code{List.map xs List.copy} or a copy at the inner edit. A copy has a
new identity, so a list keyed by reference in the view sees new rows, which is right for a list whose
contents the program is about to change behind the original's back. Copying a list that is already
unique is legal and wasteful; the evaluation counts such copies to decide whether a warning is
wanted---a warning, never an error. \emph{Solved.}

\section{Views}
\label{sec:hard-views}

\code{[ x, …rest ]} in a pattern binds \code{rest} to a view $(b, o, n)$ of \code{xs}'s base array, a
suffix; \code{[ …init, last ]} binds \code{init} to a view that is a prefix; \code{List.drop} and
\code{List.tail} return views too. A view is a contiguous slice of its base, a holder of the base, and a
write through a view writes the base: \code{List.set rest i v} is \code{b[o + i] = v}; a construction with
a view as its base prepends into $b[o - 1]$ when $o > 0$, and pushes by writing $b[o + n]$---which for a
prefix view overwrites the slot after the view's last element, and for a suffix view is the base's own
end. The demand on the view therefore asks that every holder of the base---\code{xs} included, and every
other view of it---be dead, and that is what makes the overwrite safe: the slot after a prefix view holds
an element that only the dead base reached through that slot (\code{last}, in the pattern above, is held
as a value, not as a slot). In the common walk (\code{go rest ⋯} with \code{xs} not used again) the base is
dead; where \code{xs} is used afterwards, the rejection is correct, because the elements \emph{are}
shared. Re-building what a pattern matched in the same shape, \code{[ …init, last ]} right after matching
\code{[ …init, last ]}, is an alias of the scrutinee and writes nothing, as for \code{[ h, …t ]}. A view
header also caches a plain copy of its elements and stores its length; a write through a view therefore
never mutates the header it was given, but returns a new header with no cached copy and the right length,
over the same array---so the result is the base's \emph{cell} but need not be \code{===} the operand---and
the old header, being the consumed operand, is dead (A1). A reader that took the cached copy earlier holds
a separate array, a snapshot of the old version, which is what value semantics gives it. Whether today's
lowering of \code{[ …init, last ]} makes a view or copies \code{init} does not change the rule: a copy is a
fresh cell, and the demand on it asks nothing of \code{xs}. The scalar-view rewrite removes most views from
loops anyway (\S\ref{sec:bg-lists}). \emph{Solved.}

\section{Mutable cells}
\label{sec:hard-ref}

\code{Ref.get r} returns an alias of whatever the cell holds, and \code{Ref.set r xs} stores \code{xs};
the analysis cannot see who else has called \code{Ref.get}. A list stored in a \code{Ref} is therefore
escaped, every \code{Ref.get} result is $\top$-held, and \code{Ref.update r (λxs → [ …xs, x ])} is
rejected as a limit, with a message saying that the checker cannot see the cell's other readers. A
linear-cell discipline---the cell is the only holder, and \code{update}'s callback consumes its
argument---would need a proof that no \code{Ref.get} result is live across the update, a
whole-program fact about an unbounded set of readers. The fix is a copy in the callback, or a
persistent structure in the cell. A queue, if one is added to the core library, is the same.
\emph{Open, as a precision limit}; the evaluation measures how often it fires.

\section{Messages as values}
\label{sec:hard-messages}

A message stored in the model, logged whole, or mapped by \code{Html.map} with a function that is not a
constructor is a value; its payload lists are held wherever the message is. A payload passed as
handler parameters---the common case---is covered by \Obl{P6}. \emph{Solved.}

\section{Versions: undo histories, diffs, snapshots}
\label{sec:hard-undo}

In \code{\{ model | history = [ model.todos, …model.history ], todos = [ …model.todos, t ] \}} the
record update evaluates its fields in written order, so \code{history} stores the old array as an element
before the second field extends it---a live holder, part of the record that is built after the
construction. The program is \emph{rejected}, correctly: the undo entry would change with the edit. The
message says so and offers \code{List.copy model.todos} in the history, $O(n)$ per edit, the price of a
version, written where the version is kept. An undo history whose versions are persistent structures,
such as a dictionary of notes, keeps them in $O(\log n)$ and is accepted, and so is the history list
itself when the program pops it with a pattern and pushes onto it with a construction, because each old
version of the \emph{history} is dead after its arm.

\emph{An undo of a list needs a second copy.} With the fix the message offers, and the \code{Undo} arm
that restores a version,
\begin{Verbatim}
Add t → { model | history = [ List.copy model.todos, …model.history ], todos = [ …model.todos, t ] }
Undo → case model.history of
    [ previous, …rest ] → { model | todos = previous, history = rest }
    [] → model
\end{Verbatim}
is still rejected. \code{Undo}'s summary says $\mathit{res}(.\mathit{todos}) \ni \pi_2.\mathit{history}[\ast]$,
\code{Add}'s says $\mathit{res}(.\mathit{history}[\ast]) \ni \fresh_c$, the copy; the entry fixpoint therefore
lets both \code{model.todos} and \code{model.history[*]} hold $\fresh_c$, and \code{Add}'s write of
\code{model.todos} fails \Disjoint\ against \code{model.history[*]}. At run time the two are disjoint after
the pop---\code{rest} no longer reaches the slot \code{previous} came from---but the split of
\S\ref{sec:model-excl}, which knows this inside the arm, does not survive the entry fixpoint, which is not
relational: it records which cells each path may hold, not which paths may hold the same cell at once. The
cost, which the message states, is a second copy, in \code{Undo}: \code{todos = List.copy previous}. A
relational entry---one that remembers that a path filled from the head of a container it then dropped
shares nothing with that container's remaining positions---would remove it; it is left open
(\S\ref{sec:disc-open}), and the evaluation counts its tag (T41). A persistent vector written in beni as a
library module---the current trie, with no in-place writes---would give $O(\log n)$ versions of a sequence
to programs that want them; it would be a library, not the representation of \code{List}. \emph{Solved},
with the cost stated.

\section{Debugging aids}
\label{sec:hard-debug}

\code{Debug.log tag x} reads \code{x} at the call and returns it; \code{Debug.toString} reads at the call.
Neither is a holder afterwards; both are asserted rows (\S\ref{sec:soundness-trusted}). A development
crash screen must print only the exception and the stack (A9); one that printed the model would read a
half-updated record, and the two semantics would differ \emph{after} the program has stopped---a
difference in a debugging aid, not in the program, but one to state. \emph{Solved}, with A9 recorded.

\section{Inlining}
\label{sec:hard-optimiser}

The release optimiser inlines a private function called from one site into that site, and folds a
single-use binding into its use (\S\ref{sec:bg-release}); it does not specialise functions per call
site. Inlining substitutes a body at a call, which preserves evaluation order and holders: the
inlined body's demands are the same demands at the same points, with the parameters bound to the
argument temporaries. The verdict was computed on the source and is not recomputed, so the accepted set
is the source's, never the optimiser's; a program the inliner could have proved safe is still rejected.
The fold is the subject of A5. \emph{Solved by construction.}
