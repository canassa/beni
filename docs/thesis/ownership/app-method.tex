\chapter{Method Behind the Numbers}
\label{app:method}

Every number in this thesis that does not come from a cited publication comes from one of the
measurements below. None is published elsewhere, and none was repeated on a second machine; we give
what a reader needs to judge them, and the artefacts are in beni's source repository
\citep{beni2026}.

\section{The prototype study}

\paragraph{What was measured.} Four ways to write lists in place, prototyped by transforming beni's own
compiled JavaScript \emph{by hand}, exactly as a compiler pass would, each transformation named by the
rule that licenses it:
\begin{itemize}
\item a \emph{static} variant: in place where last use and per-function interface summaries prove a value
unique, and a copy where a caller cannot prove what a callee consumes;
\item \emph{full counts}: a reference count on arrays and on records that hold them, with compiler-inserted
increments and decrements in the style of Perceus and Lean's borrowed parameters;
\item a \emph{sticky shared bit}: the counted variant with every decrement deleted;
\item the bit with no trie at all, every array plain and copied whole when shared.
\end{itemize}
They were compared with the baseline, beni's \emph{adaptive} persistent array (plain copies up to 256
elements, a 32-way trie above), and with plain copy-on-write, on six array scenarios (building by
\code{push} in a fold, a histogram over 1\,000 and 100\,000 buckets, a coin-change table, a grid game on
a board of one million cells with 1 or 100 cells changing per tick, a TEA table of 10\,000 rows, and an
undo history) and on a set of list shapes.

\paragraph{How.} Node~24.19; one pinned \code{node --expose-gc} process per variant; five rounds, two
cores used in parallel; each figure is the median of the round medians. The machine was shared, with a
load average of 4--17 on 32 hardware threads from other work, so the within-round spread is large for the
smallest operations; we claim no ordering that rests on a ratio closer to 1 than 1.25, except where a
smaller ratio is quoted with its context (the 0.84--0.95 of the TEA table). Headless Chrome~153 was a
three-round spot check, which agreed on every ordering that cleared 1.25 and showed less of the counting
variants' overhead. Correctness was checked by a differential test of 484 checks per variant, digesting
every intermediate array and checking inputs unchanged, with tests that an array handed to JavaScript is
never written afterwards and negative controls. Sizes are of the list runtime's JavaScript after brotli
compression.

\paragraph{Limits.} The transformations were made by hand, by the author, on the compiled output of
small programs; they are what a pass would do, not what a pass did. The static variant is not the checker
of this thesis: it had no exclusive-contents flag, no ownership classes for function values, no entry
protocol, and it copied where it could not prove uniqueness; it matched the sticky bit's in-place writes
only with inlined folds and summaries over record fields. No variance beyond the medians is reported
here, and no second machine was used. The scripts and raw results are in the repository's array
benchmark directory.

\section{Interface churn}

The churn figure of \S\ref{sec:bg-modules} comes from an instrument built to measure beni's inferred
\code{where} constraints. It applies a fixed class of body edit to every public declaration of a corpus,
re-checks, and counts declarations whose interface changed. For the edit ``add one equality test on a
parameter'', 50 of 90 unannotated public declarations of the core library changed their interface; on the
same corpus with the compiler as it was before static dispatch was introduced, 8 of 94 did. No annotated declaration changed
under any edit class, on either corpus or compiler. We quote the absolute figure and not a ratio: a ratio
against the annotated declarations is undefined, since they did not change at all.

\section{Counts from the sources}

Several counts in this thesis come from reading beni's sources at the time of writing: the idiom counts
of \S\ref{sec:idioms-question}, the constructions and writers in TodoMVC and Conduit
(\S\ref{sec:disc-apps}), the eight \code{List.push} calls in the core library, the trusted-surface counts
of \S\ref{sec:soundness-trusted}, the program constructors and \code{eq} and \code{compare} declarations of
Chapter~\ref{sec:disc-options}, and the absence of constructions on model lists outside \code{update} arms
(\S\ref{sec:hard-tea}). They were made with a text search over the core library, the platforms, the
compiler's test programs, the benchmarks and the example applications, by these rules:
\begin{itemize}
\item a prepending construction is a list expression with an element before a spread, \code{[ e, …x ]}; an
appending one a spread followed by an element, \code{[ …x, e ]}; an append-by-operator an occurrence of
\code{++ [}; a fold-callback prepend a lambda of the form \code{λx acc → [ e, …acc ]}; an \code{update} arm
that extends a model list a record update whose new field value is a spread or a \code{++} with a model
field as its base; patterns are excluded where the search can tell them apart;
\item a public value is a declaration beginning \code{pub} followed by a value's name and a type; a
\code{foreign} declaration is counted by its keyword at the start of a declaration; a low-level computation
is an occurrence of \code{Js.pure} outside comments;
\item a writer call is an occurrence of the writer's qualified name outside comments, excluding its own
definition.
\end{itemize}
For the applications every hit was read by hand; for the corpus-wide idiom counts it was not, and they are
approximate in both directions---a search by shape misses forms written over several lines and counts some
it should not. None is the output of the analysis, which does not exist yet; the evaluation of
Chapter~\ref{sec:evaluation} replaces them.
