Pure functional languages that compile to JavaScript must choose how to represent their immutable
sequences. A persistent structure makes every update cheap and every version safe to keep, but it
costs runtime code, indirection on every read, and a representation that JavaScript cannot consume
directly. A plain JavaScript array written in place is what a hand-written program uses, but it is
correct only when no one can observe the old version. This thesis designs an \emph{inferred
ownership checker} for beni, a strict, pure, Elm-like language for the browser, under which editing a
list in place while anything else still holds the old version is a \emph{compile-time error}, with no
ownership annotations in user code and no silent fallback: an accepted edit writes its array, and
every copy the program pays for is written in its source.

Edits are of two kinds. The library's named writers, such as \code{List.set} and \code{List.push},
consume their operand. So does list construction: in \code{[ x, …acc ]}, \code{[ …acc, x ]} and
\code{acc ++ ys}, a fixed position rule chooses the operand whose array becomes the result (the
first spread, or the leftmost operand of a chain of \code{++}), and that operand is reused in place, at either end; the
other operands are only read. An accumulator, a fold, a recursive builder and an \code{update} that
adds a row therefore run in place, as hand-written JavaScript would, and the error arises only when
the consumed operand is used again.

That makes the central question one of design: \emph{how should the language and the checker be
designed so that idiomatic code almost never hits the ownership error?} We enumerate the idioms that
must always be accepted---accumulators, folds, lists built by \code{map} and \code{filter}, pipelines,
recursive builders and updates in The Elm Architecture---with examples from beni's core library and
test programs, and for each give the analysis precision that accepts it and the language or library
choice that makes it provable. The property checked is uniqueness \emph{at the update site, decided
by liveness}. The analysis is directional, flow-sensitive and field-sensitive over which arrays each
value may hold, including closure environments; its function summaries say of every result whether
it is fresh, a parameter, a cell the closure holds, a top-level value, escaped or unknown; recursive
groups are solved by an optimistic fixpoint over a finite lattice; an exclusive-contents flag extends
the rule to edits inside a container's elements; and an entry protocol covers every function a UI
runtime calls.

We present the model, the inference algorithm, a sketch of a soundness argument under twelve stated
assumptions, the trusted surface, the hard cases, an error design that separates real sharing from the
checker's limits, the language changes the rule needs, and traces of fifty-eight programs that test the
rules. In-place lists are confined to one of beni's two browser back ends, the direct platform, which
compiles the view away and generates one handler per message from compile-time write sets; we state
precisely what it must re-render when a list keeps its identity across an edit---everything a message's
write set may reach, never what an identity test calls unchanged---and what that costs. beni's current
template renderer keeps persistent lists and every identity-based skip it has, and the rule, checked for
every target, changes nothing a program means there. Two applications re-examined under
construction-as-consumption contain in-place edits in their \code{update}s; traced by hand, one is accepted
as written and the other once \code{init} is a function and after a one-line change to how it persists its
list. Four rounds of adversarial reading kept finding holes where two features interact, so the next step we
propose is a prototype checker run against a differential soundness test over the test corpus, the
applications and randomly generated programs, and then a report-mode experiment whose main metric is the
frequency of the error on idiomatic
code. No results of either exist yet, and the proof is a sketch that has not been mechanised.
