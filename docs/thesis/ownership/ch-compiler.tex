\chapter{Integration with the Compiler}
\label{sec:compiler}

\section{A pass after type checking}
\label{sec:compiler-pass}

The ownership pass runs where the effect inference runs, after every type is solved and before the
interface is published. Futhark moved its alias checking out of its type checker in 2026 for the same
reason: the old design ``had always been hindered by having to work with incomplete type
information'', whereas a separate pass is ``given a fully well-typed program and simply had to figure
out whether any of the in-place constraints were violated (essentially, whether in-place updates are
semantically observable)'' \citep{henriksen2026rewrite}. The pass never touches unification or the
type store, and its messages carry solved types. It needs four things the checker does not keep
today: the solved type of every tracked instruction, to decide paths and crossing; the crossing bit of
every imported type, from its interface; a cell-site
identifier per instruction (the instruction index, as the write-set analysis already uses the
instruction to name the indices it tracks); and the source span of every holder, for messages, which
each instruction's main token gives. The write-set analysis already asks the checker for typed paths,
so the hook for the first exists.

\section{Effects}
\label{sec:compiler-effects}

The two effect bits and the ownership classes ride on the same function-type sites, are solved in the
same per-module phase, and are published in the same kind of interface block. They interact in one
place: a function that \emph{suspends} parks its locals in a continuation, which is one-shot (A7), so a
parked local is the same holder it was and liveness is unchanged. No ownership fact depends on an effect
bit: a command's captures are escaped whether or not its body can suspend (\S\ref{sec:hard-fibers}). An
impure call is a call like any other for holders, and the optimiser's duty to keep impure calls in place
is what A5 extends.

\section{Static dispatch}
\label{sec:compiler-dispatch}

A method call's callee is the term the dispatch table resolves, and its summary is that term's;
evidence a function receives as a parameter is a class instantiated at its caller
(\S\ref{sec:inf-generic}). Every type's \code{eq} and \code{compare}, derived or written, only read
their arguments, by the language rule of \S\ref{sec:inf-generic}. The
inferred \code{where} constraints and the summary block are both inferred facts in the interface, and
both churn the same way; the instrument that measured the first (\S\ref{sec:bg-modules}) can measure
the second.

\section{The write-set analysis}
\label{sec:compiler-writesets}

The direct platform's whole-program write-set analysis (\S\ref{sec:bg-browser}) and the ownership
checker meet at the entry protocol and at the renderer's obligation. There are three reads and one
restatement.

\begin{itemize}
\item \emph{The checker computes the entry state itself}, from summaries, at the call that starts the
program (\Obl{P5} in \S\ref{sec:hard-tea}). The write-set analysis does not analyse commands and has no
fact for two model paths that already alias at an arm's entry, so it cannot supply the entry state;
the escape and alias computation that the direct platform would need for in-place records is this same
computation, done once for both. The write-set analysis supplies the write set per message key, which
\Obl{P3} uses to decide which instance items to re-obtain.
\item \emph{The renderer combines the two.} \Obl{P7} needs, per key $\kappa$, the paths $\mathit{IP}_\kappa$
that $\kappa$ may have written in place: the paths at which \code{update}'s ownership summary has
$\mathsf{W}$ (from the checker), restricted to those that conflict with $\mathit{writes}(\kappa)$ (from
the write-set analysis); and, per value the view computes, whether it may hold such a cell (from the
ownership analysis of \code{view}'s code). All three are known when the handler is compiled.
\item \emph{The write-set consumer reads nothing new}, but its soundness statement changes. Its notion
of ``changed'' was ``not the same value, not \code{===}''. Under in-place writes a write inside
\code{model.rows} leaves the list \code{===} to its old self, so its statement no longer says that the
write set names the path. Its rules still do, because they interpret every writer and every construction
through the core library's table as a write of the path it edits, whatever object the result is; but that
is a property of the rules, not of the statement, and the obligation that rests on it, \Obl{P7}, must not
rest on an accident. The restatement: \emph{``changed'' means ``may differ in content from what was there
before the dispatch''}, with the same proof obligations rule by rule, and a check, when the ownership pass
and the write-set pass both run, that every path an accepted demand of an arm writes in place conflicts
with that arm's write set (A12). What a consumer may no longer do is conclude ``unchanged'' from
\code{===} on a value that may hold a cell written in place, which is \Obl{P7}. The write-set analysis's
own requirement that an in-place list write never touch a list the program still holds becomes the theorem
of Chapter~\ref{sec:soundness}, rather than a requirement on the emitter.
\item \emph{The write-set interpreter is the right engine for the model's paths, not for the general
checker.} It is whole-program, per message, and tracks identity; the ownership checker is per
function, directional over cells, and publishes summaries. They meet at the entry protocol and the
renderer, and nowhere else.
\end{itemize}

\section{The backend}
\label{sec:compiler-backend}

On the direct platform every accepted demand is in place, so the backend needs no per-site decision: it
emits each writer's call as it does today, lowers each construction to the writers on its base, left to
right from the base as Change~1 specifies, and the core library's writers \emph{are} the in-place
operations (Table~\ref{tab:backend}). Every other target keeps today's persistent writers and lowering
(rule~7 of \S\ref{sec:bg-language}); the two implementations of the writers have the same rows, so a
program's verdict does not depend on which one it is linked with.

\emph{On the direct platform the trie goes.} Its claims, its radix offsets, its head and tail buffers, the cache of its plain
form and its thresholds all exist to make writes to \emph{shared} lists cheap, and under the rule no
shared list is ever written. What stays is the plain form; the view form for a pattern's \code{rest}
(with the scalar-view loop rewrite still removing most views); the array builder used by functions
that build their result in tail position; and the three-fact protocol for readers (\code{length},
\code{Array.isArray}, \code{\$plain()}, the last now needed only for views). Our prototype study measured
the list runtime at 706 bytes compressed without the trie, against 1\,514 with it
(Appendix~\ref{app:method}); a page built for the direct platform ships the smaller one. The template
runtime and Node keep the trie, so the core library carries both implementations of the writers, and the
differential run of \S\ref{sec:eval-sanitiser} compares them. The library's loops written in beni are
unchanged.

Moving a consumed base into a larger array is growth, not a copy in the sense of the rule: no old
version survives it, because the base had no other live holder, and its cost is amortised over the
additions that filled the space, exactly as for \code{push} on a JavaScript array. Prepending needs free
space in front, so a list built by prepending is a view whose offset leaves room before its first
element. How much room to keep, whether a plain array gains room in front on its first prepend or carries
some from birth, and how often a view must be flattened when it is handed to JavaScript are open
(\S\ref{sec:disc-options}); the amortised bound holds for any policy that grows the room in proportion
to the length.

The backend must still keep the identity promises the language keeps (\S\ref{sec:model-demands}) and the
linearity of the builder. A construction returns its base's \emph{cell}---its header may be new, after a
prepend or a write through a view, so the result need not be \code{===} the operand---while
\code{[ …xs ]} and the re-building of a matched list return the list itself, and \code{xs ++ []} returns
\code{xs}.

\section{The release optimiser}
\label{sec:compiler-release}

The verdict is a function of the source, and \code{--release} emits the same in-place calls as a
development build, so beni's promise that a release build behaves exactly as a development build holds
with no new exception---\emph{provided the optimiser treats a demand as a barrier} (A5). Today the
single-use fold places a read of a beni value after calls that precede its use in the same statement,
and a list's length and element reads are such reads after lowering (\S\ref{sec:bg-release}); a read
of a cell and a demand on it do not commute, so the demand summaries become an input to the optimiser as
the impure bit is, and a read of a cell is never moved across a demand that may write it---a construction
included, since \code{n = List.length xs} followed by a use of \code{n} after \code{[ …xs, 1 ]} must read
the length before the push. With that,
the rest of the optimiser's contract carries over: an unused binding whose right-hand side is a pure
call may be dropped (an unused \code{List.set} is then not performed, which no reader can tell); two
surviving calls are never reordered; inlining substitutes bodies and never duplicates an argument's
evaluation; inlining a once closure's body into its one call is allowed (\S\ref{sec:hard-optimiser}).
Renaming and minification touch names, not writes. Reachability is untouched: \code{copy} ships only
when reached.

\section{Records in place}
\label{sec:compiler-records}

Records are outside this thesis's scope, but the machinery applies: a record path is a ``cell'' whose
demand is the in-place record update the lowering would emit, and its holders are the same places.
The language's promise that a record update keeps the other fields as the very same values
(\S\ref{sec:bg-beni}) becomes the only difference: a record written in place keeps its own identity
too, which the direct platform's rule already forbids the renderer to rely on. The hazard is that the
renderer compares records by identity everywhere---a reference check per dynamic hole is what makes
beni's compiled templates fast---so in-place records need a stronger form of A4 than lists do: the
argument for \Obl{P7} rests on records being rebuilt whenever their content changes, and a record written in
place would put every holder of it, not only list-valued ones, among the values that may hold a written
cell. The hand-over obligations of \S\ref{sec:hard-tea} are the obligations in-place records would need too.

\section{Incremental builds}
\label{sec:compiler-incremental}

The summary block is in the interface and its hash, and beni's interface firewall fires when it
changes (\S\ref{sec:bg-modules}). Two consequences need measurement. The first is churn: a body edit
that turns a borrowed parameter consumed re-checks every importer, necessarily, since their side
conditions change. The second is the warm rebuild budget---15\,ms for a body edit and 60\,ms for a
signature edit---since a body edit that changes a summary \emph{is} a signature edit under this design,
and signature edits do not yet meet their budget for other reasons. Every fact the analysis reads
across a module boundary is in an interface, including what a TEA program's entry protocol needs
(\S\ref{sec:inf-modular}), so the cache key needs no change.
