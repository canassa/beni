# What happened to Elm's compiler tests

Source-verified against the vendored `references/elm` clone and its git history. This is the
evidence behind the "why this shape" section of
[`.claude/skills/write-tests`](../../../.claude/skills/write-tests/SKILL.md).

---

## The headline: there are none

Current `elm/compiler` (HEAD `1bd5b369`, 2026-07-13) has **no tests**. No `test-suite` stanza in
`elm.cabal`, no test directory, no test dependencies. Not a thin suite — zero.

They were deleted on **2018-02-21** in commit `e2008b50`:

> "Get rid of testing stuff. Needs to be redone anyway for 0.19"

**1,252 commits and roughly eight and a half years later, it has not been redone.**

## What was deleted (recoverable at `e2008b50^`)

```
tests/Test.hs
tests/Test/Compiler.hs
tests/Test/Property.hs
tests/Test/Property/Arbitrary.hs
tests/test-files/{good,bad,good-expected-js}/**
```

Three layers, on `test-framework` + HUnit + QuickCheck, run by `cabal test` on Travis.

### 1. Corpus tests — the directory is the assertion

`Test/Compiler.hs` walked `tests/test-files/` at runtime (`buildTest` + `find (extension ==? ".elm")`)
and generated one HUnit case per file, named by its path. Everything under `good/` had to compile;
everything under `bad/` had to fail.

Fixtures were one idea each and tiny. `bad/InfiniteType.elm` in its entirety:

```elm
f = f 42
```

`good/Soundness/TrickyId.elm` is `myId x = let y = x in y`. Intent lived in comments inside the
fixture — `IncompletePatternMatch.elm` ends with `-- incomplete pattern match is an error` /
`-- missing: (_, Nil) -> Nil`. And `bad/BBTArgs`, no extension, contains the single word `Fail` — a
test that garbage doesn't compile.

Directories were **feature areas, not compiler phases**: `Cases/`, `CodeGenBugs/`, `Crash/`,
`Declarations/`, `Lists/`, `Literals/`, `Records/`, `Soundness/`. `CodeGenBugs/` is pure regression
material named after the bug — `Shadowing`, `Shadowing2`, `TailRecursion_ListAny`,
`CommentInterpretedAsInfix`.

**The assertions were binary**: `isSuccess` / `isFailure`. A `bad/` test passed if compilation failed
*for any reason at all* — not the right error, not the right message. Elm's famous diagnostics were
never tested.

### 2. Golden JS snapshots

`good/X.elm` was compiled and string-compared against `good-expected-js/X.elm.js`, with the path
derived mechanically (`drop 3 . splitDirectories`, `<.> ".js"`). Snapshots were small — TrickyId's is
four lines.

There was a blessing workflow, advertised in the failure message:

> "Compiled JS did not match expected JS. If the change is intentional, rerun the tests with
> environment variable: ELM_WRITE_NEW_EXPECTED=1"

One careful detail worth copying: before writing a new snapshot it forced evaluation of the JS
(`assertBool "" (LText.length js >= 0)`) so an exception couldn't silently truncate the file to empty.

### 3. QuickCheck round-trip properties

`prop_parse_print`: pretty-print an AST value, re-parse it, assert equality — over literals, patterns
and types, with hand-written `Arbitrary`/`shrink` instances. Including one frozen counterexample kept
verbatim:

```haskell
-- This test was autogenerated from the Pattern test and should be
-- left in all its ugly glory.
longPat = P.Data (V.Raw "I") [ P.Literal (Lit.Chr '+'), P.Record [ "q7yclkcm7k_ikstrczv_", ... ] ]
```

## The decay is visible in git, and that is the real lesson

At the moment of deletion the suite was **already dead**:

- The `Test-Suite` stanza in `compiler/elm-compiler.cabal` was entirely commented out — lines
  172–200, every line prefixed `--`.
- `Test.hs` had `import Test.Property` commented out, so property tests were already disabled.

The sequence was: property tests disabled → whole suite disabled in the build → deleted as dead
weight.

## What replaced it: a release pipeline, not a test pipeline

Pre-2018 Travis ran `cabal test`; it was deleted along with the tests. Travis **returned** on
2019-12-10 (`1a45b8e0`, "add Travis CI Linux x86_64 build and tags releases") — but as a release
pipeline only:

```yaml
before_install:
  - docker build -t elm -f installers/linux/Dockerfile .
  - docker cp $(docker create elm):/usr/local/bin/elm .
  - gzip -9 -c elm > $LINUX_ARCHIVE
deploy:
  provider: releases
  on: { branch: main, tags: true }
```

There is no `script:` section at all. It builds an image, extracts the binary, gzips it and uploads
to GitHub Releases **on tags only**. It verifies nothing. Failure notifications go to one
contributor's personal email.

Current GitHub Actions are two bot workflows — `set-pull-expectations.yml` and
`set-issue-expectations.yml` — that post canned comments about batched review. No build, no test, no
lint.

The word "test" appears **0 times** in `README.md` and **0 times** in `.github/CONTRIBUTING.md`.
`roadmap.md` mentions only `elm test` — the user-facing runner for testing *Elm programs*, a separate
repo — as a parked "conservative project."

**Effective state: the only automated check on the Elm compiler is "did a Docker build produce a
binary," and only when a release is tagged.** Whatever validation happens beyond that is manual and
not visible in the repo. (A plausible guess is "compile the package ecosystem and see", but that is
inference, not something sourced.)

## What this argues for

Copy:

- **Corpus tests generated from a directory walk.** Adding a case is dropping in a file — exactly the
  right economics for a compiler.
- **One-idea fixtures**, with intent in a comment inside the fixture.
- **Regression files named after the bug.**
- **Golden output with a bless-via-env-var flow**, and the force-before-write detail.

Avoid:

- **Binary pass/fail on error cases.** For a language whose pitch is its diagnostics, this leaves the
  flagship feature untested. Our `bad/` fixtures require a `.diag` file with the whole expected
  diagnostic.
- **Whole-file golden JS.** Every codegen change churns every snapshot, which is part of why this
  suite became a burden. Prefer running the emitted program; keep goldens narrow and normalised.
- **A suite that can be quietly disabled.** The cabal stanza was commented out before anyone deleted
  anything. CI must run both suites on every commit and fail loudly — never a tag-only pipeline.
