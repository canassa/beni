Research compiled 2026-10-04. Scope: techniques for avoiding copies or allocation

## 1. Reuse when unique

**Koka's Perceus + FBIP.** Perceus is a static reference-counting algorithm: the compiler inserts precise inc/dec instructions, performs reuse analysis so a pattern match that consumes a unique constructor cell can reuse that memory for the freshly built result, and drop-specializes to cancel redundant inc/dec pairs. "Functional But In-Place" (FBIP) is the resulting style — ordinary pattern-matching code gets in-place mutation for free when a value is locally unique. Koka's own benchmarks claim allocation-heavy workloads (rbtree, deriv, nqueens, cfold) on Koka 2.0.3 outperform OCaml, GHC, Swift, Java/G1 and C++ "by a significant margin." Reuse fires only when the compiler proves refcount==1 at that point; once a value escapes into a second binding or closure it silently falls back to alloc+copy, with no diagnostic. Sources: microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/; github.com/koka-lang/koka; wiki page "Functional-but-In-Place-(FBIP)".

**Lean 4's `reset`/`reuse`.** Also precise RC, plus a borrow-inference pass (parameters passed "borrowed" rather than consumed) and `reset`/`reuse` IR instructions that destructively recycle an inductive value's cell during a match-then-rebuild. Multithreading interacts badly with naive RC (atomic inc/dec cost), which is the paper's motivating problem for borrowing. Source: Ullrich & de Moura, "Counting Immutable Beans," arxiv.org/abs/1908.05647.

**Roc's refcounted-when-unique List/Dict.** Roc's `List` is laid out like a Rust `Vec`, with one extra refcount word on the heap allocation; `List.update`-style operations check that word — refcount 1 mutates in place, otherwise deep-copies — and a static ownership analysis ("Morphic") often proves uniqueness so the runtime check can be skipped. Richard Feldman, Roc's creator, described this directly on Zulip: "Roc's List basically looks like a Rust Vec... except with a reference count added... if the reference count is 1, we update it in place... thanks to Morphic, sometimes we don't even need to check the reference count" (roc.zulipchat.com/#narrow/channel/231634-beginners/topic/Mastodon.20post/near/402350503). Roc's FAQ deliberately keeps this invisible rather than exposing uniqueness/linear types to users. A documented hazard: FFI/host code can hold a reference to a list without Roc's RC seeing the increment, so in-place mutation can race an aliasing reference RC doesn't know about (roc.zulipchat.com/#narrow/stream/231634-beginners/topic/Grokking.20platforms).

**Clean's uniqueness types.** A type-system attribute (`*`/`U:`) statically guarantees a value has exactly one live reference everywhere in the program; the compiler compiles updates to unique-typed values as destructive in-place writes, and uniqueness also substitutes for monadic I/O (a unique "World" token threads state). Wikipedia states Clean's performance is comparable to GHC's (en.wikipedia.org/wiki/Clean_(programming_language)). Composability is the known cost: a function generic over unique and shared arguments needs uniqueness polymorphism, and a unique token forces single-threaded sequential use.

**Futhark's uniqueness types for arrays.** Consuming parameters are marked `*` ("the function owns this array; the caller never references it again"); `a with [i] = v` is legal only when the compiler proves `a` (and anything aliasing it) is dead afterward on every path. Source: "Futhark: Purely Functional GPU-Programming with Nested Parallelism and In-Place Array Updates," PLDI 2017 (futhark-lang.org/publications.html); language reference at futhark.readthedocs.io/en/latest/language-reference.html. A consuming function is second-class — it cannot be passed as a first-class higher-order argument — a hard restriction the docs state directly.

**SISAL build/update-in-place.** The compiler lowered to the IF1/IF2 dataflow graph IR and detected when an array-build node fed solely into an array-modify loop with no other live reference, allocating once and mutating in the loop. Bibliographic: Feo, Cann, Oldehoeft, J. Parallel & Distributed Computing 10(4), 1990; Cann, "Retire Fortran? A Debate Rekindled," CACM 1992 (dl.acm.org/doi/10.1145/129888.129897). This depends on the whole program being one compiler-controlled dataflow graph.

**Mercury's compile-time GC / structure reuse.** Rides on Mercury's existing mode/determinism system (which already declares per-argument whether a binding is unique/dead/shared) to prove when a deconstructed term's cells can be reused for a newly constructed term. Sources: Mazur PhD thesis (mercurylang.org/documentation/papers/CW2004_03_mazur.pdf); ICLP'01 and ICCL'00 papers (same papers.html index). The ICCL'00 title ("module based") signals cross-module reuse opportunities are missed or need extra interface annotation.

**Linear Haskell.** Adds a linearity annotation on function arrows (`a %1 -> b`) rather than a separate type universe, so a linear argument must be consumed exactly once — enabling pure-interface mutable-array APIs. Paper: Bernardy et al., arxiv.org/abs/1710.09756 (POPL 2018). Any API wanting the optimization must be rewritten against the linear arrow; this is new surface area existing code must opt into.

**Swift COW + `isKnownUniquelyReferenced`.** Array/Dictionary wrap a class-boxed buffer; mutating methods call a uniqueness check (the current stdlib uses `beginCOWMutation`/`endCOWMutation`, confirmed directly in Apple's stdlib source at github.com/apple/swift/stdlib/public/core/ArrayBuffer.swift) before mutating in place, else copy first. This is parasitic on ARC retain counts Swift already maintains on every class instance. `isKnownUniquelyReferenced` can give a false negative under concurrency, which is why Swift steers hand-written code toward the higher-level COW types rather than the bare check.

**Rust ownership/borrowing** is the static extreme: every value has one owner, moves transfer it, and the borrow checker statically rejects any aliasing that could conflict with a mutation — zero runtime check, zero runtime cost, paid for in restrictiveness. doc.rust-lang.org/book/ch04-00-understanding-ownership.html.

**Cross-cutting fact for this group.** Every *runtime*-refcount scheme (Perceus, Lean 4, Roc, Swift COW) needs a mutable counter word colocated with the value and a hook that fires on every store/drop; JavaScript values expose neither, so none of these four ports as-is without an out-of-band shadow refcount table, which reintroduces the bookkeeping cost the technique exists to avoid and which (per Roc's own documented FFI hazard) breaks at any boundary where JS code can hold a reference the shadow table can't see. Every *static-proof* scheme (Clean, Futhark, Mercury's modes, Linear Haskell, Rust) needs no runtime hook, but each assumes a closed, whole-program view so "no other reference survives" is provable — an assumption a TEA/Solid-style UI violates on purpose, since rendering keeps the previous model alive by reference specifically to diff against. None of the ten systems surveyed has a built-in notion of "this reference is allowed to keep existing for the view layer, but still counts as dead for update purposes."

## 2. Never allocating at all (escape analysis, scalar replacement)

**LLVM SROA.** Breaks an `alloca` of aggregate type into per-member scalar `alloca`s and promotes them to SSA values when possible; works intraprocedurally and is disabled for any slice an escaped pointer touches (llvm.org/docs/Passes.html; llvm.org/doxygen/SROA_8cpp_source.html). It is an AOT compiler pass, not a runtime mechanism — structurally the same kind of pass a compiler emitting JS could run on its own pre-codegen IR, independent of what the JS engine does afterward.

**V8 TurboFan escape analysis.** Tracks "virtual objects" for allocations (e.g. object literals) that provably don't escape the function being optimized, rewriting field reads to the stored value and omitting the real allocation. Source is the primary evidence (no reachable prose write-up this session): github.com/v8/v8 `src/compiler/escape-analysis.cc`. It runs only in the optimizing tier (after Ignition/warm-up), has a hard-coded analysis budget (comment: "Bailing out in Escape Analysis because of kTrackingBudget", 1300 bytes), and treats any unrecognized operation, any `TrustedHeapConstant`, and a specific unsupported double/indexed-element pattern (crbug 1237821) as escaping by default. Anything stored into an already-escaping structure, captured in a closure, returned, or passed to a call TurboFan can't see through also escapes.

**HotSpot C2 escape analysis + scalar replacement.** Builds a flow-insensitive connection graph after inlining, classifies allocations GlobalEscape/ArgEscape/NoEscape, and scalar-replaces NoEscape objects — eliminating the object, not relocating it to a stack (wiki.openjdk.org/display/HotSpot/EscapeAnalysis). Shipilev's measured microbenchmark: with scalar replacement firing, allocation rate drops to ≈10⁻⁴ MB/s at ≈1.9 ns/op; merging two branches that each allocate an otherwise-identical object defeats it at the merge point, allocation reappearing at ≈2,691 MB/s (shipilev.net/jvm/anatomy-quarks/18-scalar-replacement/). Nothing in source signals the failure — only GC telemetry shows it, a "silent cliff."

**Graal/Truffle partial escape analysis.** Extends whole-method escape analysis (which must prove non-escape on every path) to a per-path form: an allocation scalar-replaces on paths that don't escape and materializes only on paths that do. Stadler, Würthinger, Mössenböck, CGO 2014 (doi.org/10.1145/2581122.2544157; full text blocked this session, so no benchmark numbers quoted). This generalizes the branch-merge failure mode HotSpot hits.

**LuaJIT allocation sinking.** Within a recorded trace, an SSA-level allocation with every use proven local is "sunk" and only rematerialized at a trace exit that needs the real object (wiki.luajit.org/Allocation-Sinking-Optimization, not independently re-verified live this session). Relies on LuaJIT's linear-trace architecture; a trace abort (NYI bytecode, `pcall`, a metatable hook, a closure crossing the trace boundary) always allocates.

**GHC worker/wrapper + CPR.** Splits `f = wrap ∘ worker` so the worker passes unboxed scalars directly; paired with strictness/demand analysis and constructed-product-result (CPR) analysis. Gill & Hutton, J. Functional Programming 19(2), 2009 (bibliographic; PDF unreachable this session). Depends on the wrapper actually inlining at the call site — otherwise the split adds a box instead of removing one — and whether it fired is only checkable via `-ddump-strsigs`/`-ddump-simpl`.

**MLton flattening.** MLton is "a whole-program optimizing compiler for Standard ML" (github.com/MLton/mlton README, confirmed live) that defunctorizes/monomorphises the entire program, then unboxes tuple/constructor arguments used only locally into flattened scalar locals. Whole-program visibility is load-bearing; this is well known to make compile times large and non-incremental.

**Applicability fact (also feeds the V8 section below):** V8's escape analysis already elides allocation for object literals it proves don't escape a hot, optimized function — but only past warm-up, only within its analysis budget, and only for access patterns its walker recognizes. For records that escape (returned from an exported function, stored into a longer-lived model, passed through a not-yet-monomorphic call site — the common case for compiler-emitted module code), V8 cannot and does not elide the allocation, so a source-level avoidance pass still has work to do there; this needs verification against real emitted beni JS rather than being assumed.

## 3. Removing intermediate structures (fusion)

**Deforestation (Wadler, 1990).** A source-to-source rewrite removing intermediate trees/lists from compositions of recursive functions, restricted to "treeless form" inputs; a proof-of-termination paper, not a benchmarked one (en.wikipedia.org/wiki/Deforestation_(computer_science); original TCS 1990 PDF unreachable this session). Excludes idiomatic higher-order/accumulator code without extension, and doesn't scale across module boundaries.

**foldr/build short-cut fusion (GHC).** One local rule, `foldr k z (build g) = g k z`; library producers (`map`, `filter`, `[1..n]`, …) are rewritten through `build`, consumers through `foldr`. Still present verbatim in GHC's base library (`{-# RULES "foldr/build" ... #-}`). Sound only because `build`'s definition exploits parametricity. GHC's own user's guide documents multiple silent-failure modes: ordinary inlining can pre-empt the rule before it matches; GHC refuses to fire a rule that would duplicate non-trivial computation without a `CONLIKE` pragma; rules on type-class methods rarely fire because the method is already specialised; polymorphic pattern variables often fail to match instantiated call sites (downloads.haskell.org/ghc/latest/docs/users_guide/exts/rewrite_rules.html). Structurally can't fuse `zip` well — the gap Stream Fusion addresses.

**Stream Fusion.** Represents a pipeline as an explicit `Stream a = exists s. Stream (s -> Step a s) s` with `Step = Done | Yield a s | Skip s`; ordinary GHC inlining (not a bespoke rewrite rule) erases the existential state once everything specializes. Coutts, Leshchinskiy, Stewart, ICFP 2007, "From Lists to Streams to Nothing at All" (cgi.cse.unsw.edu.au/~rl/papers/icfp07.pdf — PDF text unreadable this session, title states the claim). Became the fusion mechanism for `vector`/`bytestring`/`text`. Still inlining-dependent: if the existential doesn't fully specialize, you pay dictionary overhead instead of getting a fused loop.

**Clojure transducers.** Decouple "what transformation" from "what source/sink" by making a transducer a function from one reducing function to another; `map`/`filter`/etc. become composable transducers drivable directly over a vector, channel, or lazy seq with no intermediate collection between stages (clojure.org/reference/transducers). A library protocol, not a compiler pass — fusion happens because `comp` composes ordinary functions, relying on the host JIT to specialize the composed closure well. Stateful transducers (`partition-by`) reintroduce mutable-state hazards.

**Elm: no fusion found.** `elm/core`'s `List.map`/`List.filter` are plain recursive functions with no `build`-style rule (github.com/elm/core/blob/master/src/List.elm, read directly); `elm-optimize-level-2`'s documented transformation list has no map/filter/fold fusion of any kind (github.com/mdgriffith/elm-optimize-level-2/blob/master/notes/transformations.md). Elm, beni's closest sibling and targeting the same JS runtime, ships zero fusion.

**PureScript backend-optimizer (`purs-backend-es`).** Operates on CoreFn (PureScript's typed core IR, not surface syntax or emitted JS) with an inlining pipeline and named "Fusion (Fold)"/"Fusion (Unfold)" passes; a fetched test snapshot confirms a five-stage map/filter/append chain compiles to one backward loop into one result array. README-stated aggregate benefits: 25–35% runtime, 20–25% minified size, 15–20% minified+gzip improvement versus stock PureScript codegen (github.com/aristanetworks/purescript-backend-optimizer). States explicitly that optimization and codegen are "currently not incremental" — whole-program fusion traded against incremental rebuilds.

**Futhark/SAC combinator fusion.** Both fuse adjacent array combinators (`map`/`map`, `map`/`reduce`) on a dedicated combinator-level IR (SOACs in Futhark, "with-loop folding" in SAC) before any C/CUDA emission; enabled because every combinator is provably side-effect-free (futhark-lang.org/publications.html; Henriksen & Oancea, FHPC 2013, hiperfit.dk/fhpc13.html). Requires whole-program visibility with no opaque function boundary — the modularity problem short-cut fusion exists to dodge via a local rule instead.

**Cross-cutting fact for this group.** Every technique surveyed does the fusion on an IR before target-code generation — GHC's Core simplifier before STG, PureScript's CoreFn before JS emission, Futhark/SAC's combinator IR before C/CUDA. None rely on the downstream target doing it. V8 performs no cross-call fusion of chained `.map`/`.filter`: two chained array methods remain two heap-allocating passes at runtime regardless of JIT tier, confirmed by the complete absence of this behavior in Elm's own compiler and ecosystem tooling targeting the identical runtime.

## 4. Batching/transient mutation behind an immutable interface

**Clojure transients.** A transient shares structure with its persistent source and permits localized destructive mutation; callers must thread the return value forward, and "it is an error if more than one thread manipulates a transient at once" (clojure.org/reference/transients). Each tree node checks a per-node "edit" `AtomicReference` flag before allowing mutation (github.com/clojure/clojure `ATransientMap.java`). Using a transient after `persistent!` throws — but this is true "also for any aliases you might have created," i.e. stale captured references become invalid, and cross-thread misuse detection has weakened across releases rather than being fully runtime-enforced.

**Immer.js.** `produce(state, recipe)` hands the recipe a Proxy-wrapped draft; mutations are recorded against the proxy and the next state is derived from them. "Unchanged parts of a data tree... are shared in memory with older versions of the same state" — only touched paths are copied (immerjs.github.io/immer). Depends on native `Proxy`; the documented ES5 fallback uses `Object.defineProperty` getters/setters and cannot intercept array index/length mutation as precisely.

**Immutable.js `withMutations`.** Creates a temporary mutable copy and batches a set of calls into one result object instead of one per call — the README states chaining three `.set` calls this way "results in the creation of 1, not 3, new immutable Lists" (github.com/immutable-js/immutable-js). Only a narrow method set is safe inside it; the mutable value must not escape the callback.

**Erlang/BEAM `setelement/3` coalescing.** The compiler can fuse a chain of `setelement/3` calls on a freshly built tuple into one destructive rewrite, gated on compile-time-known tuple size, literal integer indices, and no intervening expressions (erlang.org/doc, "Common Caveats"). The binary analogue — "private append"/writable binaries — lets `<<Bin/binary, X>>` avoid copying by over-allocating a reference-counted binary to 2× size (or 256 bytes), but "requires a single ProcBin and a single reference to it," and is invalidated (binary shrunk, next append copies) once the binary is sent elsewhere, stored in ETS, or pattern-matched.

**OCaml / js_of_ocaml / ReScript.** OCaml itself contrasts per-field `mutable` (destructive `<-` assignment) against the default functional-update `{ r with f = v }`, which always allocates a fresh block for unmarked fields (ocaml.org/manual). js_of_ocaml's own Optimizations wiki page documents JS-shape-stability guidance and a switch-splitting heuristic, but no record/block-specific copy-avoidance pass (github.com/ocsigen/js_of_ocaml/wiki/Optimizations). ReScript's manual states records "compile to straightforward JavaScript objects," with `{...r, f: v}` spread as the only update path and no documented structural-sharing optimization beyond native JS spread semantics (v11.rescript-lang.org/docs/manual).

## 5. Compile-to-JS specifics

**Closure Compiler** does dead-code elimination, string-literal inlining (chosen because it shrinks compressed size more than manual aliasing), and type-based property renaming under ADVANCED mode, with most of its win coming from unused-code removal, not value-flow/escape analysis (github.com/google/closure-compiler/wiki, FAQ page).

**js_of_ocaml** documents shape-stability guidance and switch-splitting; no block/record mutation-avoidance pass.

**Scala.js**'s optimizer does whole-program inlining and dead-code elimination at the linker/IR level; its docs explicitly caveat that running Closure Compiler on top in `fullOpt` mode is "mostly equivalent to just our own optimizer," with Closure's extra benefit being code size, not speed (scala-js.org/doc/internals/performance.html).

**Dart2js** documents tree-shaking and tiered `-O0`–`-O4` optimization levels, recommending consistent static types to aid its type-inference-driven optimizer; no specific claim found about `const`/immutable-collection representation (dart.dev/tools/dart2js).

**PureScript backend-optimizer** (detailed in §3) also includes an "aggressive inlining pipeline," tail-call optimization across mutually recursive groups, and redundant pattern-match-test elimination, plus switching the runtime data encoding to lighter-weight plain objects (github.com/aristanetworks/purescript-backend-optimizer).

**elm-optimize-level-2** documents, among shipped transformations, unwrapping Elm's curried-call wrapper objects and inlining `_Utils_eq` to `===`. Notably, it *attempted and rejected* an "Object Update Optimization" replacing `_Utils_update`'s field-by-field copy with spread/`Object.assign()`: this produced a "501% boost in Chrome" but a "50% reduction [regression] in Safari," so the shipped tool keeps manual field-by-field assignment (notes/transformations.md). This is a directly measured cross-engine performance-cliff example for exactly the record-update operation beni's fold example performs.

**Gleam's JS target.** Replaced a linear if-else pattern-match chain with a decision-tree compilation pass specifically for the JS backend; the blog post notes the BEAM backend "already performs this optimization automatically" at the VM level, so Gleam only needed to add it for JS — a direct example of a JS target needing to re-implement, at compile time, something a different backend's runtime already provides. Reported a 15% larger pre-compression bundle, fully absorbed by minification/brotli (gleam.run/news/gleam-javascript-gets-30-percent-faster).

**Roc, Koka, Lean 4 JS backends.** Roc has no JS backend (targets native/Wasm via LLVM; roc-lang.org/platforms). Koka has a documented JS backend update (ES6 modules, BigInt) but no retrieved source describes how Perceus's RC/reuse optimization behaves when targeting JS rather than native C — plausibly degraded to ordinary GC allocation there, unconfirmed this session (koka-lang.github.io/koka/doc/book.html). Lean 4's production backend targets C, not JS; no evidence of an official Lean 4 JS backend was found.

## What V8 already does at run time

V8's TurboFan tier runs an escape-analysis + scalar-replacement pass (`src/compiler/escape-analysis.cc`, github.com/v8/v8) that tracks "virtual objects" for allocations such as object literals and omits the real allocation when every use is proven local to the optimized function. This is gated by: (1) reaching the optimizing tier at all (post warm-up, past Ignition/baseline execution collecting type feedback); (2) a hard-coded tracking budget (kTrackingBudget, 1300 bytes) beyond which the compiler bails out regardless of true escape status; (3) a fixed set of recognized operations — anything the escape walker doesn't specifically handle is treated as escaping by default, and a documented unsupported double/indexed-element pattern (crbug.com/1237821) always bails out. For a record literal that is both constructed and consumed entirely within one hot function, this pass can make a beni-emitted allocation disappear at runtime without any compiler-level pass being required — but only under those conditions, and this needs verification against real emitted beni JS rather than being assumed from the source comments alone. It gives no benefit to: cold code, code that hasn't warmed up yet, records that escape the function (returned, stored into a longer-lived structure, passed through a call V8 can't see through — the common shape for compiler-emitted module-boundary code), or anything exceeding the tracking budget. HotSpot's C2 analogue (wiki.openjdk.org/display/HotSpot/EscapeAnalysis) and Shipilev's measured numbers (shipilev.net/jvm/anatomy-quarks/18-scalar-replacement/, allocation rate ≈10⁻⁴ MB/s when it fires vs. ≈2,691 MB/s at a branch-merge point that defeats it) illustrate the same tier-gated, silently-cliffing behavior in a comparable JIT, as a factual analogue — not a claim about V8's own numbers, which were not independently measured this session.

## Recurring problems reported

- **Performance cliffs with no source-level signal.** HotSpot scalar replacement is defeated by merging branches that each allocate an "equivalent" object, with no diagnostic other than GC telemetry (shipilev.net). GHC's worker/wrapper and demand analysis can simply fail to fire across higher-order calls or FFI boundaries, checkable only via debug dump flags (`-ddump-strsigs`). V8's escape analysis bails out past a byte budget or on an unrecognized op, invisibly.
- **Fusion rules competing with ordinary inlining, or simply not firing.** GHC's own users' guide: "Ordinary inlining happens at the same time as rule rewriting, which may lead to unexpected results" — rules on type-class methods rarely fire because the method is already specialized; polymorphic pattern variables often fail to match instantiated call sites (downloads.haskell.org/ghc/latest/docs/users_guide/exts/rewrite_rules.html). This is the literature's own name for the phenomenon: "fusion is fragile."
- **Static proofs that don't survive a boundary.** Roc's community flagged that FFI/host code can hold a reference to a list without Roc's RC seeing the increment, letting in-place mutation race an aliasing reference RC doesn't track (roc.zulipchat.com, "Grokking platforms" thread). Linear Haskell, Clean and Futhark's proofs are all scoped to code the respective type checker sees; none extend across a call into unchecked host code.
- **Concurrency defeats a momentary uniqueness reading.** Swift's `isKnownUniquelyReferenced` can give a false negative under concurrent access, which is why Swift's own stdlib uses the more disciplined `beginCOWMutation`/`endCOWMutation` protocol internally rather than a bare check (github.com/apple/swift, ArrayBuffer.swift).
- **Cross-engine divergence on the exact operation beni's own motivating example performs.** elm-optimize-level-2's rejected spread/`Object.assign()` record-update optimization measured a 501% speedup in Chrome against a 50% regression in Safari for the same change (github.com/mdgriffith/elm-optimize-level-2/notes/transformations.md) — a directly measured, engine-dependent cliff on record-update codegen specifically.
- **Whole-program techniques trade away incrementality.** MLton's whole-program defunctorization/monomorphisation is well known to make compile times large and non-incremental (github.com/MLton/mlton). PureScript's backend-optimizer states directly that its optimization and codegen are "currently not incremental" (github.com/aristanetworks/purescript-backend-optimizer).
- **Usability cost of exposing the proof in the type system.** Clean and Futhark's uniqueness types both make the affected functions second-class or harder to compose generically — documented directly in Futhark's language reference as a restriction, not a style choice.
