## Compile-time reactivity / fine-grained compilers

**Svelte 3/4.** The compiler statically analyzes each component's `<script>` block: every top-level `let` that is reassigned and read by markup/`$:` gets an injected `$$invalidate('name', name)` call at its assignment site. Rich Harris's own framing: "Updating some `count` value... should be as simple as this: `count += 1;`" and the compiler "convert[s] your components into highly efficient imperative code that surgically updates the DOM" without vdom diffing or proxies (svelte.dev/blog/svelte-3-rethinking-reactivity). Component state lives in a flat `ctx` array (not objects) with a fixed index per variable "because of an optimisation related to bitmask" (Tan Li Hau, lihautan.com/compile-svelte-in-your-head-part-1, a secondary analysis since Svelte's own docs don't spell out the bitmask mechanics). Generated `p(ctx, [dirty])` functions guard each DOM write with `if (dirty & 1) ...`. The limitation acknowledged by the team itself (see Svelte 5 below): the `$:` dependency scan is syntactic, not real dataflow — it only sees variables mentioned directly in a statement's own expression text.

**Svelte 5 runes.** svelte.dev/blog/runes gives the team's own stated reasons for moving away from the 3/4 model: reactivity worked differently inside `.svelte` files than in plain `.js`/`.ts` ("can make it hard to refactor code"); the syntactic heuristic could miss real dependencies, e.g. `$: area = width * height` "won't be recalculated when `height` changes" if hidden behind indirection; and "as applications grow in complexity, figuring out which values are reactive... can get tricky." Runes (`$state`, `$derived`, `$effect`) are still compiler-recognized symbols ("function as keywords," svelte.dev/docs/svelte/what-are-runes) — the compiler still elides signal machinery entirely for SSR ("we can ditch the signals altogether, since on the server they're nothing but overhead") — but the actual change-propagation primitive moved from a compile-time bitmask/invalidate scheme to a runtime signal graph.

**Vue 3 / Vapor.** Vue 3's default mode already uses compiler-computed "patch flags" (bitwise, e.g. `createElementVNode(..., 2 /* CLASS */)`) so its vdom diff skips static subtrees, with "tree flattening" tracking only dynamic descendants in a flat array (vuejs.org/guide/extras/rendering-mechanism.html). Vapor mode (github.com/vuejs/core, `vapor` branch; prior standalone repo vuejs/core-vapor now archived, "built... on core's vapor branch") compiles templates to direct DOM-creation/update instructions with no vnode tree at all, created by Kevin Deng "with support from Evan You." A dedicated rationale post/talk from the Vue team was not retrieved this session — the repo description is the only confirmed primary source.

**Angular signals + zoneless.** Signals are runtime-tracked: Angular "establishes... 'reactive contexts' during execution... to monitor which signals are read" (angular.dev/guide/signals) — dependency discovery is dynamic, per actual read, not compiler-derived. Zoneless (angular.dev/guide/zoneless) replaces Zone.js, whose problem the docs state directly: it "triggered change detection more frequently than necessary since it couldn't determine whether application state actually changed, only that something *might* have," plus bundle-size and stack-trace costs. Per the fetched guide, zoneless is "the default in Angular v21+" (single-source, not independently cross-checked this session) and signals are what make the now-granular zoneless checks skip unaffected templates.

**Preact Signals.** Pure runtime subscription model: reading `.value` inside a tracked scope subscribes it; writing notifies only subscribers; "lazy by default and automatically skip signals that no one listens to" (preactjs.com/blog/introducing-signals). No compiler dependency analysis. Qualitative claim only: "the signals version vastly outperforms the update mechanism of any traditional Virtual DOM based framework," bundle cost "just 1.6kB" — no quantitative table found. Signals are mutable boxes by design; this is foundational, not a flagged limitation.

**Solid / dom-expressions.** Verified directly against the vendored source (`references/solid`, `references/dom-expressions`). The JSX compiler (`packages/babel-plugin/src/dom/template.ts`) emits one `template()` HTML string per static shape, cloned per instance (`cloneNode`/`importNode`, `packages/runtime/src/client.js:140-159`), plus imperative statements that grab specific clone nodes and wire only dynamic parts via `effect()`. A node with ≥2 dynamic props gets one effect reading an object literal, each field `!==`-checked before writing (`template.ts:215-276`) — Carniato's documented trade-off of batching creation cost against update granularity. `insert()` (`client.js:605-682`) runs an outer tracking effect for children, nesting an inner effect when the accessor returns a function, keeping hydration ids stable. There is no vdom: dependency edges are discovered dynamically by signal reads, not rediscovered by re-rendering. Ryan Carniato's own ceiling claims (dev.to/ryansolid, "Thinking Granular"): "the DOM itself... is our biggest limitation. It's the law of physics we must obey"; list reordering "still requires diffing"; and Solid's flattened-subscription trick (lazy prop functions, leaf-only subscription) is "not portable" to component-lifecycle-centric designs like Svelte's or `lit-html`.

**Marko 6.** Fully static: "No dependency tracking happens at runtime" (markojs.com/docs/explanation/why-is-marko-fast) — Marko streams HTML directly with "no intermediate tree data structure." "Targeted Compilation" statically proves which expressions can ever change, generating zero client JS for provably-static content. "Fine-Grained Bundling" ties client bundle size to the amount of actual interactivity rather than component boundaries. Reactivity itself is documented immutable-state-first — examples use `toSpliced`/`concat` and recommend propagating change via explicit `valueChange` callbacks rather than mutation (markojs.com/docs/explanation/nested-reactivity). Self-reported: "topped the charts" on SSR-focused benchmarks "for nearly a decade" — not independently re-verified; no announcement blog post or talk transcript was retrievable this session.

**Qwik.** A different axis (startup, not update cost): resumability serializes listeners and component-tree relationships into HTML so execution "pauses... on the server, and resumes... on the client" without replaying render logic (qwik.dev/docs/concepts/resumable). The optimizer statically extracts closures into lazy-loadable chunks referenced as `./chunk.js#symbol`. Update-time reactivity (`useSignal`, `useComputed$`) is a conventional runtime signal graph, independent of the resumability compiler pass; documented gotchas include only tracking reads before the first `await` in async computeds, and destructuring a `useStore()` breaking reactivity (qwik.dev/docs/components/state).

**Million.js, ivi, Inferno, blockdom ("block" vdom lineage).** Million rewrites React components so static markup is hoisted into a template with dynamic "holes," "skip[ping] the diffing step entirely" for block-eligible trees (github.com/aidenybai/million). Its own README credits blockdom's author "for pioneering the concept of 'blocks'," and blockdom's README in turn cites "snabbdom, then solid, ivi, stage0" as its own lineage — confirmed repo-creation dates (via GitHub API) show ivi (2016) predates both blockdom (2021) and Million (2021) by years, supporting that compiled static/dynamic template splitting as a concept is older than Million's marketing framing. Million's headline "up to 70% faster" claim (million.dev) was HN front-page news twice (news.ycombinator.com/item?id=36252795, item?id=36275714). Published skepticism found: Million's own maintainer JoshuaKGoldberg opened an issue asking for "comparisons that show actual user-facing impact" beyond "marketing metric[s]" (github.com/aidenybai/million/issues/1052); an HN commenter ("d4nyll") questioned whether "a 70% optimization in performance... [leads to] a, say, 5% increase in user experience"; and a merged PR (#89) title concedes "benchmarks not using the correct compiler flags" at some point in the project's history (detail of the bug itself unverified — only the title was retrievable). Inferno (github.com/infernojs/inferno) gets its speed from monomorphic vnode construction and bitwise shape-flag memoization rather than block templates, and cites the public js-framework-benchmark rather than a self-published percentage. ivi (github.com/localvoid/ivi) precompiles templates into static/dynamic parts and deliberately exposes a minimal API with explicit `strictEq`/`shallowEq` hints instead of automatic dependency tracking. blockdom (github.com/ged-odoo/blockdom, Géry Debongnie) is the rendering engine behind Odoo's Owl 2 and explicitly labels itself "not recommended for production use."

**Imba.** Compiles each component's `render()` into code that consults a per-instance memo cache object (`$`) keyed per expression/attribute, writing to the DOM only where a cached value differs — no virtual tree built or diffed at all. Direct quote: "Imba introduces a *revolutionary* new way of reconciling your dom which is orders of magnitudes faster than existing virtual DOM approaches" (github.com/imba/imba docs). No benchmark numbers found on the fetched page; a specific "Memoized DOM" page title could not be independently confirmed this session (imba.io is a JS-rendered SPA and a Wayback CDX search found no exact match).

**Ripple.** A newer TypeScript-first framework (github.com/trueadm/ripple, author handle "trueadm," self-described in the README as having "contributed to React, Inferno, Lexical, and Svelte 5") combining Svelte-runes-adjacent signals (`track()`/`.value`, reactive `RippleArray`/`RippleObject`/etc.) with compiler-native control-flow directives (`@if`, `@for`, `@switch`). The README states the underlying TSRX compiler stack can also target React, Preact, Solid and Vue. No version, benchmark numbers, or dedicated HN thread were found.

**Lit.** Reactive properties trigger an update cycle on write; lit-html parses a tagged template literal once into static string parts and dynamic expression slots, so updates re-evaluate only those slots rather than diffing a full tree (lit.dev/docs/components/overview, /docs/templates/overview). Deeper internal diffing mechanics were not retrieved this session.

**React Compiler ("React Forget").** Per react.dev/learn/react-compiler, it performs static whole-component analysis to auto-insert the equivalent of `useMemo`/`useCallback`/`React.memo`, "eliminating the need for manual" use of those APIs, aimed at "skipping cascading re-rendering" and "skipping expensive calculations." Explicitly it does **not** replace React's fiber/vdom reconciler — it only decides what to skip recomputing, with the vdom diff still running for whatever isn't skipped. HN discussion exists (e.g. news.ycombinator.com/item?id=40819440, 204 comments) but was not read in depth this session; content there is unverified beyond title/point counts.

## Incremental computation research

**Self-adjusting computation (Acar et al.).** umut-acar.org/self-adjusting-computation: programs build a dependency trace at runtime; on an input change, "change propagation" walks the trace and re-executes only affected sub-computations, reusing memoized results elsewhere — a push model, fully dynamic, no static program analysis. Canonical citations (standard public record, not independently re-fetched this session due to 404s on CMU PDF links): Acar's 2005 CMU PhD thesis, and Acar/Blelloch/Harper "Adaptive Functional Programming" (POPL 2002 / TOPLAS 2006). The umut-acar.org page itself names "Jane Street uses this approach via their Incremental library" as a production descendant — i.e., SAC's own advocates point to Jane Street's stack (below) as the closest thing to a UI-adjacent deployment; no UI-specific paper from Acar's group was located.

**Adapton (Hammer, Acar, et al.).** adapton.org: builds a graph of "cells" (values) and "thunks" (suspended computations) named so that re-runs can match nodes across executions; "a program's run leaves behind a graph of what it named, read and demanded, and that graph is what the next run repairs" — a pull/demand-driven model, explicitly contrasted on the site with SAC's push model. Core paper: "Adapton: Composable, Demand-Driven Incremental Computation" (PLDI 2014, Hammer et al., Univ. of Maryland). Implementations exist in OCaml, Python, Racket and Rust; no UI-specific follow-on paper or benchmark was found.

**Incremental λ-calculus (ILC).** inc-lc.github.io: Cai, Giarrusso, Rendel, Ostermann, "A Theory of Changes for Higher-Order Languages — Incrementalizing λ-Calculi by Static Differentiation" (PLDI 2014) computes a function's "derivative" statically (by program transformation) using Δ-types, so that given an input and a change to it, the derivative directly yields the change in output without rerunning the function — the fully static end of this research spectrum. Follow-up: Giarrusso et al., "Incremental λ-Calculus in Cache-Transfer Style" (ESOP 2019), adds a memo cache so the derivative reuses base-run intermediate results; Giarrusso's 2020 thesis adds correctness proofs. Explicit gap: the project site lists related work but nothing connecting ILC to UI/DOM rendering — not found, not merely overlooked.

**Jane Street: Incremental / Incr_dom / Bonsai — the most directly analogous prior art.** blog.janestreet.com/introducing-incremental/: Incremental builds self-adjusting computations as an explicit DAG (the post itself frames it as an SAC implementation) over pure OCaml values; a `stabilize()` call propagates changes and recomputes only the affected subgraph. The post's own stated cost floor: "firing a single node takes on the order of 30ns," with the caveat that Incremental only wins when per-node work is nontrivial relative to that floor, or the touched subgraph is much smaller than the whole graph. Incr_dom (github.com/janestreet/incr_dom) builds on this plus the `virtual-dom` JS library: an immutable `model` type, an "incremental view function" that recomputes/patches only the parts of the view DAG downstream of changed model nodes, and a pure `action`-driven update — matching, point for point, the "diff old vs new model by identity, notify only dependent view parts" pattern under discussion. Bonsai (github.com/janestreet/bonsai) is the newer, explicitly Elm-inspired successor: "purely functional state machines" composed à la carte, separating state/incrementality/rendering as distinct primitives so a sub-component's state lifecycle doesn't need manual hoisting, and extending incrementalization beyond the view to business-logic computation over live data. No quantitative perf numbers were retrievable for Incr_dom/Bonsai specifically (their READMEs don't publish benchmarks; the dedicated Bonsai announcement blog post 404'd this session). This is the one system in the whole survey built from pure immutable values with ordinary pure update/view functions and a runtime incremental DAG doing exactly the identity-based skip-recomputation under discussion, shipped in production for years at Jane Street.

**Differential dataflow and Salsa (brief).** Differential dataflow (github.com/TimelyDataflow/differential-dataflow) propagates deltas through a data-parallel dataflow graph (map/filter/join/reduce over "collections"), reporting microsecond-scale updates on million-node graphs — push-based, batch/parallel-oriented, not single-model interactive state. Salsa (github.com/salsa-rs/salsa, the engine behind rust-analyzer) is pull/demand-driven query memoization — `input`/`function` queries recomputed only when demanded and invalidated — explicitly citing Adapton, Glimmer and rustc's query system as influences; single-machine and demand-driven rather than data-parallel.

## Static analysis of model updates / in-place mutation of immutable state

No system was found that statically derives a "write set" of model paths directly from a pure `update` function's source and uses it to drive view notification without diffing (i.e., idea (b) in the brief) — Svelte 3/4's `$$invalidate` is the closest practical analogue, but it operates on mutation *sites in the component itself*, not on an external pure-update-function's write effects, and the Svelte team's own retrospective (svelte.dev/blog/runes) describes its dependency detection as an unreliable syntactic heuristic rather than a sound static write-set analysis. This is reported as a gap in available prior art, not a confirmed absence.

**Immer** (immerjs.github.io/immer): ES6 Proxy "drafts" record which branches of state a mutation touched; on `produce`'s finish, only touched branches are copied, with untouched subtrees shared by reference (structural sharing) — closest existing mechanism to deriving a change-set from mutation-style code. `produceWithPatches` returns `[nextState, patches, inversePatches]` in an RFC-6902-like format with array paths; Immer's docs state patches prioritize correctness over minimality (not guaranteed to be the smallest diff).

**FBIP / uniqueness-based in-place mutation (idea (c)).** Koka's "Functional but In-Place" (FBIP) plus Perceus reference counting let the compiler prove a value is uniquely referenced (refcount 1) and reuse its memory in place instead of allocating (koka-lang.github.io/koka/doc/book.html, §3.5); backing papers include "The Functional Essence of Binary Search Trees" (PLDI 2024) and "FP²: Fully in-Place Functional Programming" (ICFP 2023), with Perceus itself a PLDI 2021 distinguished-paper winner. Roc implements the same underlying idea via plain (non-atomic, single-threaded) refcounts: per Roc's own Zulip, "If Roc sees a refcount of 1, it is allowed to do inplace mutations" (roc.zulipchat.com/#narrow/stream/231634-beginners/topic/Grokking.20platforms/near/264552341), and "reference count enables in place mutation, but no reference count means you can never get inplace mutation" (roc.zulipchat.com/#narrow/stream/304641-ideas/topic/parallelization/near/277371552, Brendan Hansknecht). Lean 4's documentation on the same mechanism could not be located this session (404). **No source was found applying FBIP/uniqueness specifically to a UI/vdom model** — explicitly flagged as not found rather than assumed absent.

## js-framework-benchmark, current state

github.com/krausest/js-framework-benchmark: ~186 implementations, keyed and non-keyed, measuring create 1k/10k rows, replace-all, partial update (every 10th of 10k), select/highlight, swap rows, remove row, append 1k, clear table, plus memory and Lighthouse-derived metrics; ranking since Chrome 118 is a weighted geometric mean. The author states explicitly: "For all benchmarks the duration is measured including rendering time," and warns results are sensitive to keyed-vs-non-keyed mode and to specific Chrome builds — the repo itself documents a ~30% slowdown between two Chrome versions as a methodological caveat the author raised. The live results table (krausest.github.io/js-framework-benchmark) is rendered client-side and its current per-framework numbers could not be extracted via static fetch this session — current standings are unverified here, though the HN thread "The greatness and limitations of the JavaScript-framework-benchmark" (news.ycombinator.com/item?id=22267547) discusses the benchmark's own caveats.

## What remains above vanilla, per published analyses

- **Carniato (Solid), on Solid/fine-grained reactivity's own ceiling:** "the DOM itself... is our biggest limitation. It's the law of physics we must obey" (dev.to/ryansolid/thinking-granular); list reordering "still requires diffing" even in a fine-grained system.
- **Jane Street, on Incremental's floor:** "firing a single node takes on the order of 30ns" — Incremental is only a net win when per-node work exceeds that floor or the touched subgraph is much smaller than the whole graph (blog.janestreet.com/introducing-incremental).
- **React Compiler, by its own framing:** it only decides what *not* to recompute; React's fiber/vdom diff still executes for whatever the compiler didn't prove skippable (react.dev/learn/react-compiler) — i.e. the compiler narrows vdom work, it does not remove the vdom layer.
- **Million.js's own maintainer:** acknowledges a gap between isolated micro-benchmark deltas ("up to 70% faster") and demonstrated "user-facing impact" (github.com/aidenybai/million/issues/1052).
- **js-framework-benchmark's own author:** results shift materially with browser version and keyed/non-keyed mode choice — the measured gap to vanillajs is not purely a framework property.

## Recurring problems reported

1. **Syntactic/heuristic dependency detection breaks silently.** Svelte 3/4's `$:` tracking only sees variables named directly in a statement's text; the Svelte team's own blog names concrete failure cases (`area = width * height` missing a `height` dependency hidden behind indirection) as a direct motivation for runes (svelte.dev/blog/runes).
2. **Compile-time vs runtime is not a clean binary for any shipped system.** Every compiler-driven framework surveyed (Svelte, Vue, Solid, Marko, Qwik, Million) still relies on a runtime piece — a signal graph, an effect scheduler, or (for Vue/React Compiler) a diff that still runs — the compiler narrows or restructures runtime work rather than eliminating a runtime entirely.
3. **Benchmark-claim skepticism is common and often comes from maintainers themselves**, not just outsiders: Million.js's own issue tracker (#1052) and a historical "wrong compiler flags" benchmark bug (#89) are self-reported; js-framework-benchmark's author documents his own benchmark's sensitivity to Chrome version.
4. **Signals-based systems (Preact, Solid cells, Ripple) are mutable by construction**, which sits in tension with a pure-immutable-model architecture — none of the signal-based frameworks surveyed operate on immutable application state; they all introduce a mutable reactive cell as the unit of change.
5. **List reordering/keyed diffing resists fine-grained elimination.** Even Solid, the most mature fine-grained compiler surveyed, says reordering "still requires diffing" per Carniato — fine-grained reactivity solves scalar/attribute updates well but not list-shape changes.
6. **No prior art connects uniqueness-typed in-place mutation (FBIP) to UI/vdom models.** This was checked explicitly across Koka's docs, Roc's Zulip and general searches; the combination appears to be an open/unexplored space in public sources, not a documented and discarded idea.
7. **Academic incremental-computation systems (SAC, Adapton, ILC) have essentially no documented UI application** outside Jane Street's OCaml stack; SAC's own advocacy page points to Jane Street's Incremental as its closest production/UI-adjacent proof point, rather than citing a UI paper from the SAC research line itself.
