Status: research, 2026-10-10. Nothing here is normative. It answers the owner's question of research 68 and 69 — \emph{could editing a \code{List} while anything else still holds the old version be a compile error, with ownership inferred and no annotations in user code, so that every list is a plain JavaScript array written in place?} — by designing the checker that would do it, from the properties beni already has, and then saying where it would break. The decision whether to adopt it is the owner's; this document's job is to make the case for \emph{how} it would work strong enough that an adversarial reader can find the holes, and to list the holes it already knows about.

It reads the design documents of the compiler (\code{language.md}, \code{checker-v2.md}, \code{backend.md} §4 and §8, \code{write-sets.md}, \code{browser-direct.\allowbreak{}md}, \code{boundary.md}, \code{transparent-effects-proposal.\allowbreak{}md}), research 42 (beni's own spike on in-place writes), research 68 and 69 (the survey and its second pass), and the library \code{references/\allowbreak{}ownership/} catalogues: the core papers were read deeply, and every rule quoted below was checked against the paper's page. Citations give paper, section and page. Where this document reconstructs something a paper only asserts, it says so.

Terms, defined once and used throughout (more are defined where they first appear):

\begin{itemize}
\item \textbf{Cell.} One JavaScript array that backs a \code{List} value. Two \code{List} values that are the same cell are \code{===}; editing a cell in place changes what every reference to it sees.
\item \textbf{Holder.} Anything from which a cell can be reached and read later: a variable binding, a field of a record, an element of another list, a closure's captured variable, a fiber's saved locals, a \code{Cmd}'s thunk, the runtime's own state, a JavaScript sibling, a \code{Ref}.
\item \textbf{Content holder / identity holder.} A content holder may read the cell's elements; an identity holder only ever asks \code{a === b} of it. Only content holders can observe an in-place edit; identity holders are a separate hazard (§2.2).
\item \textbf{Dead.} A holder is dead at a point when no execution continuing from that point reads through it. A dead holder may exist; it just never looks.
\item \textbf{Unique at a site.} A cell is unique at an update site when every holder of it is dead once the update's arguments have been evaluated — the operand's own binding included. This is the property the checker proves (§2.3). It is weaker than Clean's “exactly one reference exists”, and it is what lets reads stand before writes.
\item \textbf{Demand.} A function whose summary says it writes a parameter in place: \code{List.set}, \code{List.push} and their kin in \code{core/}. Nothing in user code is a demand; user code only inherits demands by calling them.
\item \textbf{Summary.} What the checker infers per function and publishes in its interface: for each parameter, whether the function consumes it, shares it or only borrows it; for the result, which parameters it may alias; for each function-typed parameter, how often it is called and whether it escapes (§2.6).
\item \textbf{False error.} A rejection of a program that would in fact have run correctly in place. Because the checker is sound and incomplete, every imprecision is a false error, never a wrong answer; §6 says how the message tells the two apart.
\item \textbf{Value semantics / update semantics.} The meaning beni has today (every update builds a new list; the old one is untouched) and the meaning the checker licenses (an accepted update writes the cell). The soundness claim is that the two cannot be told apart (§4).
\end{itemize}
