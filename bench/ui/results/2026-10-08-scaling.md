# UI scaling sweeps and the table benchmark, 2026-10-08: beni as merged, Solid 1, vanilla JS

Where beni stands against Solid 1, with vanilla JavaScript as the floor, after research 56's A and
B landed on `master` (PR #3, `84de8d94d`). The first batch to measure the merged compiler, and the
first with vanilla JS on every sweep, including the three added on 2026-10-04 (live rows, helper
rows, helper tree). Slice C (`List.$diff`) is not merged, so the long-list rows below are without
it.

Raw samples: [`2026-10-08-scaling-full-merged.json`](2026-10-08-scaling-full-merged.json) and
[`2026-10-08-table-merged.json`](2026-10-08-table-merged.json). Tables with interquartile ranges:
`node report-scaling.mjs results/2026-10-08-scaling-full-merged.json` and
`node report.mjs results/2026-10-08-table-merged.json`.

## Method

- **Harness and programs:** as [`2026-10-04-scaling.md`](2026-10-04-scaling.md): one real click
  on `#go` in a fresh page, click to paint from a Chrome trace, after five warm-up clicks. Each
  framework's program is written as that framework's developer would write it. Vanilla JS writes
  the one node a message changes. On the live-rows page it renders the inputs once and never
  touches them again, which is how one writes it by hand: there is nothing to reconcile, so it
  does none of the work beni's controlled-input guarantee does.
- **Subjects:** beni's development build (ReleaseFast compiler at `84de8d94d`), Solid 1 and
  vanilla JS. Every point is unthrottled (1x), the column `2026-10-04-scaling.md` says to read
  below about 1 ms. 2 pages × 4 samples per point, medians in script milliseconds.
- **Machine:** Chrome 153.0.8010.36 headless, pinned to CPUs 8–15 of a Ryzen 9 5950X. The batch
  ran 11:27–11:42 UTC; 1-minute load at batch starts was median 0.41, max 1.49; no failures.
  The table benchmark is js-framework-benchmark's nine operations with the official throttling,
  n = 10 (11:42–11:52 UTC, load 0.50–1.55), with beni's `--release` build added.
- **Reading across batches:** Solid 1's own medians move by up to 0.02 ms between batches
  (holes 10: 0.071 on 10-04, 0.092 here), so compare subjects within this batch, not with the
  numbers of earlier reports.
- **Sizes** (the `B` columns): each subject's whole bundle, every JavaScript file the page loads
  concatenated, through terser (`--compress --mangle --module`), then brotli 11, in bytes
  (`sizes.mjs`'s method, per sweep point: `node scaling-sizes.mjs`; gzip -9 is in
  [`2026-10-08-scaling-sizes.json`](2026-10-08-scaling-sizes.json)). beni's size is its
  `--release` build, the one a user ships. The sweeps time the development build; on the table
  benchmark the two builds are within 12% of each other on every operation. Solid 1's is its
  production bundle; vanilla's is its one script. Bursts and the stream run on the 1 000-hole page,
  so their size is that page's.

## 2. The table benchmark (js-framework-benchmark, official throttling, n = 10, script ms)

| operation | beni | beni `--release` | Solid 1 | vanilla | beni ÷ Solid 1 | beni ÷ vanilla |
|---|--:|--:|--:|--:|--:|--:|
| create 1k | 4.55 | 4.65 | 4.90 | 4.67 | 0.93 | 0.97 |
| replace 1k | 10.1 | 10.5 | 11.8 | 9.68 | 0.86 | 1.04 |
| update every 10th | 1.45 | 1.51 | 1.68 | 0.71 | 0.86 | 2.04 |
| select | 0.90 | 0.99 | 1.70 | 1.39 | 0.53 | 0.65 |
| swap | 0.97 | 0.95 | 1.76 | 0.39 | 0.55 | 2.49 |
| remove | 0.48 | 0.47 | 0.56 | 0.53 | 0.86 | 0.91 |
| create 10k | 49.4 | 48.9 | 55.5 | 47.6 | 0.89 | 1.04 |
| append 1k | 5.62 | 5.00 | 5.23 | 4.88 | 1.07 | 1.15 |
| clear | 22.4 | 21.6 | 22.5 | 21.2 | 1.00 | 1.06 |

The development build is ahead of Solid 1 on seven operations, even on clear, and behind on
append (1.07). The `--release` build is ahead on all nine: append 5.00 against 5.23, clear 21.6
against 22.5. The interquartile ranges of update every 10th (beni 1.13–1.62, Solid 1 1.60–1.83)
and select overlap the neighbouring subjects', as they did on 10-04. Against vanilla, the
development build is level or ahead on create 1k, select and remove, within 6% on replace,
create 10k and clear, and 2.0–2.5× on update every 10th and swap. Those two operations touch a
handful of rows, which vanilla writes directly.


The table app's bundle, minified then brotli 11, in bytes (`node sizes.mjs`): beni `--release`
5 510 (5 670 as served, without terser), beni development 8 462, Solid 1 4 354, vanilla 1 415,
P2 1 537, Solid 2 21 988. beni's release bundle is 1.27× Solid 1's and 3.9× vanilla's.

## 3. Bundle size, and how it scales

The sweeps' pages are generated and highly repetitive, and brotli removes repetition well. So a
large page's size says how much distinct code each framework writes per element, more than how
large a real application would be.

- **Programs whose code does not grow with N** (rows, derived, live rows, helper rows, helper
  tree). The data is made at run time, so no subject's size moves with N.
  - Rows: beni 3 823–3 835 against Solid 1 3 565–3 576 (+7%).
  - Derived: 3 637–3 643 against 3 557 (+2%).
  - Live rows: 3 448–3 453 against 3 515–3 516 (−2%).
  - Helper rows: 3 231–3 235 against 3 478–3 481 (−7%).
  - Helper tree: 1 511–1 513 against 3 065–3 067 (−51%).
- **The floor.** On the smallest page of each sweep beni is 1.7–2.9 KB smaller: holes 10
  1 241 against 2 948, width 4 1 131 against 4 037, depth 1 1 372 against 4 082.
- **Size that grows with the program.** Fitted from the first to the last point, in bytes per
  element:

  | sweep | beni | Solid 1 | where Solid 1 becomes smaller |
  |---|--:|--:|---|
  | holes (per hole) | 6.1 | 5.3 | from about 3 000 holes (20 505 against 20 066); 10 000: 61 905 against 55 497 (1.12×) |
  | width (per field, each in a hole) | 16.0 | 5.9 | from about 300 fields; 1 024: 17 436 against 10 064 (1.73×) |
  | depth (per level) | 13.8 | 3.2 | not within the sweep (128: 3 127 against 4 486); about 260 levels by extrapolation |

  beni's per-element cost is the larger on all three. Solid 1's size starts higher and grows
  more slowly, so beni's lead on small programs shrinks and, past a few thousand holes or a few
  hundred model fields, reverses. Width is the steepest; why a field costs beni 16 bytes is not yet
  traced.
- **Vanilla** stays between 168 and 415 bytes on every sweep except width (208 → 1 742 at
  1 024 fields). Its holes page is one literal HTML string, which brotli reduces to about 195
  bytes at any N (gzip -9: 253 → 946).

## Summary

- **Vanilla JS is flat at 0.039–0.061 ms per message** on every sweep except swap (0.074–0.101)
  and bursts, which do K times the work. Solid 1 is flat at roughly 2× vanilla. Where beni
  matches Solid 1, it is also about 2× vanilla.
- **Level with Solid 1 (within 10%, or faster):** derived views to 100 000 items, model width to
  256 fields, depth to 32, helper rows, the helper tree (between 0.97 and 1.22 by point, with no
  trend), small views (holes to 300), and the stream. **Clearly faster:** swaps from 300 rows
  (3–6× at 3 000–30 000), bursts from K = 30 (0.67–0.73×), and the table benchmark: seven of nine
  operations in development, nine of nine in release.
- **Behind Solid 1:**
  - **Live rows, 1.6–22×, growing linearly:** about 0.24 µs per row per render, 2.42 ms at
    10 000 rows (50× vanilla). This is the cost of the controlled-input guarantee as specified;
    the next slice is to make it proportional to the inputs actually edited.
  - **A long keyed list's one-row edit, 1.2–3.8×, growing:** 0.442 ms at 30 000 rows. This is
    slice C's target; C is not merged.
  - **Model width 1 024: 3.9×.** Copying the record in `update`; research 55's open question.
  - **Depth 64–128: 1.3–1.5×.** Not named in research 56. It grows with D, where Solid 1's
    store path grows more slowly.
  - **Large views: 1.20–1.27× at 1 000–10 000 holes.** That is about 0.02 ms absolute.
  - **A burst of one synthetic click: 1.46×.** The microtask is kept on purpose for batching,
    and a trusted click no longer pays it.
  - **Append, in the development build only: 1.07×.**
- **Size:** beni is smaller than Solid 1 on small programs (1.7–2.9 KB less at the start of each
  sweep, half the size on the helper tree) and about level on the other fixed apps (−7% to +7%). It
  grows faster per element: per hole 6.1 bytes against 5.3, per model field 16.0 against 5.9,
  per level of depth 13.8 against 3.2. Solid 1 is smaller past about 3 000 holes or 300 fields
  (1.12× at 10 000 holes, 1.73× at 1 024 fields). On the table app beni `--release` is 5 510
  bytes against Solid 1's 4 354 (1.27×); vanilla is 1 415.

## Caveats

- Chromium/V8 only, development builds on the sweeps, one machine.
- The first attempt at this batch measured stale pages: `scaling.mjs` decided whether to
  rebuild a page by its source alone, so pages built on 10-04 by the compiler before A were
  measured as "beni" (holes 10 at 0.147). The run was discarded. `scaling.mjs` now stamps each
  built page with a hash of the beni binary that built it and rebuilds when the stamp differs.
  Earlier batches that reused a `bench/ui/out/scaling` tree across compiler changes could have
  had the same problem. Research 56's batches built each compiler into a directory of its own
  (`--variants`), which this defect does not reach, but its plain `beni` subject could have.
- The tree was dirty during the batch only by a text edit to `plans/`; no compiler or bench
  source differed from `84de8d94d`.
- On this machine Chromium must run with `LD_LIBRARY_PATH` unset: the login environment points
  it at an `alsa-lib` built for a newer glibc, and Chrome then does not start.
