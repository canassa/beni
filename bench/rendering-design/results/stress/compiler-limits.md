# Compiler resource limits encountered by the size sweep

These are failed builds, not measured bundle sizes. They are not extrapolated.
The direct failure is tracked in [#203](https://github.com/canassa/beni/issues/203).

On the original flat mixed app, N=1,728, seed 17, Linux killed beni for global OOM.
The kernel recorded **30,003,552 kB anonymous RSS** and **41,337,944 kB virtual
memory** for beni pid 3733677 at 2026-10-15T20:47:17Z. N=1,152 had compiled and
measured at 242,074 brotli rendering bytes after the common normalization.

A separate layout probe uses exactly the same leaves but 27 additional routing
modules of up to 64 children, generated by `stress-grouped-generate.mjs mixed
1728`. Its TEA build succeeds (232,685 brotli bytes for the original full release
bundle); direct reports `beni: OutOfMemory` with a 16 GiB address-space cap.
The grouped source is not spliced into the flat-source curves.

Subsequent stress compiler invocations use that per-process cap. A curve ends
at a failed build, with the reason and input/compiler hashes in `stopped.jsonl`.
Other curves continue independently. A follow-up of the failed list N512 build
with `--jobs=1` also reports `OutOfMemory` under the same 16 GiB cap
(`direct-single-thread-probe.json`); compiler parallelism is not sufficient to
explain that limit. `failures.jsonl` also retains harness
failures: the first missing dependency was installed; Terser's default-stack
failure is retried with a 16 MiB V8 stack and 32 MiB OS stack, without changing
its optimization options or the source being measured.

Reproduce the capped probe on Linux in the pinned compiler environment:

```sh
node bench/rendering-design/stress-grouped-generate.mjs mixed 1728
CASES_FILE=/.out/grouped-pilot-cases.json RESULT_PREFIX=grouped-pilot- \
  BENI_MEMORY_BYTES=17179869184 BENI=zig-out/bin/beni \
  node bench/rendering-design/build-today.mjs
```

This is research evidence, not a diagnosis or compiler fix. No repository gates
or suites were run.
