# M4-2 — the front-end artifacts on disk: the file key, the container, and the write pass

**Status:** plan, 2026-09-19, written at `8ce74de` with M4-0 and M4-1 landed. Nothing is started.
The contract lives in three documents and this one holds only what is plan: the artifact set, the
file key, the container, the write pass and the acceptance axis are
[`fast-compiler.md`](../docs/design/fast-compiler.md) §8, *The front-end artifacts, and the file
key*, with the `mmap` correction in §8.3; the per-artifact shapes and the hit path are
[`frontend.md`](../docs/design/frontend.md) §3.1, §3.2, §3.5, §3.6, §4, §6; the shared container is
[`checker.md`](../docs/design/checker.md) §7. **Standing:** M4 first, cache before socket
(`plans/m4-plan.md` D5, D1); D6–D9 are the daemon's, **PENDING**, and nothing here needs them.

Measurements marked *(measured)* were taken here, 2026-09-19, on the M4 plan's machine (Ryzen 9
5950X, 32 threads, Zig 0.16.0), **ReleaseFast** into a scratch prefix outside the repo, corpus
`zig build bench -- --generate=100000` — 624 files, 1 835 956 bytes, **634 modules with core** and
1 936 179 bytes with it. Every wall figure is best-of-N with the one-minute load average between
**0.13 and 0.46** throughout; every cold/warm comparison is **ABBA-interleaved**; raw lines are in
§4, §6 and §11. **The filesystem is named every time**: the repo and the cache are on **btrfs**
(`compress=zstd:1`) and `/tmp` here is **tmpfs**, 3× cheaper on precisely the operation this slice is
about — a figure taken there would have been wrong by that factor.

---

## 1. What this slice is, and what it is not

**Is:** a file whose **file key** is unchanged is not lexed, parsed or lowered. Its pre-resolve
`Bir`, its token spans, its line-start table and its rendered front-end diagnostics are loaded from
disk and installed by the worker that would have produced them, and `--self-profile` reports
`files_lexed = files_parsed = files_lowered = 0`. **Is not** the `stat` fast path, which M4-1
deferred here and which §5 hands to M4-5 on the numbers: the source is still read and still hashed,
because the file key is over its bytes. Nor the firewall cutoff (M4-3), any whole-program pass or
emitted byte (M4-4), the pack file and §8.3's zero-copy load (M4-4), or the daemon (M4-5).

**Why it is worth a slice.** The front end is **41.9 ms of a 62.2 ms warm `check --jobs=1`**
*(measured, §11.2)* — 67 % of it. Nothing else in M4 is a two-thirds share of anything.

## 2. The decisions, and the alternative each rejected

| # | Decision | Rejected, in one line |
|---|---|---|
| 1 | Four artifacts: pre-resolve `Bir`, the token `tag`+`start` columns, `line_starts`, the rendered front-end diagnostics | The `Ast` and `comments` with them — nothing downstream of `lower` reads either on a `check` or a `build`, and `fmt`/`dump` take no cache flag, so they are bytes written on every cold build and loaded by nothing (§3) |
| 2 | A **file key** distinct from M4-1's module key: build id + package + `Lower.Options` + source hash, nothing else | Reusing the module key — it folds every import's key, so a leaf's body edit would throw away every importer's front end, which is the one case this slice exists to serve |
| 3 | A second file, `<file key>.bef`, beside M4-1's `<module key>.bec` | Two independently-keyed sections of one file — a file is named by one key or it is not content-addressed |
| 4 | `read` + validate + fix up, little-endian by definition, **not** `mmap` | `mmap` per entry, as §8.3 said: 4.5–5.0 ms against 1.9–2.3 ms, and identical whether one byte or every page is touched, so the cost is the syscall pair (§4) |
| 5 | `symbols` ships as offsets into a per-artifact `strings` blob; the load `getOrPut`s each DISTINCT string once, then calls the existing `Bir.applyRemap` | A lookup per symbol SLOT — 3.4× the hashing for the same answer. And content-derived global `Symbol` ids, which fix determinism and not this: no dense numbering survives a file being added (§7) |
| 6 | Load and store on the **worker**, interning into its `Local` pool | M4-1's serial pre-pass — that exists because an entry's re-intern must `getOrPut` into the thread-confined `Global`; a per-file artifact has a `Local` to hand |
| 7 | Plain `create` + write, no temp file and no `rename`, for `.bef` and `.bec` alike | Keeping `rename`: 26.1 ms against 12.9 ms serial for 633 entries, to buy an atomicity a content-addressed name already provides (§6) |
| 8 | No `stat` fast path; the rule it will need is written down and it moves to M4-5 | Taking it now — a net 3.9 ms for a path-keyed index in a compiler that deliberately never makes a path absolute (§5) |
| 9 | Loaded columns are **session-owned `gpa` memory** through `Artifacts.set`; the read buffer and the string blob are worker scratch | A worker-arena allocation or an `mmap`ing — an arena only grows, and a mapping cannot be dropped per file, which is what M4-5 needs (§10) |
| 10 | `fmt` and `dump` keep refusing `--cache-dir` | Letting `dump` benefit — a `dump --stage=bir` served from a cache stops being the oracle `--roundtrip-frontend` asserts against |

## 3. The artifact set, decided from who reads what on a warm run

The crux of the slice, answered by reading every consumer.

**Tokens: two of four columns survive `lower`.** `tag` and `start` are read by `Session.tokenSpan`
(`src/Session.zig:1200-1201`, `tag` for `Tokenizer.tokenEnd`), `moduleNameOfImport` (`:1246`),
`Emit.tokenPosition` (`src/js/Emit.zig:326`) and `js/Lower`'s `token_starts` (`js/Emit.zig:1210`,
consumed at `src/js/Lower.zig:348-349`). `line` and `payload` are read only by `Parse.zig:176-178`,
`bir/Lower.zig:263-265`, `fmt/Format.zig:163-165` and `dump/tokens.zig:34`. The cached form is 5
bytes a token in two columns rather than 13 in four — and, worth more than the 2.6×, **it holds no
`Symbol`**, because `payload` was the only place a token ever did.

**`Ast`: read after `lower` by nothing** on a `check` or a `build` — only the format phase
(`Session.zig:783`), `dump --stage=ast` (`main.zig:214`) and the parse phase that made it. Same for
`comments` (`main.zig:196`, `:211`, `:222`, `Session.zig:701`, `:795`): `Bir.module_doc_start/end`
and `Decl.doc_start/doc_end` index it and their only readers are `dump/ast.zig:119`, `:151` and
`dump/bir.zig:202`, `:229`. The `Ast` is the **easiest** artifact in the compiler to cache
(`plans/m4-plan.md` §2.1: three flat arrays, no `Symbol`, no fixup) and that is not a reason to; M5's
LSP wants a tree for the file being edited, which is a miss by construction.

**`Bir`, pre-resolve: read by everything** — `Resolve.rewriteReferences` in place
(`src/resolve/Resolve.zig:220-238`), `Types.build` (`src/check/Types.zig:364`, `:477`), `Cycles`,
`Reach` (`src/js/Reach.zig:224`, `:313`), `js/Lower`, `Emit`, and the whole check on a miss.
**`line_starts`: read by every `diagnostic.position` call** (`Session.zig:1196`, `:1213`,
`js/Emit.zig:324`) — recomputable by a scan, cached because it is 4 bytes a line and because it is
what will let M4-5 stop reading the source at all. **Front-end diagnostics: rendered by the phase
that will not run** — lex, parse and lower render on the worker (`Session.zig:709-720`, `:746-757`)
into `Worker.Pending`, `{code, severity, start, end, message}` (`:304`, `:320-345`), so the rendered
rows travel with the artifact. Positions rather than offsets (a position is a function of the content
the key pins); `span.file` and `title` stay recomputed from the path and the code, so a file that
MOVED without changing its bytes still names itself correctly.

## 4. `mmap` or `read` — measured, and §8.3 corrected

633 files in a fresh two-level fan-out on **btrfs**, best of five (`scratchpad/m42/io_bench*.zig`).
2 213 B is M4-1's measured entry; 13 000 B is §3.1's estimate for a `.bef`.

```
                                 2 213 B   13 000 B   15 213 B
open + read into a buffer           1.98      2.23      2.27   ms
readFileAlloc into an arena         3.24      5.76      6.35   ms
open + mmap + munmap, all pages     4.53      4.99      5.03   ms
open + mmap + munmap, header only   4.61      4.96      4.97   ms
open + fstat only                   1.86      1.86      1.90   ms
one pack file: mmap + 633 headers   0.05      0.27        —    ms
one pack file: one read             0.06      0.31        —    ms
```

**`read` beats `mmap` by 2.2×**, and `mmap` costs the same whether the loader touches one byte or
every page — so what is paid is `open`+`mmap`+`munmap`, ~7.5 µs a file, not the paging. §8.3's "mmap
on load" was written for a format, not a granularity, and at one file per key the granularity
decides. Two consequences, taken deliberately: the on-disk form stays **little-endian by definition
and host-alignment-independent** like the interface record (a `read` has no alignment to satisfy), so
nothing in a cache directory is machine-specific *by layout*; and §8.3's zero-copy load is re-aimed
at the pack file — **one mapping reads 633 headers in 0.05–0.28 ms**, 20× the best per-file figure —
M4-4's (§6 C). `readFileAlloc` into an arena, which `cache/Dir.load` uses, is 1.6–2.8× a read into a
reused buffer; the `.bef` reader takes a per-worker scratch buffer, which `Worker.arena` already is.

## 5. The `stat` fast path: the numbers, the safety rule, the deferral

**What it saves** *(all measured)*: `read` **5.15 ms** + the source hash **0.57 ms** − **1.86 ms** for
633 `open`+`fstat` = net **≈3.9 ms** of a predicted ~33 ms warm `check`, about 12 % — the
second-largest thing left after this slice. **What it costs** is a map from PATH to file key, and
**a path here is never made absolute** (`frontend.md` §1, `0bc5d89`): paths are normalised lexically
and kept as the user typed them so a diagnostic names the file the way the user named it. An index
keyed on that string is a function of *how the build was invoked*, not of the file — `beni check src`
and `cd .. && beni check proj/src` would miss each other, `--root` moves it again, and making the key
absolute reintroduces exactly what §1 refuses.

**The rule it must obey, written now so it is not re-derived:** trust a `(size, mtime, inode)` match
only when the recorded mtime is **older than the index's own write time by more than the filesystem's
timestamp granularity** — git's "racy timestamp" rule — and hash otherwise. That covers the file
edited twice inside one tick; the rest degrade to a hash, 0.57 ms for the project (a `git checkout`
restoring an old mtime changes the inode or the size or trips the racy window; a copied tree changes
the inode; a skewed clock gives an mtime never "older by more than the granularity"). The escape
hatch is **always hash when the index is not trusted, never a flag** — a correctness knob a user can
turn the wrong way is worse than 0.57 ms, and `--no-cache` exists.

**Decided: not in M4-2; it is M4-5's.** A daemon holds the sources and the watcher, so it answers
"did this change" without a stat at all, and its index is per-process rather than on disk.

## 6. The write pass, re-evaluated — `plans/m4-1.md` §11.5's question, answered

633 files into a **fresh** tree with the fan-out pre-created, btrfs, three repetitions, one variant
per process invocation so no run warms another *(measured)*:

```
variant                        2 213 B               13 000 B
atomic (temp+rename), jobs=1   26.05 26.18 26.28     28.37 28.64 28.72   ms
atomic (temp+rename), jobs=8   15.55 15.86 16.09     14.79 15.75 17.18   ms
atomic (temp+rename), jobs=16  16.17 16.95 17.05     16.46 16.69 16.80   ms
plain create,         jobs=1   12.38 12.90 12.95     14.90 14.91 15.45   ms
plain create,         jobs=8    6.81  6.83  7.01      7.03  7.18  7.80   ms
plain create,         jobs=16   6.88  7.22  7.72      7.43  7.91  7.95   ms
one pack file                   0.52                  2.73               ms
```

On tmpfs the atomic-serial, atomic-8 and pack rows at 2 213 B are 8.0 / 2.1 / 0.6 ms — **3.3× cheaper
on the writes, identical on the loads**. **ext4 was not measured and nothing here is a claim about
it**; expect something between the two, the per-file cost being journal and directory metadata.

**The size barely matters; the file count does.** 2.2 kB and 13 kB are within 10 % in every row — so
M4-2's ~8 MB of extra bytes is nearly free and its 633 extra FILES are not, which is why §2 decision
3 had to be argued rather than assumed.

**A: the `.bef` is written by the worker that produced it**, in the per-file phase — 7.0 ms at
`--jobs=8`, 12.9 ms at `--jobs=1`, overlapping other files' lexing. No serial pass and no new failure
path: that phase already does file I/O and already reports nothing on failure. This is *not* what
M4-1 decision 9 declined — that was a write on the **DAG**, where a failure would have to be reported
from a checking worker and the cost would vanish from the row that measures it. `frontend_store` is
that row here.

**B: drop the temp file and the `rename`, for `.bef` and `.bec` alike.** 26.1 → 12.9 ms serial,
15.9 → 7.0 ms at eight workers. Safe **because the name is a content hash**: two processes racing on
one key write identical bytes, so any interleaving is still the right bytes; a reader seeing a
partial file sees a short one and the section table's bounds check makes it a miss; a crash mid-write
leaves a truncated file the next build's miss overwrites, so the failure is self-healing. Two lines
in `src/cache/Dir.zig:134-138`, and it makes M4-1's own cold path 13 ms cheaper — most of what §11.5
worried about. *Rejected: keeping `rename` for its own sake — `Dir.zig`'s header argues for it
against a lockfile, and that argument is about not wedging the next build, which a plain create does
not do either.*

**C: the pack file is recorded and not taken.** 25–50× better on the write and 20× on the load, and
where §8.3's zero-copy load belongs — but it needs an index, a merge-on-write so two builds with
different option sets do not evict each other, and a GC story M4-1 deliberately has none of. Taking
it here decides the directory's shape twice, the mistake §11.5 named. M4-4, with these numbers.

## 7. The symbol problem, and what it costs

Every front-end artifact that holds a `Symbol` holds it through **one column**, `Bir.symbols`
(`src/bir/Bir.zig:57-60`), and `applyRemap` is one loop (`:738-740`). The token `payload` column is
the other place, and §3 removes it from the artifact entirely. So the whole problem is one column.

**Measured**, over the 624 app files: **117 201** identifier-token occurrences, **38 274** distinct
summed per file (61 per file), **10 454** distinct across the corpus. `Bir.symbols` does not dedup
(`bir/Lower.zig:402-406`), so its slot count is bounded by the first; `strings` by the second.

**The machinery exists and already runs on every build.** `merge_interners` is **1.48 ms at
`--jobs=1` and 1.53 ms at `--jobs=8`** *(measured)*, covering ~10 500 `getOrPut`s **plus**
`Artifacts.applyRemap` over every file — 310 028 token payloads and ~130 000 Bir slots, 440 000
rewrites. M4-2's load does **3.7× the distinct lookups** (each file looks up its own set) and **0.3×
the slot rewrites** (no token payloads). Splitting 1.48 ms evenly between the halves gives ≈2.9 ms;
the honest prediction is **2–4 ms**, reported as a `frontend_load` sub-row against the **14.1 ms**
`lower` it replaces. It happens on the worker, into `Worker.interner` (`InternPool.Local`), because
`Global` is thread-confined (`src/InternPool.zig:24-26`); step 3's merge then carries it to the
global pool in worker-index order, unchanged — the load produces exactly the local numbering
`Global.merge` was written to reconcile, so **no rule changes and no new synchronisation appears**.
This is the one place M4-2 is simpler than M4-1, whose entry load must be a serial pre-pass because a
record's re-intern has nowhere to go but `Global`.

**Rejected:** one lookup per symbol SLOT (3.4× the hashing, and `strings` stops deduplicating); and
content- or file-index-derived global `Symbol` ids, which `fast-compiler.md` §5.1 has as "decided,
not implemented" — that fixes the `--jobs` dependence `Session.zig:16-22` warns about, a determinism
problem, and **not this one**, because no dense global numbering survives a file being added without
a second global side table carrying its own invalidation.

## 8. The ordered change list

Each step is green on all three gates on its own. The riskiest decision — the symbol remap — lands
**first, behind `--roundtrip-frontend`, before any disk I/O**, as M4-1 landed its key table before
its writes.

**M2-a — the container and the format.** `src/frontend/artifact_bytes.zig`: `write`/`read` to §8's
section list, `symbols` becoming offsets into `strings` on write and `Bir.applyRemap` rewriting it on
read. In-source round trips over the records the existing `Bir` tests build, plus §9.4's
corrupt-input table. Nothing touches a file.

**M2-b — `verify`.** The structural walk §8 lists: declaration ranges nested, contiguous and in
order; every side-table range in bounds; every tag a value its enum defines; every `SymbolIndex`
inside `symbols`; every `main_token` inside `token_tags`. In-source, plus §9.4's mutation sweep.

**M2-c — `--roundtrip-frontend`.** A `bool` on `Cli.Common` (`src/Cli.zig:77-135`), through
`Session.Options`, honoured at the end of `lowerPhase` (`src/Session.zig:731-779`) — write, read
back, install in place, **before** `Resolve` and before anything downstream. The matrix's two
round-tripped runs pass all three flags, so the format is proven lossless over ~336 fixtures at no
extra invocations; absent from `beni help` and `checker.md` §2's table. **The slice's cut line**:
everything risky about the symbol column is settled with no cache directory in sight.

**M2-d — the file key, and `--frontend-keys`.** `src/cache/FileKey.zig` beside `Key.zig`, §8's recipe
as a pure function with hermetic golden vectors; hidden `--frontend-keys` prints one
`<path> <32 hex digits>` line per file sorted by path, `--cache-keys`' twin. §9.1's whole table lands
here, again before a byte reaches disk.

**M2-e — writing.** The worker writes its `.bef` after the phase. `Profile.Phase` gains
`frontend_store`; `Profile.Counter` gains `files_lexed`, `files_parsed`, `files_lowered`.
`cache/Dir.zig` drops temp-and-rename for both file kinds (§6 B) and gains `storeFrontend`. Output
does not move by one byte and the three counters equal the file count.

**M2-f — reading, and the hit path.** The worker computes the key, reads, validates, verifies,
re-interns into its `Local` and installs — or lexes. `Profile.Phase` gains `frontend_load`; §9's
scenarios now assert hits and misses, and cold ≡ warm. **M2-g — the matrix's assertion.**
`matrix_test.zig`'s warm run asserts the three counters are 0 and its cold run that they equal
`files`; no new axis and no new invocation. **M2-h — the numbers.** `bench/bench.zig` gains a
`frontend` row (write, read, verify, re-intern, bytes on disk, per-module distribution) and §11 here
is filled in, as `plans/m4-1.md` §11 was.

### 9.2 `--roundtrip-frontend` over the whole corpus

16. Every checker-driven corpus kind with the flag, byte-identical: exit code, stdout, stderr,
    diagnostics, `--stage=raw`, `--stage=dispatch`, the `.iface` golden, the emitted JavaScript.
17. **The identity oracle.** `dump --stage=tokens|ast|bir` with the flag over every `parse/good` and
    `bir/` fixture, byte-identical. `bir` is the direct assertion; `tokens` asserts the two-column
    reduction lost no span; `ast` must be unchanged **by construction** because the `Ast` is not an
    artifact, and asserting it is how that stays true.
18. **`fmt --stdout`** over every `fmt/` fixture with the flag, byte-identical: the formatter reads

### 9.3 The cache as an environment

20. `--jobs=1` writes, `--jobs=8` reads, and the reverse: all hits, output byte-identical. **The
    interner-order fixture** in slice zero §7.1's form — `P = {Zeta}` against `P' = P + Aardvark`, an

21. Two processes at once on one project and one cache directory: both exit 0 with identical output,
    a third run hits everything. With §6 B this is also the torn-write fixture.
22. A read-only cache directory, empty and pre-warmed; `--no-cache` beside `--cache-dir`;
    `--cache-dir` naming an existing FILE; a path with spaces and non-ASCII — all as M4-1 §6.3. And
    `fmt --cache-dir=x` and `dump --cache-dir=x` stay `unknown option`, exit 2.

### 9.4 Corrupt artifacts — each a MISS, never a crash, never a wrong answer

23. Per artifact kind and per section: zero-length; truncated mid-section; wrong magic; unknown
    `format_version`; a section offset or length past the end; a header key that is not the file's
    name; a `strings` record overrunning its blob; a `SymbolIndex` past `symbols`; a `main_token`
    past `token_tags`; a `Decl.inst_end` before its `inst_start`; overlapping declaration ranges; an
    `Inst.Tag`, `Decl.Kind`, `Local.Kind` or `Ref.Kind` no version defines; random bytes. Each: the
    build is byte-identical to a cold one and exits the same way.
24. **A deterministic mutation sweep**, as slice zero §7.7 established: one real artifact, each byte
    flipped in turn and set to `0x00` and `0xFF`; every outcome either a clean load `verify` accepts
    or a refusal. Never a trap, never a read past the buffer. In-source, seeded, bounded.
25. A `.bef` that is structurally valid but describes a DIFFERENT file — another key's artifact
    renamed — is refused by the header key, not by luck.

## 10. Memory and lifetime

For a one-shot process none of this matters; all of it matters to M4-5, and now is the cheap time.
**The ownership rule:** every loaded column is allocated from `session.gpa` and installed through
`Artifacts.set`, exactly as a lexed or lowered one is (`src/Artifacts.zig:5-16`), so an edited file's
columns are freed and rebuilt on their own and every other file's survive — the property `:15-16`
says the daemon needs. The read buffer and the `strings` blob are **worker scratch** from
`Worker.arena`, consumed into the interner and gone when the arena resets between files.

**What M4-2 must NOT do.** Allocate an installed column from the worker's arena — an `Arena` free is
a no-op except for the most recent allocation (`src/Arena.zig:14-16`), and `plans/m4-plan.md` §4.1's
lesson is that in an arena a quadratic is a leak. Hand `Artifacts` an `mmap`ing — a resident process
would hold 634 mappings for the life of the project and could not drop one file's. And add nothing
to `plans/m4-plan.md` §2.6's re-entrancy list: a replayed diagnostic appends to the same
`Worker.diagnostics` a reported one does, so that list's "never cleared" stays M4-5's problem on the
schedule it already had.

## 13. Risks, and what could not be determined

**Risks**

1. **The `Bir` is reached by raw index all over the compiler, and a loaded one is the first that did
   not come from `Lower`** — `Reach`, `js/Lower`, `Types.build` and `Emit` index `insts`, `decls`,
   `refs` and `extra` directly. `verify` (M2-b) is the whole of the defence and §9.4 item 24 the
   whole of the evidence that it is enough; neither may be skipped. If `verify` costs more than a
   small fraction of the 14.1 ms `lower` it replaces, the slice bought less than it thinks.
2. **The estimated columns of §3.1** are perhaps a quarter of the artifact. At 20 kB a module the
   cold write is still flat (§6) but the directory is 13 MB and the GC question arrives sooner.
3. **Dropping `rename` (§6 B) touches M4-1's entry too**, and M4-1's fixtures are what would catch a
   regression. Land it in M2-e with §9.3 item 21 green, or not at all.
4. **A replayed front-end diagnostic stores rendered prose** and inherits `plans/m4-1.md` §10 risk 3:
   if any lex, parse or lower message ever embeds a path or a line number OF ANOTHER FILE, a replay
   after that file moved is wrong. These are per-file phases with no cross-file knowledge, so it
   should be impossible by construction — but "should be" is not a grep, and one over
   `src/lex/Diagnostics.zig`, `src/parse/Diagnostics.zig` and `src/bir/Diagnostics.zig` is the
   implementer's first task.
5. **`--roundtrip-frontend` runs inside the phase, not after it**, so a bug in it is a bug in every
   fixture at once. That is deliberate — it is what makes the oracle strong — and it makes M2-c the
   commit most likely to be reverted, which is why it is first.

**Could not determine.** **The exact artifact size** (§3.1's five marked estimates; the cross-check
against the 8 351 050-byte `--stage=bir` text is consistent but is not a measurement of the binary
form), **the re-intern cost** (§7 derives 2–4 ms from `merge_interners`' 1.48 ms and the
distinct/slot ratios; nothing measured that row's own split) and **what `verify` costs** (bounded
only by "a linear pass over ~600 kB of columns per module") — all three are measurement 4's.
**Whether the warm path is worth parallelising**: `research/04` §5 warns that at a 15 ms budget
thread wake-up can exceed the work and `fast-compiler.md` §10 says not to, and at a predicted 33 ms
warm `check` the question is still not live; M4-3 makes it so. **ext4, XFS, or a network
filesystem**: §6 is btrfs and tmpfs, and the per-file write cost is what would differ most.
