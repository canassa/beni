## 1. What this slice is, and what it is not

**Is:** a module is re-checked only when something it can OBSERVE about one of its imports changed.
The enumeration of "observe" is §3, it is proved complete by §4's instrumented run rather than
asserted, and it is enforced by a safe-build self-check (§9 M3-a) so that an omission is a compiler
error in the test suite and not a stale answer in the field. **Is not:** the emit-side cutoff,
`frontend_decode`, the whole-program passes, the pack file (M4-4); the `stat` fast path, the daemon,
the memory ceiling, watching, cancellation, garbage collection (M4-5); the declaration-level graph
(M4-6). §13 lists them with pointers.

**Why it is worth a slice, in one measurement** *(measured, §5.1)*. On the 100k corpus, warm
`check --jobs=1`: **40 ms** fully warm, **130 ms** with no cache — and **115 ms after a comment is
added to one leaf module**. A comment. The cache buys 12 % on the one case `fast-compiler.md` §2's
warm rows are about, because that edit moves **624 of 634 module keys** and **0 of 634 interface
hashes**. Nothing else left in M4 is a 3× on anything.

## 2. The decisions, and the alternative each rejected

| # | Decision | Rejected, in one line |
|---|---|---|
| 1 | An import contributes **`(interface hash, dependency digest)`**, replacing its key | The interface hash alone — §6 demonstrates two edits that leave the hash byte-identical and turn a clean build into an error, so it is not a firewall but a hole |
| 2 | The digest is a **second hash**, never folded into the record | Widening the record — it would put a module's private business into bytes every `.iface` golden and `--stage=raw` output asserts, bump `format_version`, and re-bless the whole golden set for nothing |
| 3 | The digest is **inductive over direct imports**, carrying each import's `(hash, digest)` | An explicit transitive type-reachability closure — the same answer computed twice, and the second computation is the one that can be wrong (§7) |
| 4 | The digest is keyed by **type NAME**, over the set the module's own record names | Keying on declaration ordinals or `TypeId`s — both move when a private declaration is added, which is the firewall defeat the `TypeId` leak already cost once |
| 5 | `core_epoch` becomes **`core_surface`**: the same one term, over core's `(hash, digest)` pairs instead of its keys | Narrowing it to implicit edges on the six well-known modules — sharper, and it needs an enumeration of the BUILD side's core reaches that is M4-4's (§7.1) |
| 6 | Keys are **finished on the DAG**, in the worker that claimed the module | A serial pre-pass — an import's interface hash exists only once the import has been checked or loaded, and a serial pass can only see the hashes of modules that HIT, which is the case the cutoff does not need |
| 7 | The DAG load re-interns through the non-mutating **`Global.find`**; a miss is a cache MISS | `getOrPut` with a lock, or a sharded `Global` — measured unnecessary: **0 of 24 281** cross-process re-interns would have missed `find` (§4.3), and a miss that degrades needs no proof at all |
| 8 | The enumeration is enforced by a **safe-build self-check**, not by this document | Trusting the reading — `plans/m4-plan.md` §8 risk 5 says a reading finds less than a run, and CLAUDE.md rule 3 says a green suite has repeatedly coexisted with real defects |
| 9 | `alias_body` is **withdrawn from the record** and lives in the digest | The `types` row `checker.md` §7 declared — a PRIVATE alias is reachable by name and has no `types` row, so the record could never have covered the case |
| 10 | The default flip is the **last commit**, behind the harness, a one-line revert | Flipping with the switch — a cache on by default must be right about every input, and the harness is what establishes that |

## 3. The enumeration: what a dependent's check reads

**The claim.** A module's check is a function of (its own source, its own options, the compiler
build, and for each module N it can reach: N's interface record and N's dependency digest). `X` is
exactly those two per reachable module. The work list is `plans/m4-slice-zero.md` §4's sixteen rows
plus what §4's census and two read-throughs found that it missed; every row is `file:line`.

### 3.1 The three channels

Every cross-module read on the checking path goes through one of three, and naming them is what makes
the enumeration finite: the **session `Types` table** (whole-program, dense `TypeId`, built serially
before any worker and read-only afterwards); **`interfaces[N]`** (the intended firewall, O(1)); and
**`artifacts.bir(N)`** (the other module's raw `Bir` — three sites, and §4 measures how often each
fires). `graph` is a fourth, but carries only metadata — `moduleName`, `moduleFile`, `lookup`,
`find`, `package`, `dependencies` — every item of which is already in the key's import terms or in a
`type_refs` row.

### 3.3 Why `TypeId` numbering is not a dependency

Slice zero's §4 row 1 says a check reads "every declaration of every module, to number `TypeId`,
private types included". True, and it is `Types.build`'s business rather than a dependency: the
question is whether a `TypeId` VALUE can reach anything a dependent emits or reports. It cannot, and
every place it used to has been closed: `Interface.Term.app`/`.alias` spend `lhs` on a `type_refs`
index since `792bf76`; `Dispatch.Shape.nominal` and `ExtDerivedUse.type` become names on the way to
the sidecar's bytes; the `derived` table sorts by EMITTED NAME TEXT (`Dispatch.zig:457-493` through
`Check.zig:1411-1452`); `Exhaustive` compares ids without printing one (`Exhaustive.zig:1159`);
`Lower` and `Emit` read `types.entry(id).name` and `.module`. **The experiment is slice zero §11.3's
E4 row re-run at 634 modules** *(measured, §5.2)*: a private type added to a leaf moves **0** interface
hashes, its own included. The digest is keyed by name over the set the record names, so it does not
move either — and `plans/m4-1.md` §6.1's row 5, the one that table called "the interesting one", is
kept: the leaf alone re-checks.

## 4. The instrumented run — proving the enumeration rather than asserting it

### 4.1 Method

A temporary patch (`scratchpad/m43/instrument-full.patch`, kept, tree reverted) adds `src/xmr.zig`:
a thread-local `reader`/`reader_file` set by `Check.Driver.check`, a thread-local `phase`, and a
fixed `Kind` enum. Instrumented: every `Types` accessor taking a module or a `TypeId` (`entry`,
`ofDecl`, `ofInterface`, `find`, `refIds`, `Builder.aliasBody`, `findWellKnown`); `Artifacts.bir`,
comparing the file index against the reader's; and sixteen `Interface` accessors, for which
`Interface` gains a temporary `owner: u32` set at `Resolve.zig:167` and `Check.zig:596`. Each records
`(kind, read module)` when the read module is not the reader's.

**What it cannot see, stated rather than glossed:** direct field reads such as
`iface.values[i].scheme` and `iface.types[i].ctors_start`. Every one is reached through an accessor
first — `findValue`, `findType`, `symbol`, `scheme` — so the KIND is counted even where the field
read is not. The counts are lower bounds on VOLUME; they are not lower bounds on the SET OF KINDS,
which is what the census is for. The permanent self-check (§9 M3-a) closes the gap by recording at
the `&interfaces[N]` handoff rather than inside the accessors.

### 4.3 The re-intern question, which decides where the load can run

M4-1 loads entries serially before the workers because a cross-process record's re-intern must
`getOrPut` into the thread-confined `InternPool.Global`. M4-3 needs the load on the DAG (§8). The
patch counts, for every string a cross-process load re-interns, whether `find` would have missed:

```
warm 100k --jobs=1   XMR-INTERN total=24281  would_miss_find=0
warm 100k --jobs=8   XMR-INTERN total=24281  would_miss_find=0
warm core            XMR-INTERN total=663    would_miss_find=0
warm tests/corpus    XMR-INTERN total=663    would_miss_find=0
```

**Zero, everywhere, at both widths.** The argument behind the number: every string in an entry names
either a declaration of a module in this build or a module in this build — value, type, constructor,
quantifier and method names come from the module's own source, and `type_refs`/`module_refs` rows name
modules and types that some module of this build declares — and M4-2 re-interns every module's whole
`Bir.symbols` column on every run. So the load may use `find`, needs no lock and no sharded `Global`,
and can run on any worker. **And the posture is degrade, not trap**: a `find` miss is a cache MISS and
the module is checked, so even if the argument is one day wrong the failure is a slow build.

## 6. The two gaps, demonstrated

Both are eight-line projects; both are §10's first two fixtures. Neither would be caught by the
interface hash, and each is a `beni check` that exits 0 over a program the cold compiler rejects —
the one failure mode `checker.md` §7 says a compiler may not have.

### 6.1 A private type's `equatable` bit

`Leaf` declares a private `type Hidden = H Int | Extra Int` and a `pub make : Int -> Hidden`; `Mid`
declares `pub same : Int, Int -> Bool` whose body is `Leaf.make x == Leaf.make y`. Change `Extra Int`
to `Extra (Int -> Int)`.

*(measured)* Before: `app:Leaf 5c2c9081ffef02f1b4f3f01810e6552a`, exit 0. After: **the same
`5c2c9081ffef02f1b4f3f01810e6552a`**, and `Mid.beni:6:17 NOT EQUATABLE`, exit 1. `Leaf` still checks
clean, so it is cached; its record does not move, because `Hidden` is private and has no `types` row;
`Mid`'s own record does not move either, because `same` is annotated. Under an interface-hash key
`Mid` hits and the build exits 0 over a program the cold compiler rejects.

### 6.2 A `pub type alias` body no scheme of its own module names

`Leaf` declares `pub type alias Pair = { a : Int }` and a `pub greet : Int -> Int` that does not
mention `Pair`; `Mid` declares `pub firstOf : Leaf.Pair -> Int` whose body is `p.a`. Rename the
alias's field `a` to `z`.

*(measured)* Before: `app:Leaf 3c04159f0261359519a124b72830713f`, exit 0. After: **the same
`3c04159f0261359519a124b72830713f`**, and `Mid.beni:6:6 MISSING FIELD`, exit 1. An `alias` term's
range is its arguments followed by the ACTUAL type, so an alias a `pub` value of the declaring module
mentions IS covered — verified: the same edit with `pub pairOf : Int -> Pair` present moves the hash.
This is the case where nothing mentions it, and §4 says no corpus in the project reaches the code
path at all.

**Two probes for the converse — the digest must not be wider than it needs.** Renaming a private
type's CONSTRUCTOR and adding a nullary constructor to a private type both leave the hash unmoved
*(measured)*, and both must leave the digest unmoved too: a dependent cannot name a private type's
constructors, `Exhaustive.ctorUnion` and `Solve.allNullary` reaching them only through
`Interface.findType`, which a private type is not in. Renaming the private TYPE does move the hash,
correctly — `type_refs` names it.

## 7. Transitive reachability, and the answer

**The question.** `checker.md` §7's first `type_refs` consequence says a reference is to the DECLARING
module, not the module it came through: `C` can use `B.mk : A.T` without naming `A`. `Types.find`
then resolves `(package, A, T)` against `A`'s whole declaration list (`Types.zig:303-311`). So `C`'s
check reads facts about `A` — rows 2–6 — with no import edge to `A` at all. `Solve.zig:2896-2907`
knows: it carries an `internal` guard for a method whose declaring module has no interface, with a
comment saying §6.8's implicit `ext_type` edges are not landed.

**The answer: the digest is inductive, so one level of import terms carries every level.** `digest(N)`
folds each of N's own direct imports' `(iface_hash, digest)`. `M`'s key folds its direct imports'
`(iface_hash, digest)`. By induction the key covers every module reachable through any chain of
imports — which is a superset of "reachable through a type reference", because a record can only name
a module its own module could resolve.

**Why not compute the closure.** It would have to be computed before the key — i.e. before checking
— from `type_refs` tables that only exist after checking; and it is a second derivation of a fact the
first one already has, which is where two derivations drift. The inductive form costs one extra
16-byte term per import in two hash inputs, in the shape M4-1's key already has and M4-1's fixtures
already exercise.

**What it costs the cutoff, honestly.** An inductive digest means a change moving `A`'s digest moves
`B`'s and therefore `C`'s key, so a DIGEST-visible change has a transitive wave exactly as M4-1's key
does. What stops it is that a digest-visible change is rare — a type's arity, kind, settled bits,
alias body or emitted derived set — and §5.2 is the evidence: a comment, a whitespace change, a
private value and a private type move none of them, and those are the edits the budgets are about.
**The implementer reports the digest wave beside the key wave** (§11 measurement 2); if it is large
on a real corpus, narrowing to "only the digest rows this dependent can name" is the next slice's.

### 7.1 `core_surface`, and the narrowing recorded but not taken

Same one term, different input: core's sorted `(module name, interface hash, digest)` list instead of
its keys. It buys the property that a comment or body edit anywhere in core no longer moves every
module in the project — a thing a user does under `--core-root` — and keeps the property that an
interface-visible core change reaches everything, which is correct anyway since `core/Basics` is
imported by essentially every module. **The cost is a barrier**: no non-core module's key can be
finished until every core module has settled. At `--jobs=1` that is free, `graph.order` putting core
first; at `--jobs=32` it serialises the first ~10 modules of a 634-module DAG, which already happens
for every module importing core. Measurement 5 is the number.

*Rejected: narrowing it to implicit edges on the six modules `Types.findWellKnown` names* — the set
`Graph.mintedModules` (`Graph.zig:408`) already mints edges for. It is sharper and needs a proof this
slice cannot give: `js/Reach.zig:224-233` resolves `String.compare` and `Basics.eq` by scanning those

## 8. The ordering problem, and the DAG-walk design

**The problem.** M4-1 computes every key in one serial pass over `graph.order` between `resolve` and
the check (`Session.zig:1285`), then loads every entry in a second serial pass (`:1298`). Under the
new recipe an import's interface hash exists only once that import has been CHECKED or LOADED, so the
serial pass can only finish the keys of modules all of whose imports hit — and the case the cutoff
exists for is precisely the one where an import MISSED and was re-checked to the same interface.

**The design, in five lines.**

1. The serial `cache_key` pass keeps everything with no import term — package, name, option string,
   `source_hash`, `sibling_hash` — as a per-module `own_terms` byte blob, and keeps the `cache_key`
   profile row. It loses only the import loop.
2. The `Driver` gains two published arrays, `iface_hash: [][16]u8` and `digest: [][16]u8`, one slot
   per module, written by the worker that finished that module and read only by its dependents.
3. `Driver.check(m)` finishes `m`'s key from `own_terms[m]` plus its imports' two published values,
   then attempts `CacheEntry.load` **on that worker**, re-interning through `Global.find` (§4.3). A
   hit calls the existing `install`; a miss runs `ModuleCheck` as today.
4. Whichever path ran, the worker computes `m`'s own `iface_hash` (on a hit it is `iface_bytes.hash`
   over the entry's `interface` section verbatim, so nothing is recomputed) and `m`'s `digest`,
   publishes both, and only then calls `finish(m)`, which is what releases its dependents.
5. `core_surface` is computed once, by the driver, after the last core module publishes and before any
   non-core module's key is finished — one extra readiness condition on the existing schedule.

**The invariants, because they are what a reviewer checks.** **Determinism (rule 5):** a key is a
function of `own_terms` and of values published by modules that `buildSchedule`/`finish`
(`Check.zig:434-478`, `:530-544`) guarantee are complete before `m` is released, so no key's value
depends on which worker got there first; the `--jobs=1`/`--jobs=8` byte-compare is the assertion and
it is already in the suite. **One writer per slot:** `iface_hash[m]` and `digest[m]` are written only
by `m`'s worker, the discipline `interfaces[m]`, `dispatch[m]` and `types.ref_ids[m]` already keep.
**Interning:** `Global` stays read-only for the life of the DAG, which is what it is today, and
`find` does not mutate it; M4-2's `Local` pools belong to the front-end phase and are merged before
the DAG starts. **Serial equivalence:** at `--jobs=1` `Driver.serial` walks `graph.order`, so keys
are finished in exactly the order the M4-1 serial pass used — one code path, one scheduling rule.
**Re-entrancy:** `plans/m4-plan.md` §2.6's five fixes are **still not needed**, for M4-1 §8's reason,
one build per process; re-verified for this slice, which adds two arrays torn down with the `Driver`
and moves a read that was already once per module. All five stay M4-5's.

**What it costs, and what moves.** The key's byte string grows 16 bytes per import; at 5 710 import
rows that is ~91 kB more hashed, ~0.02 ms. `cache_load`'s serial 5.89 ms becomes per-worker work —
the same at `--jobs=1` and parallel above it for the first time. `Session.checkSerial` loses
`loadEntries` and half of `computeKeys`, and the three counters it computes there move to after the
check, summed from per-module flags. `--cache-keys` still prints after the check with unchanged
output, so every M4-1 and M4-2 fixture written against it keeps working.

### 10.2 The differential harness — `plans/m4-plan.md` §4.5's matrix, made sharp

A driver (`bench/cutoff.sh`, `bench/churn.sh`'s successor and sharing its edit machinery) that, for
each project × each module × each edit class:

```
cold   = build into a fresh cache directory, capture every stream and output file
warm0  = build again; assert byte-identical to cold; assert modules_checked == 0
apply  the edit
warm1  = build; assert byte-identical to a COLD build of the edited tree
             (every stream, every output file, the exit code)
       assert the set of modules re-checked is exactly what the enumeration predicts
revert the edit
warm2  = build; assert byte-identical to cold; assert the re-checked set is the
             modules whose entry the edited state displaced, and no more
```

**The second assertion is the one that matters and the one that is new.** Byte-identity alone is
satisfied by a cache that never hits; the criterion is byte-identity **and** the counter. The
predicted set is computed by the harness from `--iface-hash` and `--dep-digest`, not hard-coded, so a
new edit class needs no new expectation.

Projects: `bench/corpus` (excluding `JsonCodecs.beni` and `NotesApp.beni`, which do not resolve from
a pristine root — the exclusion `bench/churn.sh` makes and §4.2's exit code confirms), `core` under
`--core-root`, and the directory fixtures under `tests/corpus/`. Edit classes: `bench/churn.sh`'s
E1–E4 plus §10.1's rows 2–16. **§10.1's rows on the five-module project join `test-blackbox`** —
~27 scenarios × 3 invocations, the shape `cache_test.zig` already has. The full cross over every
module of every project is thousands of builds and stays a documented `bench/` command with a stated
budget: **its wall time is reported and may not exceed ten minutes** on the M4 plan's machine, or it
is sampled deterministically (a fixed stride over the module list, seeded and printed).

## 14. Risks, and what could not be determined

**Risks**

1. **The enumeration is the slice.** A missing kind is a wrong answer that depends on history — the
   worst kind, unreproducible from a clean checkout. Three things stand between that and a shipped
   bug and none may be skipped: M3-a's self-check, §10.2's harness, and §10.1's rows 10, 13 and 16,
   which fail before the digest. §4.2 finding 1 is evidence that the list is complete over what the
   project compiles today; it is not evidence about programs nobody has written.
2. **The alias row is untested by every corpus the project has** (§4.2 finding 3). It is one of the
   two demonstrated miscompiles and its census counter is 0 on all four corpora, so its fixture is
   the only thing that will ever exercise it — it must land with the digest and not after.
3. **The inductive digest has a transitive wave** (§7). The right trade on the evidence, since the
   edits the budgets are about move no digest row — but `bench/corpus` has thirty `pub` declarations
   per module against the generated corpus's one, and nothing has measured the wave there.
   Measurement 2 exists to find out before it is a report.
4. **`ambiguous_method_receiver` is the one warning cached and replayed**, and a warning's prose is
   stored rather than recomputed (`plans/m4-1.md` §10 risk 3). If it names another module, a replay
   after that module changed could be stale — and unlike the error paths it is NOT closed by the
   clean-check rule, because a warning does not prevent caching. **One grep over
   `src/check/Diagnostics.zig`'s formatter is the implementer's first task**; if it names a module,
   the answer is a digest row or a refusal to cache that module.
5. **M3-d moves a read from a serial pass onto the DAG**, which `plans/m4-1.md` decision 9 chose
   deliberately. Its reason — `getOrPut` into a thread-confined pool — is measured away in §4.3, and
   the posture is degrade rather than trap, so the risk is a slow build and not a wrong one. It is
   still the commit most likely to be reverted, which is why it lands at the OLD recipe with no
   output change.
6. **`core_surface` introduces a barrier** the DAG does not have today (§7.1): free at `--jobs=1`,
   a serialised head of the walk at 32. Measurement 5.

**Could not determine**

- **Whether any cached WARNING embeds another module's identity** (risk 4). One grep settles it, and
  it is the implementer's first task, as `plans/m4-1.md` §10 and `plans/m4-2.md` §13 each handed one
  on.
- **The digest wave on a hand-written corpus.** §5.2 is the generated corpus, one `pub` declaration
  per module. Measurements 1 and 2.
- **What the cutoff is worth at `--jobs=32`.** `plans/m4-2.md` §13 said the "is the warm path worth
  parallelising" question was not live at a 33 ms warm check and that M4-3 makes it so. It does, and
  at a predicted ~41 ms warm check over a ~36 ms serial floor the answer may well still be no.
- **Whether §10.2's full cross fits ten minutes** or must be sampled. On `bench/corpus` alone it is
  18 × 23 ≈ 414 builds; the generated corpus would be ~14 000. Sampling is specified as the fallback
  rather than discovered as one.
- **Whether `find`-only interning holds for a program nobody has written.** §4.3 measured 0 misses
  over 24 281 strings on four corpora and gives the argument; the argument is not a proof, and §10.3
  item 28 is what makes the failure a miss rather than a crash.
