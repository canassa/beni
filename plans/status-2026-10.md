## 1. Summary

beni is three weeks old (first commit 2026-09-12, 822 commits since) and is already an unusually
solid **compiler**: ~132 000 lines of Zig, a checker rewritten from the ground up with no known
unsound, crashing or order-dependent case left, Elm-quality diagnostics, a formatter, an on-disk
incremental cache, a release optimiser that does whole-program specialisation, JSX typed against a
platform vocabulary, a Solid-style compiled-template renderer that beats Solid 2 (and now Solid 1)
on all nine js-framework-benchmark operations, a fiber runtime with structured concurrency, and a
browser TEA platform with commands, subscriptions and HTTP. Compile speed is far inside its own
budgets. What it is **not yet** is a language a stranger could build and ship a web app with: it
cannot decode JSON into a record, has no routing, no storage, no HTTP headers (so no auth), no
packages, no dev server or watch mode, no source maps, no editor support, no user documentation
and no installable release. The core engineering is ahead of the product surface by a wide margin;
the shortest path to "a developer can ship a real app" is almost entirely platform, library and
tooling work on top of what exists, with executable schemas as the one large compiler-side piece.

## 6. Recommended roadmap

Sizing is in weeks at the project's current pace (an owner directing implementer agents, spec
first); "S" ≤ 1 week, "M" 1–3 weeks, "L" 3–6 weeks. Each milestone ends with an app in
`tests/corpus/browser/` and in an `examples/` directory, which is its acceptance test.

**Milestone 1 — TodoMVC, shipped (≈ 3–4 weeks).**

1. *Browser essentials* (S–M): `Event` accessors (`key`, modifiers, pointer), keyboard events in
   `Browser.Events`, `Storage` (`impure`, `Result`-returning), `Random` in a fiber, `Url` read-only.
2. *Defects and logging* (S–M): the decided defect rule (stop, log, development crash screen), a
   platform logger usable under `--release`, the crash reporter naming the `foreign`.
3. *Developer loop v0* (M): `beni new` with a template, an emitted `index.html` (a manifest key,
   so the platform owns it), `beni build --watch` as a polling one-shot over the existing cache —
   no daemon needed — and a tiny static `beni serve` for development.
4. *Source maps for development builds* (M): pulled forward from M5; the browser-first rule makes
   debugging emitted JS without them the first thing a user hits.
5. *TodoMVC itself* plus a first "getting started" page (S).

**Milestone 2 — a small real app: auth, API, routing (≈ 6–9 weeks).**

1. *Executable schemas, synchronous v1* (L): settle the four schema questions; the library path
   first, then specialised parse/print, differential-tested. This is the critical path; a
   stop-gap `Json` module in core would be thrown away and is not recommended.
2. *Http v2* (M): methods, headers, status and response headers, timeouts, typed bodies through
   schemas (`Http.request` with a schema for each direction).
3. *Navigation* (M): `Url` parsing, `Tea.application` with URL change and link requests, the
   navigation capability record, the link-click guard.
4. *Effects completion for apps* (M): `race`, `timeout`, `retry`; the remaining effects decisions.
5. *Interop, interim* (S): document project-local platforms as the supported escape; decide ports.
6. *Acceptance*: a RealWorld/Conduit-class app (login with a bearer token, CRUD against an API,
   five routes, forms with validation through schemas).

**Milestone 3 — usable by people who are not on the project (≈ 6–10 weeks, partly parallel).**

1. *Distribution* (S): CI on Linux/macOS/Windows, release binaries cross-compiled by Zig, an
   install script, a version scheme.
2. *Packages v0* (M–L): ordinary-package manifests with path and git dependencies and a lockfile;
   a registry later.
3. *Editor support* (M–L): a TextMate/tree-sitter grammar first (S), then an LSP v0 — diagnostics,
   format, hover types — on the daemon (M4's remaining slices).
4. *`beni test`* (M): top-level `expect`, a TEA test driver with a fake clock and fake services.
5. *Documentation* (M): a guide, the `core`/platform API reference generated from `--|` comments
   (the doc-example gate already compiles them), the two example apps.
6. Then: code splitting, SVG, `Intl`, SSR + hydration.

## 7. Risks

**Technical**

- **Schemas are the critical path and the most complex remaining design**, entangled with
  effects (effectful transformations, the stored-function ABI) and with release specialisation.
  Shipping a synchronous v1 without freezing the ABI is what keeps it off the path.
- **Fresh foundations.** The checker (one week old), the array-backed `List` (one day), the
  runtime in beni and whole-program specialisation all landed in the last ten days. The
  differential oracles are strong, but no external program has exercised them.
- **One engine.** Every rendering and size claim is Chromium; Firefox and Safari have scheduler
  numbers only. A real-device and mobile pass is owed before speed is a public claim.
- **The wall's cost.** Rule 6 makes every capability the core team's job, and platforms are Zig
  compiled into the binary, so a third party adding a platform rebuilds beni. That is right for
  guarantees and slow for an ecosystem; the interop question decides how slow.
- **Incrementality under whole-program optimisation.** Release specialisation is whole-program by
  construction; development builds must stay per-module for the daemon and LSP to be fast. A
  `pub` signature edit already re-checks almost everything.
- **Document weight and drift.** `backend.md` is over 6 000 lines, `checker-findings.md` 5 700,
  the diary 4 000; `README.md`, `language.md` §0 and `plans/queue.md` (marked "PARKED") lag the
  code, and some plan entries carry next-day dates. Normative-documents-first only works while
  the documents stay true.
- **Toolchain churn.** Zig 0.16's std has already cost a file-read trap and a stale-binary
  incident; every Zig upgrade is a project.

**Project**

- **Research outpaces product.** 47 research reports and three ground-up rewrites in three weeks,
  zero external users. The next phase needs the opposite ratio: example apps as acceptance tests,
  and features chosen by what those apps hit.
- **Decision backlog.** The owner's queue (section 5) gates schemas, logging, the daemon and
  interop; several "for the owner" markup decisions are already built and would be expensive to
  overturn late.
- **Direction changes.** Implementation was parked and un-parked, the sequence type flipped twice
  in a day. Each change was well argued; the risk is to anyone building on beni meanwhile.
- **Bus factor.** One owner, agent-written code and agent-oriented documentation. A user-facing
  guide and CI are also the onboarding path for a second human contributor.
