# M4-1 — the persistent cache: its key, its layout on disk, and the sidecar

**Status:** plan, 2026-09-19, written at `1ac6fa9` with M4-0 landed (`506f596`..`f8357ba`,
`792bf76`). Nothing is started. The contract lives in four documents and this one holds only what is
plan: the key, the directory and the acceptance axis are
[`fast-compiler.md`](../docs/design/fast-compiler.md) §8; the entry's bytes and the dispatch sidecar
are [`checker.md`](../docs/design/checker.md) §7; the two flags are
[`frontend.md`](../docs/design/frontend.md) §1; the sibling term is
[`boundary.md`](../docs/design/boundary.md) §7.3.

**Standing.** The owner decided on 2026-09-19 that M4 comes first (`plans/m4-plan.md` D5), in the
plan's own order, cache before socket (D1). D6–D9 are the daemon's and are **PENDING**; nothing here
depends on any of them.

Measurements marked *(measured)* were taken here, 2026-09-19, on the M4 plan's machine (Ryzen 9
5950X, 32 threads, Zig 0.16.0, ReleaseFast), corpus `zig build bench -- --generate=100000` — 624
files, 1 835 956 bytes, 633 modules with core.

---

## 1. What this slice is, and what it is not

**Is:** a module whose cache key is unchanged is not re-checked. Its interface record, its dispatch
table and its diagnostics are loaded from disk and installed; `constrain`, `solve`, `exhaustive`,
`fillInterface` and `Cycles` never run for it. Both `beni check` and `beni build` take the skip.

**Is not:** the firewall cutoff. An importer of an edited module is re-checked in M4-1 whether or
not the edit moved the import's interface hash, because §2's key carries the import's key and not
its hash. **That is the whole of M4-3**, and M4-1 is what makes it measurable.

So M4-1's demonstrable win is a second build of an unchanged tree, plus the nine core modules and
the platform, which are unchanged in every build anyone will ever run. Everything sharper waits.

## 2. The decisions, and the alternative each rejected

| # | Decision | Rejected, in one line |
|---|---|---|
| 1 | An import contributes its **cache key**, not its interface hash | The `(interface hash, sidecar hash)` pair — M4-3's answer without M4-3's proof, and the sidecar that would carry the settled bits does not exist while every `Bir` is in memory |
| 2 | `--cache-dir=<path>`, **no default**, opt-in in M4-1, default in M4-3 | On by default now — a cache on by default must be right about every input, and this slice's fixtures are what establish that |
| 3 | Content-addressed, one file per key, two-level fan-out | One file per module path, overwritten — two option sets fight over one file and a stale entry becomes a wrong answer instead of an unreferenced one |
| 4 | Write-to-temp + `rename`, no locks | A lockfile — a crashed build then wedges the next one, and `rename` already gives every property needed |
| 5 | The entry holds record + **dispatch table** + diagnostics | Record only, `check`-benefits-alone — the warm path would then be asserted only through `check`, and `run/` and `emit/` are where a serialization bug shows as a wrong program |
| 6 | Errors: **refuse to write**; warnings: cache and replay | Cache everything and trust the stored diagnostics — an `<error>` scheme is a hole a dependent checks clean against, and one bug there is `beni check` exiting 0 on a broken program |
| 7 | The build id is computed by `build.zig` over `src/` and passed as a build option | Hashing the installed binary at run time — correct, and ~2 ms of a 15 ms budget |
| 8 | Always read and hash the source; no `stat` fast path | The fast path now — M4-1 reads every source anyway, so it would save 0.57 ms of a 4.5 ms read; it pays when the read goes (M4-2) |
| 9 | Reads are serial, before the workers; writes are serial, after the check | Reading on the DAG — `InternPool.Global` is thread-confined and a cross-process load must `getOrPut` (`src/resolve/iface_bytes.zig`'s header reserves exactly this) |
| 10 | The declared-type sidecar of `plans/m4-slice-zero.md` §4 is not this slice's: M4-3 needs its definition and its hash, M4-4 its bytes | Writing it now — every row is a function of the declaring module's `Bir`, which M4-1..M4-3 all keep present, so it would be bytes nobody reads |

## 3. The key, and what it costs

The recipe is `fast-compiler.md` §8, byte for byte. Three notes that belong to the plan rather than
the contract:

1. **Uncacheability propagates.** A module the graph poisoned (a cycle member), or one whose import
   did not resolve, has no well-founded key: it is marked uncacheable, contributes 16 zero bytes to
   its importers, and marks them uncacheable too. One `bool` beside the key.
2. **Cost, derived from measurement.** Hashing every source is 1 835 956 bytes at the 3.2 GB/s the
   `iface` bench row measures (980 920 bytes in 0.304 ms) = **0.57 ms**; the 633 key strings are
   ~200 bytes each and cost ~0.04 ms. Total **~0.6 ms at 100k lines**, against `plans/m4-plan.md`
   §6's « 1 ms and the 4.68 ms whole-program serial floor. The `read` phase alone is 4.5 ms
   *(measured)*.
3. **`--cache-keys` is the instrument, and it lands before any file does.** Hidden, `check`-only,
   one `<package>:<Module> <32 hex digits>` line per module sorted by that key — `--iface-hash`'s
   twin (`src/check/Command.zig:113`). The whole edit-scenario table of §6 is fixtures against it,
   with no cache directory in sight, which is why it is commit 2 and not commit 6.

| `merge_interners`, `graph` | runs | runs |

## 5. The ordered change list

Each step is green on `zig build test && zig build test-blackbox && zig build fmt-check` on its own.

**M1-a — the compiler build id.** `build.zig` computes `SipHash128(1,3)` over `beni.version`
(`src/beni.zig:8`), `builtin.zig_version_string`, the optimize mode, the target triple and every
file under `src/` (path then bytes, sorted), and passes it as a build option. `beni version` prints
it after the version. `--cache-build-id=<s>` parses on `check` and `build`, hidden. Touches
`tests/blackbox/blackbox_test.zig`'s version assertion. Nothing else moves.

**M1-b — the key, and `--cache-keys`.** `src/cache/Key.zig`: the recipe of `fast-compiler.md` §8 as
a pure function with hermetic golden vectors, plus the serial pass over `graph.order` that fills one
key per module and the uncacheable bit. `--cache-keys` prints them. `Profile.Phase` gains
`cache_key`. **This is where §6's edit-scenario fixtures land**, all of them, before a byte is
written to disk. Also touches `blackbox_test.zig:281`'s exact-phase assertion.

**M1-c — the entry container.** `src/cache/entry_bytes.zig`: header, key field, section table,
the `interface` section (`iface_bytes.write`'s bytes verbatim) and the `diagnostics` section, with
in-source round-trip tests and the corrupt-input table of §6.4. Nothing reads or writes a file yet.

**M1-d — the dispatch sidecar, and `--roundtrip-dispatch`.** `src/cache/dispatch_bytes.zig`:
`write`/`read`/`resolve` to `checker.md` §7, with `module_refs` and `type_refs` replacing every
`Graph.Index` and `TypeId` (`src/check/Dispatch.zig:49`, `:97`, `:119`) and `symbols` becoming
offsets into `strings`. `--roundtrip-dispatch` is `--roundtrip-interfaces`' twin: every module's
table is written, read and re-resolved in place the moment its check finishes, so every emitted file
downstream is built from a table that has been through the format. The matrix's existing roundtrip
runs pass **both** flags, so the format is proven lossless over 336 fixtures at no extra runs.
**This is the slice's cut line**: without M1-d, `build` can take no hit and `check` keeps its skip.

**M1-e — `--cache-dir`, `--no-cache`, and writing.** The directory, the `v<n>/<kk>/<rest>.bec`
layout, write-to-temp-and-rename, the clean-and-unpoisoned rule, the serial write pass after
`Check.run`. `Profile.Counter` gains `cache_hits`, `cache_misses`, `modules_checked`;
`Profile.Phase` gains `cache_store`. Output does not move by one byte; `cache_hits` is 0.

**M1-f — reading, and the hit path.** The serial pre-pass reads, validates against the shell,
re-interns through `getOrPut` and installs the record; the DAG hit path resolves the sidecar's two
reference tables through `Graph.find`/`Types.find`, installs the table, replays the diagnostics and
fills `ref_ids`. `Profile.Phase` gains `cache_load`. The §6 scenarios now assert hits and misses,
and cold ≡ warm.

**M1-g — the matrix's third axis.** `tests/blackbox/matrix_test.zig` gains a cold-with-cache run at
`--jobs=1` into a fresh directory and a warm run at `--jobs=8` against it, both byte-compared with
the plain run, both asserting counters. Two runs, not four: the `--jobs` cross rides on the pair.

**M1-h — the numbers.** `bench/bench.zig` gains a `cache` row (cold write, warm read, bytes on
disk, key time) and §7 of this file is filled in, as `plans/m4-slice-zero.md` §11 was.

### 6.2 Correctness under failure

11. **A module cached while broken.** `Leaf` has a type error: build twice into one cache directory
    — identical stderr, exit 1 both times, `Leaf` a miss both times, no entry file for `Leaf`'s
    key. Then fix `Leaf` and assert the project compiles and `Mid` re-checked. *Fails before the
    clean-bit rule with an exit 0 and an `<error>` hole.*
12. **A module with a WARNING is cached and replays it.** An `ambiguous_method_receiver` in the root
    package: warm run's stderr byte-identical, `cache_hits` includes that module.
13. **A poisoned module.** Two modules in an import cycle: neither is ever written, the cycle is
    re-reported identically, and the modules outside the cycle still hit.

### 6.3 The cache as an environment

14. **`--jobs=1` writes, `--jobs=8` reads** and the reverse: all hits, output byte-identical. The
    fixture that would catch a `Symbol` or a `Graph.Index` reaching the bytes.
15. **Two processes at once** on one project and one cache directory: both exit 0 with identical
    output, and a third run hits everything.
16. **A read-only cache directory**, empty: exit 0, output identical to no cache, `cache_hits` 0 and
    no message on either stream. **Pre-warmed and then made read-only**: every module hits.
17. **`--no-cache` beside `--cache-dir`**: nothing read, nothing written, counters 0.
18. **`--cache-dir` naming an existing FILE**: exit 2, the path named, like `--out`'s failure.
19. **A path with spaces and non-ASCII**: `<tmp>/a cache dír/` works.

### 6.4 Corrupt entries — each a MISS, never a crash, never a wrong answer

20. Zero-length; truncated mid-section; wrong magic; unknown `format_version`; a section offset or
    length past the end; a header key that is not the file's name; a `strings` record overrunning
    its blob; a `module_refs`/`type_refs` index out of range; a `Target` tag no version defines;
    random bytes. Each: the build produces byte-identical output to a cold one and exits the same
    way. In-source for the two formats' readers, black-box for the six that a fixture can write.
21. **A loaded record whose shape disagrees with the shell** — fabricate one with an extra `pub`
    value — is a miss, not a miscompile.

### 6.5 The matrix

22. `matrix_test.zig`'s cold-with-cache and warm runs over every checker-driven kind, as M1-g.

## 7. Measurements the implementer must report

Against `plans/m4-plan.md` §1.1's budgets, on the M4 plan's machine, ReleaseFast, 100k corpus:

1. **Warm vs cold `check` and `build`**, at `--jobs=1` and `--jobs=8`. *Expected*: warm `check`
   55–70 ms against 127 ms cold, warm `build` 110–140 ms against 180 ms — because the front end
   (`read`+`lex`+`parse`+`lower` = **39.8 ms** *(measured)*), `resolve` (**7.89 ms**), the 4.68 ms
   whole-program floor and, for `build`, `emit` (**90.46 ms**) all still run. **The 15 / 60 / 25 ms
   warm-rebuild budgets are not reachable in M4-1 and are not this slice's to miss**: they need
   M4-2's front end off the warm path and M4-3's cutoff, and stating that here is what keeps the
   measurement honest.
2. **Key computation**, as the `cache_key` profile row. Must be « 1 ms; predicted ~0.6 ms.
3. **Entry write time, cold, 633 modules**, as the `cache_store` row. 633 creates plus 633 renames
   is the number to watch: if it exceeds 20 ms, move the write onto the checking worker (decision 9
   is about reads, not writes).
4. **Entry read time, warm**, as the `cache_load` row, against the 0.979 ms `iface` read row.
5. **Bytes on disk**: after one cold build, and after 100 single-line edits with no GC. The
   interface half is 1 549 bytes per module *(measured, slice zero §11.1)*; the dispatch half is
   unmeasured.
6. **`--roundtrip-dispatch`'s cost**, as slice zero measured `--roundtrip-interfaces` at +1.1 %.
7. **`zig build test-blackbox` wall time**, before and after. The roundtrip axis cost +25.4 s for
   four runs; two more should be ~+13 s.

## 8. Re-entrancy: what M4-1 needs from `plans/m4-plan.md` §2.6

**None of the five.** M4-1 is still one build per process, so `SourceStore.finish`'s append,
`worker.diagnostics` and `worker.counters` never being reset, and `Artifacts.resize`'s unconditional
`freeAll` are all unreached. `Schemes.Writer.attach`'s non-idempotence is the one that could have
bitten and does not: a hit **replaces** `interfaces[m]` wholesale rather than re-attaching, which is
the shape `--roundtrip-interfaces` already established (`src/check/Check.zig:1109-1110`), and a miss
attaches exactly once as it does today. **M4-3 needs none of them either**, for the same reason. All
five are M4-5's, and they become mandatory the moment one process serves two builds.

## 10. Risks, and what could not be determined

**Risks**

1. **The dispatch sidecar is where a silent miscompile can hide.** `plans/m4-plan.md` §8 risk 2
   names the configuration exactly: a cached callee and a recompiled caller computing the
   hidden-parameter order independently (`Schemes.quantifierOrder` versus `Schemes.instantiate`).
   M1-d's `--roundtrip-dispatch` over 336 fixtures and M1-g's warm axis over `run/` and `emit/` are
   the two things standing between that and a wrong program; neither may be skipped to save time.
2. **The slice's win is narrow by construction.** Only an unchanged tree hits. If anyone reads
   "incremental" into M4-1 and measures an edit, they will find nothing; §1 and §7 say so twice for
   that reason.
3. **A rendered message in an entry could go stale.** The entry stores the prose the checker
   rendered, not a recipe for it. If any checker message embeds another module's PATH or a line
   number of one, a replay after that module moved would be wrong. Nothing was found, but nothing
   was audited either — see below.
4. **`diagnostic.Code` is stored as an integer**, which is safe only because the build id covers
   `src/diagnostic.zig`. Weaken the build id to a version string and this becomes a wrong-message
   bug with no test that can see it.
5. **`--cache-dir` is product surface** and has to be supported forever, unlike the four hidden
   flags. That is deliberate — CI needs to name a cache directory — but it is a one-way door.
6. **633 serial `rename`s on the cold path** may be a measurable regression on a 180 ms build.
   Measurement 3 exists to find out before it is a report.

**Could not determine**

- **Whether any checker diagnostic embeds a cross-module path or line number.** One grep over
  `src/check/Diagnostics.zig`'s formatters settles it and is the implementer's first task; if one
  does, that code's diagnostics are not cacheable and the module carrying one is not cached.
- **The dispatch sidecar's size.** The interface half is measured at 1 549 bytes per module; the
  table's is not, and `bench/corpus` (30 `derived` rows per module) and the generated corpus (almost
  none) will differ by a lot.
- **Whether a cache written on one machine loads on another** with the same build id. It should —
  every scalar is little-endian and no `Symbol`, `TypeId` or `Graph.Index` reaches the bytes — but
  nothing tests it and nothing should claim it until something does.
- **What the warm path costs at `--jobs=8`.** `research/04` §5 warns that at a 15 ms budget thread
  wake-up can exceed the work; measurement 1 is the first data point beni will have.
