## 2026-11-03 17:23 UTC — run the workers corpus in CI

**What I did.** #697 had no pull request, so nothing waited on Cesar but the work itself. I added a `workers` job to `.github/workflows/ci.yml`, built like the `browser` job: the `.#workers` shell, a Nix store with a key and a 4G bound of its own (the shell's closure is 3.05 GB against the default shell's 1.0 GB), saved from master only, and `zig build test-workers` on every pull request, with `check` needing it. It sets `BENI_RUN_HASH_DIR` empty, so every Worker runs every time, about a minute for the corpus, and it restores the `tests` job's Zig caches and saves none. The four places that said no CI job runs the corpus — CLAUDE.md, flake.nix, a build.zig comment and §9.12 (k) — say that CI does.

**What I learned.** The flake keeps a set `BENI_RUN_HASH_DIR`, an empty one too, and `build.zig` reads empty as no cache, so a CI job can opt out of the run-hash cache in one line. `actionlint` from nixpkgs runs through heavy-run in seconds; its one note on the workflow, a single-quoted `$BENI_RUN_HASH_DIR` that the inner shell expands, is on master's `tests` job too. A comment in `build.zig` or `flake.nix` is part of CI's cache keys, so even a comment there costs one cold cache.
