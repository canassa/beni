## 2026-11-05 20:26 CET — browser-inline compiles event handlers that are functions

**What I did.** #1176. On `browser-inline`, an event whose handler value names no key when the program is built — `onClick={handle}` with `handle : Event → Msg`, a lambda, a message the model holds — was a class-4 limit ("its message would need a dispatcher"). The dispatcher exists since #1174, so the `.value` arm of the event plan (`platforms/browser-inline/zig/inline.zig`) now gives a dispatch plan: the listener is `on(E[n], dispatch, type, make)`, and `make`, the handler applied to the payload, is what `send` reads of the event. Spec first: `browser-inline.md` §8.3, §8.7 and §5, amended 2026-11-05. Pages: `browser/inline/LinkGuard` gets back its `handled` link; `build/bad/inline/MessageValue` became the page `browser/inline/MessageValue`; `browser/inline/HandlerFunction` and its twin `browser/tea/InlineHandlerFunction` (the same bytes) cover a keydown, an input and a pointer through their extractors, an arm, a declared `preventDefault` and a helper's argument; `browser/prerender/EarlyFunctions` is `EarlyInput` with lambdas and the same goldens; `emit/release/inline/HandlerFunction` pins the shape. Every master `browser/inline/` page, dev and release, is byte for byte what master's binary writes (1 606 files).

**What I learned.** The timing rule has one right place in this runtime, and it was already there: `send` calls its `read` argument before it looks at the queue (#559). So the handler goes in `read` and the dispatcher in `f`. If the handler were in `f`, a queued send would run `preventDefault` after the event. A stateful control on such an event's element must be written back by every key's handler, because the key is known only when the event fires. The queued build of a worktree compiles whatever is on disk when its slot frees, not when it is queued: to keep a master binary, I took the fix out of the tree until that build ended.
