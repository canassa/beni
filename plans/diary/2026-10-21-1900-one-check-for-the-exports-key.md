## 2026-10-21 19:00 CEST — one check for the exports key

**What I did.** Answered the Claude review of #599 (the `"exports"` output key). The runtime-module refusal was reported in the development entry path only, so a release build hoisted the same chain and `check` never saw it. The test moved into `checkEntryExports`, which every path runs before anything is written, as a static fact of the chain: a lowering plus a markup module is a runtime module. Two `build/bad` fixtures pin the two refusals the review found without a fixture (`ExportsListOnPlatform`, `ExportsWithRuntimeModule`). The warning takes its severity at the report call, a `comptime` assert pins the entry bindings' length against `Rename`'s eight characters, the Manifest test covers `[]` and `null`, and `backend.md` §2 says why a listed name is ASCII only and that a runtime's `exports(name)` must throw. Proved the failing side with a beni built from the branch point in a second worktree: all six fixtures fail on it. Rebased onto master, re-recorded the run hashes, gates green.

**What I learned.** A refusal that lives in one emit path is three defects, not one: development, release and `check` each decide alone. Put a manifest-level refusal where the manifest is read, once. A `build/bad` fixture whose program is formatted by hand fails `beni-fmt-check` before it fails anything else: run `beni fmt` on a new fixture before the gates. The failing side of a feature's fixture is cheap to prove when a worktree with a seeded Zig cache holds the branch point: one `zig build` under the lock, then the fixtures by hand.
